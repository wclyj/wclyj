# 平时很快的语句，为什么会突然慢一下

有些语句平时几毫秒，偶尔变成几百毫秒甚至更久，过后又自己好了，很难抓现场。这种短促的变慢，常常不是索引忽然消失，而是 InnoDB 在那一瞬间把脏页写进了磁盘。

## 内存里的页和磁盘上的页会暂时不一样

更新走 WAL。事务改的是缓冲池里的页，并把重做记录按顺序写进 redo log，写完就可以向客户端确认。数据文件里的那一页，可以晚一点再改。

用社区工具室的记账来对照：白板是 redo，本子是数据文件，管理员脑子里记着的当前数量是缓冲池。某件工具原来借出 24 件，这次又借出 7 件。管理员在脑子里改成 31，同时在白板上记一笔。本子上可能还写着 24。在把本子改过来之前，脑子和本子不一致。

缓冲池里的页和磁盘上同一页内容不同，这页就叫脏页。刷回磁盘、两边一致之后，叫干净页。脏页和干净页都在内存里，不是“脏了所以不在缓冲池”。

把“再借出 7 件”走完可以看见三个位置各是什么。缓冲池里的数量从 24 改成 31，redo 追加一条记录，客户端就可以拿到成功。账本文件上可能仍写着 24。这笔差异会一直留到某次刷盘。刷完之后，如果这页还留在缓冲池里，它变成干净页，内容仍是 31，并不会因为刷过就从内存里消失。

干净页要被挤走时，内存可以直接让给新页，因为磁盘上已经是同一份内容。脏页不行：丢掉内存里的 31，下次读盘只能得到 24，中间那次借出就没了。redo 里虽然还留着记录，正常的读路径也不会为每一次缺页去重放日志。否则“内存没有，磁盘就一定是对的”不再成立，所有读都要先检查日志，缓冲池就失去意义。

平时的更新快，是因为它只写内存和顺序日志。偶尔抖一下，多半是某次请求碰上了刷脏页，被磁盘拖住了。

## 什么情况会刷

还是用工具室的白板。管理员会在四种情况下改本子。

第一种，白板写满了。再有人来借，必须先把白板上还没入账的记录抄进本子，擦出空位。对应 redo log 写满。redo 是环形的：写位置 `write pos` 往前追，追到检查点 `checkpoint` 就没有空位了。此时 InnoDB 停掉所有更新，把检查点往前推，推的过程中要把这段日志所覆盖的脏页全部刷盘。检查点不能只改一个指针。从旧位置推到新位置，中间那段日志对应的脏页都必须先落盘，新空出来的弧才可以继续顺序写。

第二种，要记的事太多，脑子快满了。来了新的一页，必须先忘掉一页旧的。若忘掉的是脏页，得先写回本子。对应缓冲池不够用。不能图省事把脏页直接丢弃、下次再从磁盘读入并用 redo 重放。那样的话，内存里没有的页，磁盘上也不一定对，每次缺页都要重放日志，读路径会垮。刷脏页换来一个简单不变式：

- 页在内存里，内存中的版本就是当前结果，直接用；
- 页不在内存里，数据文件上的版本就是当前结果，读进来就能用。

第三种，柜台闲着。没有人借还的时候，顺手把白板抄进本子。对应 MySQL 觉得系统空闲，后台线程见缝插针地刷一些脏页。生意忙时也不能完全不刷，否则白板很快又满。

第四种，年底盘点关门。全部账先结进本子，明年开门不用先翻白板。对应实例正常关闭：把脏页刷完，下次启动可以直接读数据文件，少一段恢复。

第三种没有用户在等，第四种库本来就要停。需要认真看的是前两种，它们会撞上正在执行的语句。

redo 被写满时，所有更新停住，监控上的写入量会掉到 0。这是 InnoDB 极力避免的状态。

内存不够则是常态。缓冲池里的页有三种：还没分配的、在用且干净的、在用且脏的。实例跑久了，空闲页很少。新页不在内存里时，只能淘汰最久不用的页。淘汰干净页，直接复用；淘汰脏页，先刷盘变成干净页再复用。

刷脏页本身不可怕，下面两件事才会让语句明显变慢：

1. 一次查询要腾位置，连带刷掉太多脏页，这一次查询的延迟被拉长。
2. 日志写满，更新全部堵住，写吞吐掉到 0。

所以引擎要控制脏页比例，别让系统滑进这两种状态。

## 刷多快，由两个压力里更急的那个决定

先告诉 InnoDB 磁盘能承担多少 I/O，它才知道“全力刷”是多快。参数是 `innodb_io_capacity`，建议设成磁盘的 IOPS。可以用 fio 做 16KB 随机读写来量，例如：

```bash
fio -filename=/data/fio.test -direct=1 -iodepth 1 -thread -rw=randrw \
  -ioengine=psync -bs=16k -size=1G -numjobs=4 -runtime=30 \
  -group_reporting -name=pool_probe
```

这个参数设小了，问题很常见。一块 SSD 的随机能力远高于每秒几百次，`innodb_io_capacity` 却留在 200。InnoDB 就按这个偏低的上限慢慢刷，脏页产生的速度超过刷出的速度，脏页堆积，随后查询淘汰页和更新写日志都会变慢。主机的 IO 利用率看起来还不高，因为引擎自己不敢用满磁盘。

不能一直全力刷。磁盘还要响应用户的读和日志写。刷盘速度要看两件事：脏页有多挤，redo 还有多少空。

`innodb_max_dirty_pages_pct` 是脏页比例的参考上限，默认 75。设当前脏页比例为 M。InnoDB 先算一个 0 到 100 的数：M 已经不低于上限时取 100，否则大约是 `100 * M / 上限`。脏页越接近 75%，这个数越大。

另一边，当前 redo 写入序号和检查点序号的差记为 N。N 越大，说明日志越快被写满，引擎另算一个同样落在 0 到 100 的数。算法细节可以不记，只要记住 N 变大，这个数就变大。

两个数取更大的那个，记为 R。后台刷脏页的速度大约是 `innodb_io_capacity * R%`。脏页比例和日志剩余空间，谁更危险，谁就把速度抬上去。

举一个具体比例。脏页占缓冲池 45%，上限是 75，前一个数大约是 60，表示用六成的 IO 能力去刷。若此时 redo 还很空，后一个数更小，R 取 60，刷盘让出其余能力给用户请求。反过来，脏页只有 20%，但写位置已经快追上检查点，后一个数接近 100，R 就取 100，引擎会按 `innodb_io_capacity` 的全速去刷，宁可暂时挤占用户 IO，也要避免更新全部停住。两个信号是或的关系，不是平均。只盯着脏页比例、不管日志剩余空间，仍然可能在比例不高时突然抖一下，那就是日志先告急。

因此业务侧感觉到的“抖”，来源可以是：你的查询恰好要淘汰一个脏页，不得不先写盘；也可以是后台正在按 R 刷盘，占用了 IO，你的更新跟着变慢。

避免的办法是把 `innodb_io_capacity` 设到磁盘真实能力附近，并盯住脏页比例，别让它经常贴着 75%。比例用状态量相除：

```sql
show global status like 'Innodb_buffer_pool_pages_dirty';
show global status like 'Innodb_buffer_pool_pages_total';
```

两个 `Value` 相除即可。持续高于百分之六七十，就该看是容量设小了、redo 太小，还是写入确实超过了磁盘。

## 刷一页时会不会把邻居一起拖下去

查询如果必须先刷一个脏页，本来就比平时慢。还有一个机制会让它更慢：准备刷某一页时，若相邻的页也是脏的，就一起刷；邻居的邻居如果也脏，继续捎上。随机写被合并成更大的连续写。

`innodb_flush_neighbors` 控制这件事。设为 1 时启用这种连坐，设为 0 时只刷当前页。

机械盘时代这很值。随机 IOPS 往往只有几百，把相邻脏页合并成一次顺序写，能少很多次寻道。SSD 的随机能力高，瓶颈常常不在“能不能随机写”，而在语句被额外的页拖住多久。这时把该参数设成 0，刷完必须刷的那一页就返回，响应时间更稳。8.0 的默认值已经是 0。

## 小结

WAL 把提交路径上的随机写收成顺序的 redo，换来的是缓冲池里的脏页。脏页由后台按比例刷出，也会在内存不够、淘汰旧页时被同步刷出。redo 写满则会让所有更新停下来等检查点。

`innodb_io_capacity` 要接近真实 IOPS，脏页比例不要长期接近默认上限。机械盘可以让邻居页一起刷，SSD 上关闭邻居刷，避免一次抖动扫进一片无关的页。

## redo 只有很小一截时会怎样

一台内存 64GB、`innodb_io_capacity` 设到 15000 的实例，redo 一般会留出数 GB、分成多个文件。若误留成单个 64MB 的文件，会发生什么？

日志环太短，`write pos` 很快追上检查点。为了腾出那 64MB，检查点必须频繁向前，每次向前都要求对应脏页先落盘。等于系统不停地做“日志快满了”那种刷盘，更新被一段段堵住，表现就是周期性的抖动。把 `innodb_io_capacity` 再调大也补不齐：限制来自日志空间，不是来自磁盘峰值。缓冲池有 64GB，里面可以积下远超 64MB 的脏页，可 redo 不允许这些脏页在内存里停留太久。WAL 把随机写变顺序写的好处，在日志太小时发不出来。

## 上一讲：一长串几乎相同的前缀怎么做索引

学号或校园卡号若前半段高度重复，正着或反着做前缀索引，区分度都差。一个学校内部，城市码加学校码是固定的，邮箱后缀也全是同一个域名。真正会变的是入学年份和序号。若这两段合起来是固定的 9 位数字，就不必把整串字符放进索引。

把这 9 位收成整数列，例如 `201100001` 这种形式，`int` 占 4 字节，也能保持唯一。这其实是一种最简单的哈希：按约定把字符串收成数字，并且业务保证收完仍然不冲突。索引变短，页里能放下的键变多。

另一种声音也成立：一个学校几十年累积下来，学生表可能只有几十万到一百万行，表并不大。若为了省这点空间把学号拆开，所有查询都要跟着改，优化成本可能高于收益。表小、语句简单时，直接存原始字符串更划算。先估数据量，再决定要不要做这种压缩。
