# 行锁什么时候释放，热点行如何把 CPU 打满

上一篇谈的是全局锁和表锁。这一篇只看行锁：它能提高并发，也会在事务写法不对、或者所有人都挤在同一行时，把吞吐打下来。

行锁由引擎各自实现，不是 Server 层统一发号。MyISAM 没有行锁，并发控制只能落到表锁，同一张表上同时只能有一个更新在跑，写多的业务很快顶满。InnoDB 支持行锁，这是它取代 MyISAM 的重要原因之一。

直观地说，事务 A 改了某一行，事务 B 要改同一行，就得等 A 结束。没那么直观的是这些锁何时放开。InnoDB 用的是两阶段锁，理解错了，事务里的语句顺序就会白排。

## 两阶段锁

设 `wallet_id` 是表 `wallet` 的主键。事务 A 连续做了两件更新，都还没提交：

```sql
begin;
update wallet set balance = balance - 30 where wallet_id = 11;
update wallet set balance = balance + 30 where wallet_id = 28;
```

此时事务 B 执行：

```sql
update wallet set balance = balance - 5 where wallet_id = 11;
```

B 会被堵住，直到 A 执行 `commit`（或回滚）才能继续。A 改完 `wallet_id = 11` 之后并没有把这行的锁还回去，第二句更新拿到的 `28` 那把锁也一样。两把行锁都活到事务结束。

这就是两阶段锁：事务执行期间只加锁，不因为“这句已经用完了”就提前解锁；全部锁在提交或回滚时一起释放。

对写事务的直接启发是：如果一个事务要锁多行，把最容易和别人撞车的那一行尽量往后放。锁虽然都要持有到提交，但越晚加上，这一行被占用的时间越短。

看一个轮渡售票的简化流程。旅客甲在码头乙买一张票，事务里要做三件事：

1. 从甲的余额扣掉票价；
2. 给码头乙的账户加上这笔票价；
3. 写一条售票流水。

三句必须在同一个事务里，否则扣款和入账会对不齐。同时旅客丙也在码头乙买票，两笔事务真正抢的是第 2 句：同一个码头账户那一行。

无论语句怎么排，行锁都要等到提交才释放。如果按「流水 → 扣旅客 → 加码头」来排，码头那一行的锁只覆盖事务尾巴上很短的一段。反过来若一上来就加码头账户，后面扣款、写流水的时间里，所有买这个码头票的事务都在排队。把热点行的更新贴着 `commit` 放，锁等待会短一截。

语句顺序只能缩短热点锁，不能消灭它。若这个码头搞一天低价预售，开卖瞬间数据库像是挂了：CPU 接近打满，每秒却完成不了一百个事务。原因通常不是码头那一行锁得太久，而是死锁检测本身被并发放大了。

## 死锁和检测

并发线程如果形成环状等待，每个都拿着别人需要的锁，谁也走不下去，这就是死锁。

事务 A 已经锁住 `wallet_id = 11`，接着要改 `28`。事务 B 已经锁住 `28`，接着要改 `11`。A 等 B 放 `28`，B 等 A 放 `11`，两条会话都不会自己结束。

出现环之后有两条策略：

- 一直等到超时。超时时间是 `innodb_lock_wait_timeout`，默认 50 秒。
- 主动检测。`innodb_deadlock_detect` 设为 `on`（这也是默认值）时，发现环就把环里的某一个事务回滚掉，让其余事务继续。

在线服务等不了 50 秒。把超时改成 1 秒也不行：真死锁确实能快点解开，但普通的锁等待也会被误伤，正常排队的事务被当成失败。所以通常保留检测，而不是把等待时间砍到很短。

检测要付出代价。一个事务被挡住时，引擎要顺着它等待的那条链看下去，确认有没有环。每个新来的等待者都做一次这样的检查，成本大约是当前等待者数量的线性函数。

若 1000 个事务同时更新同一行，每个后来者都要和前面那一长串等待关系比对，总工作量到百万次这个量级。检测结论往往是“没有死锁，只是都在等同一行”，但 CPU 已经花在图遍历上。监控上就是 CPU 很高，提交数却上不去。预售把码头账户打成热点行时，看到的就是这个现象。

## 热点行可以怎么拆

症结是等待图太大，不是业务算错了一行余额。

第一种办法是临时关掉死锁检测，前提是能确定这段业务不会形成环。风险不对称：正常情况下死锁被回滚后，业务重试即可，数据不会错。关掉检测之后，真碰上环就只能干等超时，在线请求成批失败。这是用正确性周边的可用性去换 CPU，只能短时间、在看住的场景里用。

第二种办法是把同一行上的并发数压下去。等待者只有十来个时，检测的图很小，CPU 不会被打满。放在客户端做限流往往不够：客户端一多，局部限制加总仍然很大。600 个应用实例各自放行 5 个线程，数据库侧仍可能看到 3000 个并发更新。限流要做在进入引擎之前，比如在数据库中间件上按主键排队，或者有能力改源码时在 Server 层排队。InnoDB 内部同时等待同一行的事务少了，检测就轻了。

第三种办法是把逻辑上的一行拆成多行，从设计上降低碰撞概率。码头账户不必只留一行，可以拆成 8 行分桶，账户总额等于 8 个桶之和。入账时随机挑一个桶加钱，两个事务撞上同一个桶的概率大约降到原来的八分之一，等待队列和检测成本一起下降。

这不是无条件的优化。出账、退票要把余额减回去。若随机挑到的桶已经是 0，代码必须改去别的桶扣，或者先做汇总再扣，否则会出现“总余额够、单个桶不够”的假失败。拆行之前要把减少的那条路径设计完。

## 小结

InnoDB 的行锁在用到时加上，在事务结束时才释放。事务里有多行更新时，把最热的那一行放在最后，缩短它被锁住的窗口。

调整顺序避免不了死锁。检测默认开着，热点行上等待者太多时，检测本身会占满 CPU。处理方向是减少同时碰同一行的事务数：确认无环再临时关检测、在进引擎前排队，或者把热点行拆成多行分桶。

## 删掉前几千行，三种写法怎么选

要清掉表 `event_log` 里最前面的 6000 行，有三种做法：

1. 一条语句：`delete from event_log limit 6000;`
2. 同一个连接里循环 20 次：`delete from event_log limit 300;`
3. 开 20 个连接一起跑：每个执行 `delete from event_log limit 300;`

选第 2 种。

第 1 种把 6000 行的删除放进一个事务。行锁（以及范围上的间隙锁）要持有到语句结束，撤销日志也一次堆很大。锁时间长，和其他写入更容易挤在一起，大事务回滚时也很慢。

第 3 种看起来并行，20 个删除却会在同一段主键范围上抢锁。`limit` 并不保证每个连接删到互不相交的行，间隙锁还会让它们互相等待，甚至形成死锁。并行度是加上去了，锁冲突也加上去了。

第 2 种每次只删 300 行，语句结束就把锁和 undo 放掉，再删下一批。批与批之间不并发抢同一范围，单次事务短，对线上其他语句的影响是一小段一小段的。总耗时可能比“理想中的并行”长，但数据库在这段时间里仍然能做别的事。

## 备库逻辑备份时主库来了 DDL

上一讲的问题是：备库用 `--single-transaction` 做逻辑备份，主库的 binlog 里同时传来一条 DDL，会怎样？

假设 DDL 针对表 `cargo_bin`。备份过程里和锁有关的几句可以抽成：

```sql
/* Q1 */ set session transaction isolation level repeatable read;
/* Q2 */ start transaction with consistent snapshot;
/* Q3 */ savepoint sp_bin;
/* 时刻 1 */
/* Q4 */ show create table cargo_bin;
/* 时刻 2 */
/* Q5 */ select * from cargo_bin;
/* 时刻 3 */
/* Q6 */ rollback to savepoint sp_bin;
/* 时刻 4 */
```

Q1 再设一次可重复读。Q2 用 `with consistent snapshot` 在语句结束时拿到一致性视图。Q3 的保存点是为了后面能退回到这里。Q4 拿表结构，Q5 导数据。Q6 滚回保存点，作用是放开 `cargo_bin` 上的 MDL 读锁。表假定很小，DDL 一旦开始执行就能很快结束。

按 DDL 到达的时刻：

1. 在 Q4 之前到达：备份不受影响，拿到的是 DDL 之后的表结构。
2. 在时刻 2 到达：表定义已经变了，Q5 报 `Table definition has changed, please retry transaction`，备份进程停掉。
3. 落在时刻 2 和时刻 3 之间：备份会话占着这张表的 MDL 读锁，主库传来的 DDL 在备库上被堵住，表现为主从延迟，一直到 Q6 把读锁放开。
4. 时刻 4 之后：MDL 读锁已经释放，备份不受影响，导出来的是 DDL 之前的表结构。
