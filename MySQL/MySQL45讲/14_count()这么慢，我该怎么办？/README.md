# 表行数为什么越查越慢

页面上经常要显示“一共多少条”。流水表变大之后，一条不带条件的计数会越来越慢。直觉是：引擎明明可以在旁边记一个总数，查询时读出来就行。InnoDB 没有这么做，是有原因的。这一讲先看计数在引擎里怎么实现，再看业务如果又要频繁写入、又要随时读到行数，计数该放在哪里。

## count(*) 在不同引擎里怎么做

同样是不带 `WHERE` 的 `count(*)`，引擎不同，做法就不同。

- MyISAM 把表的总行数存在磁盘上的元数据里，执行这种计数时直接返回，很快。
- InnoDB 做不到这一点。它要把行从引擎里读出来，逐行判断，再累加。

这里说的是没有过滤条件的计数。一旦加上 `WHERE`，MyISAM 也不能靠那个存好的总数交差，同样得去找满足条件的行。

前面已经比较过为什么业务表更倾向 InnoDB：事务、并发和崩溃恢复都更完整。表用了 InnoDB，行数上来之后，全表计数变慢就是这条实现带来的结果。

InnoDB 为什么不学 MyISAM，把一个整数存起来？因为同一时刻的多个查询，由于 MVCC，并不存在一个所有事务都认可的“表有多少行”。

假设 `move_log` 里现在有 18000 行，隔离级别是可重复读。三个会话按下面的顺序活动：

1. 会话 A 用一致性快照开启事务，立刻计数，得到 18000。
2. 会话 B 也用一致性快照开启事务。
3. 会话 C 自动提交，插入一行。
4. 会话 B 再插入一行，先不提交，并在自己的事务里计数，得到 18001。它看得见自己的插入，看不见这套快照建立之后才提交的 C。
5. B 提交之后，C 再发一条新的自动提交计数，得到 18002。与此同时 A 再计数，视图没变，仍然是 18000。

三个会话对“这张表有多少行”给出了不同答案，而且每个答案对自己的视图都是对的。A 的 18000 没有漏算，它的快照里后面两行还不存在。B 的 18001 把自己未提交的插入算进去，这符合“自己的修改自己可见”。C 在两条插入都提交之后重新计数，得到 18002，也符合读到最新已提交状态。InnoDB 若只在元数据里放一个整数，就无法同时满足这些视图：返回 18000 会让 C 少见两行，返回 18002 会让 A 看见本不该看见的提交。它只能把行读出来，按当前查询的可见性过滤，可见的才计入这一次的总数。行越多，这次过滤要碰的页越多，所以计数会随表变大而变慢。

计数本身仍有优化。InnoDB 是索引组织表，主键叶子上是整行，二级索引叶子上主要是索引列加主键。二级索引通常小得多。不带条件的 `count(*)` 无论扫哪棵树，逻辑上都是在数可见行，因为每一行都会出现在每条索引里。优化器会挑最小的那棵，常常是某条很短的二级索引，而不是把整行都搬上来的主键。在结果正确的前提下少读数据，是存储引擎里很普遍的取舍。这也说明：给一张大流水表留一条窄索引，有时不是为了业务查询，只是为了让这种全表计数少扫一些页。当然，索引本身要付出写入维护，是否值得要看计数有多频繁。

`SHOW TABLE STATUS` 的输出里有 `TABLE_ROWS`，命令本身很快。这个数不能代替精确计数。它来自索引采样，官方文档给出的误差可以到四成甚至五成。展示一个大约数可以，拿它做账不行。

收束一下：

- MyISAM 的无条件计数快，但没有事务。
- `SHOW TABLE STATUS` 快，但不准。
- InnoDB 直接计数结果可信，表大了就会慢。

页面若要频繁显示流水总数，就得自己保存这个数。思路是找一个位置，记下 `move_log` 的行数，插入加一，删除减一。

## 用缓存保存计数

写入很密时，第一反应往往是放进 Redis。插入一行就把键加 1，删除一行就减 1。读和改都很快。问题是缓存会丢更新，而且即使不丢，也可能和表里的行对不上。

Redis 的值不能只活在内存里，通常会定期落到别处。即便如此，仍可能丢失最后一次增量：表里刚插入一行，计数也加了 1，Redis 随即重启，从持久化副本读回来的却是加 1 之前的数字。

恢复办法是有的。重启之后对表做一次真实的 `count(*)`，再写回 Redis。崩溃不是常态，这一次全表扫描可以接受。

更麻烦的是 Redis 正常工作时，计数和明细仍然可能逻辑不一致。页面既要显示总数，又要显示最近 80 条流水。实现上会先读计数，再读表，或者顺序相反。把“对不齐”定义成两种：

1. 最近 80 条里已经有新行 R，计数却还没加上。
2. 最近 80 条里还没有 R，计数却已经加上了。

会话 A 负责写入：先向 `move_log` 插入 R，再给 Redis 加 1。会话 B 在这两步之间来读页面，就会看见 R，同时看见旧的总数。

把 A 的顺序倒过来，先加计数再插行，也堵不住。B 可以卡在两步中间，看见总数已经增加，明细里却没有 R。并发下没法规定两个线程的语句严格落在某个缝隙之外。只要存在这样的交错，缓存里的总数和表里的行就不是同一份视图。根子是这两套存储之间没有一个共同的事务。

## 把计数放回数据库

缓存方案既可能丢增量，又可能和明细对不齐。改成在同一个库里放一张计数表 `move_tally`，例如一行记录 `total_rows`。

崩溃丢失首先被解决。计数的修改和流水的插入写进同一套 redo，提交之后重启还能恢复。

对不齐也可以收掉。有人会觉得，这不过是把前面的 Redis 操作换成对 `move_tally` 的更新，交错依然存在。差别在于现在可以用事务把两步包起来。

会话 A 的事务里既插入 `move_log`，也给 `move_tally` 加 1，直到提交才对外可见。会话 B 若在 A 提交前读取，按可重复读或读已提交，都看不见未提交的插入，也看不见未提交的加 1。明细和总数要么一起出现，要么都还是旧的。事务提供的就是这一份共同视图。

## 几种 count 写法的差别

评论里常问 `count(*)`、`count(主键)`、`count(某列)` 和 `count(1)` 谁更快。下面仍以 InnoDB 为准。

`count()` 是聚合函数。对结果集里的每一行，参数不是 NULL 就加 1，是 NULL 就跳过，最后返回累加值。

因此 `count(*)`、`count(主键)` 和 `count(1)` 都是在数行。`count(某列)` 数的是这列不为 NULL 的行，语义不同，不能互相替换。

比较开销时抓住三条：

1. 服务器层要什么，引擎就准备什么。
2. InnoDB 尽量不多给列。
3. 优化器把 `count(*)` 特殊处理成“数行”。其他看起来等价的写法，并没有全部做成同样的短路。

`count(主键)`：引擎扫行，取出每行主键交给服务器。主键不可能是 NULL，服务器按行累加。取出主键要解析行并拷贝字段。

`count(1)`：引擎仍然遍历，但不必把某个列的值交上去。服务器对每一行放进常数 1，再累加。少了解析和拷贝，所以通常快于 `count(主键)`。

`count(某列)`：列若声明为 `NOT NULL`，引擎仍要把该列读出来，服务器确认非空后累加。列若允许 NULL，还得取出值再判断，是 NULL 就不计。这符合第一条，服务器点了哪一列，引擎就返回哪一列。

`count(*)` 是例外。它不去取全部列，也不取主键，专门按“这一行可见则加 1”来做。`count(*)` 的参数位置并不是一个可能为 NULL 的表达式。

有人会问，主键显然非空，优化器为什么不把 `count(主键)` 也改写成和 `count(*)` 一样？不是不能做，而是这类“看起来显然”的改写很多，引擎已经为 `count(*)` 准备了路径。应用直接写 `count(*)` 就能用上。

按通常的开销排序：`count(某列)` 慢于 `count(主键)`，`count(主键)` 慢于 `count(1)`，`count(1)` 和 `count(*)` 接近。需要行数时优先写 `count(*)`。

## 小结

无条件计数在 MyISAM 和 InnoDB 里不是同一条路径。InnoDB 因为要尊重每个事务自己的可见性，不能把一个全局行数直接返回。把总数放进 Redis，快，但两套存储没有共同事务，明细和总数会对不齐，重启还可能丢增量。把总数放进同一实例的计数表，和插入放在一个事务里，就能共用一份视图。这也是业务愿意把这类“要强一致的派生数据”留在 InnoDB 里的原因。

思考题：事务已经能保证别人读不到中间状态，因此先插流水还是先改计数表，都不影响最终能看见的结果。若从锁竞争考虑，这个事务里应该先写哪一张表？

## 上期问题时间

上一讲问：什么情况下 `ALTER TABLE ... ENGINE=InnoDB` 重建之后，表占用的空间反而变大。

一种情况是表里本来就没有可回收的空洞，例如刚刚重建过。重建期间如果还有业务在写入，新产生的删除或更新又会留下空洞，重建的收益被抵掉一部分。

还有一个更底层的原因。重建时 InnoDB 不会把每一页塞满，大约留出 1/16 给后续更新，避免刚整理完就因为修改而拆页。所以重建之后并不是理论上最紧的装法。

可以连成这样三步：

1. 先把表重建一次，页里带着预留空间。
2. 随后的插入把一部分预留用掉，页变得更满。
3. 再重建一次。新页又按同样的比例预留，原先被填满的那些空间重新散开，文件就可能比第二次重建之前更大。
