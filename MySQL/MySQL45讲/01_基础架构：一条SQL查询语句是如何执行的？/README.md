# 一条查询在 MySQL 里要走过哪些模块

刚接触库的时候，很容易把 MySQL 当成一个黑盒：语句丢进去，结果吐出来。比如货架表 `bin_stock` 只有库存编号这一列当主键，执行：

```sql
select item_name, qty
from bin_stock
where sku_no = 42;
```

屏幕上只有输入和返回值。真正拖慢排查的，是中间那一段看不见的路径。出了慢查询、权限突然失效、或者语法报错位置对不上，如果只盯着业务 SQL，很容易在表层打转。

把这次查询拆开，目的不是背组件名单，而是以后看到异常时能对上号：它停在握手、停在解析，还是停在引擎取数。

## 先分成两层

一次查询会穿过两层。

上面是 Server 层。连接接入、语句缓存（老版本才有）、解析、选计划、真正调度执行，都在这里。日期、数学、加密这类内置函数也在这里。跟具体存取格式无关的能力，例如存储过程、触发器、视图，同样放在这一层，所以换引擎也不会把它们换掉。

下面是存储引擎层，负责把行存下去、再按接口取出来。这一层是插拔式的，InnoDB、MyISAM、Memory 可以共存。从 5.5.5 起，不写引擎子句时默认就是 InnoDB。想改用别的，要在建表时写明，例如 `engine=memory`，数据就放在内存表里，重启即失，也不提供 InnoDB 那套事务。

不同引擎的页格式、锁、崩溃恢复都不一样，但它们共用同一套 Server 层。所以下面用 `sku_no = 42` 这条查询，把 Server 层从左走到右。

## 连接器

客户端先得接上服务器。命令行大致是：

```bash
mysql -h 10.2.8.15 -P 3306 -u clerk_ro -p
```

`-p` 后面不要直接粘密码。密码会出现在进程列表和 shell 历史里，生产机上等于把口令贴在公告栏。

这里的 `mysql` 只是客户端。TCP 三次握手完成后，连接器才用你给的账号和口令做认证。

- 账号或口令不对，客户端收到 `Access denied for user`，进程直接退出。
- 认证通过后，连接器去权限表把该账号的库、表、列权限读出来，挂在这条连接上。此后这条连接上的每一次权限判断，用的都是当时那份快照。

因此，管理员中途 `REVOKE`，已经连着的会话不会立刻变瘦。旧会话继续按连上那一刻的授权干活，只有新握手的连接才会看到新权限。排查“我明明收了权限他还能查”时，先看他是不是一条老连接。

连上之后如果闲着，`show processlist` 里 `Command` 会显示 `Sleep`。空闲太久，连接器会主动拆掉。时长由 `wait_timeout` 决定，默认 28800 秒，也就是 8 小时。拆掉之后客户端再发语句，会收到 `Lost connection to MySQL server during query`。应用得重连，再把语句送一遍。

长连接指握手成功后，后续请求都复用同一条连接。短连接则是做完一两句就断开，下次再握手。握手要做 TCP、认证、读权限，成本不低，所以业务侧应尽量复用连接。

长连接也有副作用。执行过程中临时排序、临时表、join buffer 等内存挂在连接对象上，多数要等连接销毁才归还。连接池里的连接几天不换，内存会慢慢爬高，严重时被操作系统 OOM killer 杀掉，现象是 MySQL 自己重启了。

两条常见处理办法：

1. 用过一段时间，或者刚跑完一条很吃内存的大查询之后，主动断开，下次再连。
2. 5.7 及以后可以在大查询之后调用 `mysql_reset_connection`。它不重新握手，也不再读一遍权限表，但会把会话级状态和临时内存清回到刚连上的样子。

## 查询缓存

连接可用之后，语句进入第二站。8.0 之前，Server 会先看查询缓存：这句原文是不是曾经执行过。

缓存按键值存放。键是语句文本本身（包括空格、大小写差异），值是当时的结果集。键对上了，就把值直接交回客户端，后面的解析、优化、引擎访问都可以跳过，命中时非常快。

没命中就继续往下走。整句做完，再把语句和结果写进缓存。

多数业务不该开这块缓存。失效太勤：只要某张表有一次更新，这张表上所有缓存条目一起作废。刚放进去的结果，往往还没被第二个人用到，就被一次写清掉。写入频繁的库，命中率会差到不值得维护那份哈希。比较适合的是几乎不改的静态表，比如一年才发布一次的税率对照表。

老版本允许按语句决定用不用。把 `query_cache_type` 设成 `DEMAND` 后，普通语句不进缓存；确定要缓存的那句，显式加上提示：

```sql
select sql_cache tax_rate
from tax_rule
where region_code = 'CN-31';
```

8.0 把整块查询缓存删了。从这一版起，语句不再有这条捷径，执行计划从解析开始才是常态。

## 分析器

缓存没命中（或者根本没有缓存），就要弄清这句想干什么。

先做词法分析。输入是一串被空格切开的文本，分析器要认出哪些是关键字，哪些是表，哪些是列，哪些是字面量。看到 `select` 就知道这是查询；`bin_stock` 被当成表名；`sku_no` 被当成列名；`42` 是整数常量。

再做语法分析。词法结果按语法规则组装，判断这棵句子是否合法。少写一个字母就会在这里失败：

```sql
elect item_name from bin_stock where sku_no = 7;
```

服务器返回 `ERROR 1064 (42000)`，提示 `You have an error in your SQL syntax`，并在 `near` 后面给出它认为出错的起点。一般要盯紧 `near` 后面那一小段，而不是整句重读。

词法和语法都过了，还有一层名字解析：表在不在、列属不属于这张表。这一步仍然算分析阶段的事，优化器还没开始比计划。

## 优化器

分析器回答“要做什么”，优化器回答“哪条路更便宜”。

表上有多个索引时，它决定走哪一个。多表连接时，它决定谁当驱动表。例如：

```sql
select p.pallet_no, s.hub_name
from pallet p
join shipment s on p.ship_id = s.ship_id
where p.zone_no = 6
  and s.hub_code = 18;
```

至少有两种合法走法：

- 先在 `pallet` 里找出 `zone_no = 6` 的 `ship_id`，再拿这些值去 `shipment` 里对 `hub_code`。
- 先在 `shipment` 里找出 `hub_code = 18` 的行，再回 `pallet` 核对 `zone_no`。

两种走法结果相同，代价往往差一个数量级。行数、索引选择性、缓冲池里有没有页，都会影响选择。优化器估完成本，执行计划就定了，然后才交给执行器。它有时也会选错，那是统计信息或成本模型的问题，后面专门谈索引时再拆。

## 执行器

计划定了之后，执行器先确认当前账号能不能对目标表做这件事。没有 `SELECT` 权限时直接拒绝：

```sql
select item_name from bin_stock where sku_no = 42;
-- ERROR 1142 (42000): SELECT command denied to user 'picker'@'10.0.0.8' for table 'bin_stock'
```

有两点和“执行到一半才查权限”不完全一样。命中查询缓存时，返回缓存结果之前也会做权限校验。另外，优化器动手之前还有一次 `precheck`。可以把它理解成：真正碰数据之前，权限必须先过关。

权限通过后，执行器按表定义找到引擎，调用引擎暴露的行接口。

假如 `sku_no` 上没有索引，流程是全表挨行看：

1. 调引擎取第一行，判断 `sku_no` 是不是 42。不是就丢掉，是就把这一行放进结果。
2. 调“下一行”接口，重复判断，直到引擎说没有更多行。
3. 执行器把收集到的行返回客户端。

如果 `sku_no` 上有索引，接口换成“第一条满足条件的行”和“下一条满足条件的行”。比较和过滤的位置下沉到引擎内部，Server 层拿到的已经是候选行。

慢查询日志里的 `Rows_examined` 在执行器每次向引擎要行时累加。有的调用里，引擎为了找这一行，自己在页里或索引里多看了好几行，所以引擎内部扫描行数和 `Rows_examined` 不一定相等。看到日志里行数不大，不代表磁盘上没有多翻页。

## 小结

一条查询的主路径是：连接器（认证并冻结权限）→ 查询缓存（仅 8.0 之前，且通常不值得开）→ 分析器（词法、语法、列名是否存在）→ 优化器（索引与连接顺序）→ 执行器（再核权限，按引擎接口取行）。

引擎决定数据怎么放，Server 层决定语句怎么被理解和调度。两边的交界，就是执行器对引擎那些“第一行 / 下一行”接口的调用。

## 留下的问题

`bin_stock` 里并没有 `aisle_no` 这一列，却执行了：

```sql
select item_name from bin_stock where aisle_no = 3;
```

一定报 `Unknown column 'aisle_no' in 'where clause'`。这个错误出在上面哪一站？

答案落在分析器。`aisle_no` 作为标识符，词法和语法都说得通，但名字解析时发现表结构里没有这一列，语句在进入优化器之前就被退回。优化器还没机会选索引，执行器也还没向引擎要行。
