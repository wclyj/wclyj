查询语句的路径前面已经拆过：连接器、分析器、优化器、执行器，最后进入存储引擎。更新语句并不是另起一条完全不同的流水线，它会先把这几站再走一遍，然后再多写两份日志。

很多运维同学会说，库可以回到过去十几天里的任意一秒。这句话能成立，靠的就是下面要讲的日志，而不是数据页本身有时间机器。

用一张入库单说明。表里只有库位编号和件数：

```sql
CREATE TABLE parcel_bin (
  bin_id INT PRIMARY KEY,
  piece_cnt INT NOT NULL
) ENGINE=InnoDB;
```

把 17 号库位的件数加上 4：

```sql
UPDATE parcel_bin
SET piece_cnt = piece_cnt + 4
WHERE bin_id = 17;
```

执行前仍然要先通过连接器拿到会话。老版本里如果开着查询缓存，对 `parcel_bin` 的更新会把这张表上已经缓存的结果全部作废。整表失效来得太勤，缓存命中往往补不回维护成本，所以当年并不建议开启。8.0 起这条缓存已经从服务器里拿掉了，但“一次写入让整表缓存作废”仍然解释得通它为什么难用好。

分析器通过词法和语法确认这是更新。优化器看到 `bin_id` 是主键，选定这条索引。执行器再让引擎定位到那一行并改写。查询会走的那些模块，更新一样要经过，否则服务器无法知道这是一句合法的改写、该用哪条索引、改的是哪一行。和只读语句不同的是，改写落定之前还要经过两份日志：引擎内部的 redo log，以及服务器层的 binlog。这两份设计也可以借到业务系统里，用来做崩溃恢复和变更回放。

# 重做日志：先记变更，再落数据页

可以把它想成冷库月台。白天货车一辆接一辆，办事员如果每收一箱就跑回办公室改订装本，光翻页和找行就要耽误整条队伍。实际做法是月台一块白板先记下“哪个库位、加减多少”，等空闲再把白板过到订装本上。白板写满了，就先腾出一段：把那一段抄进订装本，再擦掉，好继续收货。

InnoDB 用的是同一类想法，也就是 WAL：先写日志，再写数据页。某行要改时，引擎把这次修改记进 redo log，同时改掉缓冲池里的页，更新对客户端就可以返回。真正把脏页刷回磁盘，往往留到后面相对空闲的时候。

redo 的空间是事先定好的，循环使用。假如配成 3 个文件、每个 512MB，这块“白板”一共大约 1.5GB。`write pos` 是下一次写入的位置，写到末尾就绕回第一个文件。`checkpoint` 是可以擦除的位置，擦之前必须保证对应的数据页已经落盘。两根指针之间的空隙才能接新的更新。一旦 `write pos` 追上 `checkpoint`，白板满了，新的更新只能停下来，先推进检查点。

只要修改已经进了 redo，或者已经进了数据页，进程突然退出也不会把已提交的结果弄丢。这种“崩溃之后还能把已提交修改找回来”的能力，就叫 crash-safe。白板和订装本至少有一处留着这笔账，复工时就能对上。反过来，如果只改了内存里的数据页、日志却没留下，断电之后缓冲池清空，这笔修改就找不回来。所以“先返回成功”的前提不是页已经在磁盘上，而是描述这次修改的日志已经按提交策略落稳。

循环写也会带来一个运行时限制。检查点推进得慢，而写入又很密，`write pos` 会逐渐贴近 `checkpoint`。空隙耗尽时，InnoDB 只能暂停新的更新，先把一部分脏页刷出去，再把检查点往前挪。这不是某条语句写错了，而是日志环的容量和刷盘速度没跟上提交速率。容量可以用文件个数和单文件大小调整，但再大也是环，不能当成无限追加的归档。

# 归档日志：服务器层的 binlog

服务器层负责连接、解析和优化，引擎层负责存取。redo 是 InnoDB 自己的日志。服务器层另有一份 binlog，所有引擎都能用。

两份日志并存，是历史叠出来的。早期默认引擎是 MyISAM，它没有崩溃恢复能力，binlog 的用途是归档和复制。InnoDB 后来以插件形式加进来，不能只靠 binlog 保证已提交的页能恢复，于是自带了 redo。

两边的差别可以记成三条：

1. redo 只属于 InnoDB；binlog 由服务器层写出，换引擎也有。
2. redo 记的是某个数据页上的物理修改；binlog 记的是语句或行变更的逻辑，例如“把 `bin_id = 17` 的 `piece_cnt` 加上 4”。
3. redo 在固定文件里循环覆盖；binlog 追加写，单个文件到了上限就切到下一个，旧文件保留，直到备份策略把它清掉。

对应到这条把件数从 28 改成 32 的更新，redo 里更接近“某个数据页的某一处被改成新内容”，恢复时按页重放即可，不必再理解业务上的加 4。binlog 里则留着这次变更的逻辑：哪一行、哪一列、从什么变成什么，或者语句本身。拿去另一台机器重放时，不依赖原库那个数据页的物理位置。两份日志一个负责把本机页修回提交后的样子，一个负责把“发生过哪些变更”带到备份和备库。

有了这两份日志，再看这条更新在执行器和引擎之间怎么交接。假设改之前件数是 28，改完应是 32。

1. 执行器向引擎要 `bin_id = 17` 这一行。主键沿 B+ 树定位。数据页已在缓冲池里就直接返回，否则先从磁盘读进内存。
2. 执行器在拿到的行上加 4，得到 32，再调用引擎的写入接口。
3. 引擎把新行放进内存页，并把这次修改写进 redo，此时 redo 处于 prepare。然后告诉执行器：引擎这边可以提交了。
4. 执行器生成 binlog 并把它刷到磁盘。
5. 执行器调用引擎的提交接口，redo 从 prepare 改成 commit。更新完成。

最后三步把 redo 拆成准备和提交，这就是两阶段提交。它看起来绕，是为了让两份日志对“这笔事务到底算不算数”给出同一个答案。

# 两阶段提交

目标可以回到开头那句：怎样把库恢复到过去某一秒。

binlog 按追加方式记下逻辑变更。如果承诺能回到 12 天内的任意时刻，备份系统里就得留着这 12 天的 binlog，并且定期做全量备份。周期按业务要紧程度选，可以每个自然日一次，也可以每周一次。

假如周四 16:10 发现有人在 16:02 误删了一张表，恢复步骤是：

- 找到最近的一份全量，比如周三凌晨那份，先恢复到一个临时实例；
- 从这份全量对应的位点开始，按顺序重放 binlog，停在误删之前。

临时实例上的表就和误删前一致，再按需要把数据导回线上。全量解决的是“从零搭出某一夜的库”，binlog 解决的是“从那一夜补到出事之前的那一秒”。少了全量，只有日志的话重放太长；少了日志，全量只能回到备份那一刻，16:02 之前的合法写入会一起丢掉。周期越长，最坏情况下要补的日志越多，恢复窗口越不可控。这个取舍留到下一讲再收成一个指标。

为什么中途不能只按一种顺序写完两份日志？用反证。仍然是上面那条更新，旧值 28，新值 32。假设第一份日志刚写完、第二份还没写完时进程崩溃。

1. 先写完 redo、binlog 还没写完。重启后 redo 能把这一行恢复成 32。binlog 里却没有这次加 4。之后用 binlog 去搭临时库或备库，那一行会停在 28，和原库不一致。
2. 先写完 binlog、redo 还没写完。崩溃恢复时这笔事务无效，原库仍是 28。binlog 里却已经有“28 改成 32”。重放之后临时库变成 32，又和原库不一致。

所以两阶段提交不是多写一次状态，而是让 redo 和 binlog 对提交与否保持一致。恢复时如果 redo 停在 prepare，就去看 binlog：binlog 里已经有这笔事务，就把 redo 提交；binlog 里没有，就回滚。

这也不只是误删之后才用得上。扩读容量、补一台备库，常见做法同样是全量加上 binlog 重放。两份日志若对不齐，主备会在这一行上分叉。

# 小结

这一讲的重点是两份日志：redo 保证崩溃之后已提交的修改还在，binlog 负责归档、按时间点回放和主备同步。

`innodb_flush_log_at_trx_commit` 设为 1 时，每次事务提交都把 redo 刷到磁盘。建议保持 1，避免进程异常退出后丢掉最后那批已提交事务。

`sync_binlog` 设为 1 时，每次提交都把 binlog 刷盘。同样建议保持 1，避免恢复或复制时缺事件。

两阶段提交是跨两套日志维持同一提交结论的办法。不做内核，业务里同时写数据库和消息、或者同时写两套存储时，也会碰到同类问题。

留下一个判断题：全量备份从“每七天一次”改成“每个自然日一次”，恢复能力上主要改善的是哪一项指标？换来这项改善要多付什么成本？
