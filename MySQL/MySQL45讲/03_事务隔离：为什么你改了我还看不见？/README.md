转账是事务最常被拿来讲的场景，这里把数字换掉。账户里只剩 350 元，要转给同事周宁 350 元。程序里会先读余额，再做加减，再把两行余额写回去。这些步骤必须绑在一起。否则读完还没扣款的空隙里，同一笔 350 元可以再被另一笔转账读走，账就平不了。

事务要的就是：这一组读写要么全部留下，要么全部撤销。在 MySQL 里，事务是引擎提供的能力，不是每一种引擎都有。MyISAM 没有事务，这也是它后来让位给 InnoDB 的重要原因。下面都以 InnoDB 为准。

# 隔离性与隔离级别

ACID 里这一讲只看 I，也就是隔离。多个事务同时跑，会碰到脏读、不可重复读和幻读。隔离级别就是在“挡住这些现象”和“还能并发”之间选一个位置。挡得越严，并发通常越差。

标准里的四档可以分成：

- 读未提交：别的事务还没提交的修改，当前事务也能看见。对方如果随后回滚，当前事务已经读到的值就从未真正落库，这就是脏读。
- 读已提交：对方提交之后，修改才对自己可见。同一事务里两条相同的查询，可能因为中间有别人提交而得到不同结果，这就是不可重复读。
- 可重复读：事务执行期间，反复读取应和它启动时看到的一致；别人未提交的修改同样不可见。它挡住的是“同一行被别人改掉之后，我再读却变了”。
- 串行化：对同一行，写加写锁，读加读锁。锁冲突时，后来的事务等到先来的事务结束才能继续。并发被收成排队，脏读和不可重复读都靠等待避免，而不是靠事后忽略某个版本。

中间两档最容易混，用一张只有一个整数列的表看返回值。列上起初是 40。

```sql
CREATE TABLE balance_snap (
  amount INT
) ENGINE=InnoDB;

INSERT INTO balance_snap (amount) VALUES (40);
```

按时间顺序：事务 A 先读一次，记为 V1；事务 B 把 40 改成 75 但先不提交；A 再读一次，记为 V2；B 提交；A 再读一次，记为 V3。

- 读未提交：V1 已经是 75，因为 B 还没提交也被 A 看见了。V2 和 V3 同样是 75。
- 读已提交：V1 仍是 40。B 提交后 V2 变成 75，V3 也是 75。
- 可重复读：V1 和 V2 都是 40，事务中途看到的结果必须稳住。V3 要等 A 自己这轮事务结束后重新开始，才能读到 75。若 V3 仍算在 A 的同一事务里，它也应保持 40。这里把 V3 定义成 A 提交之后的下一次读取，所以是 75。
- 串行化：B 在改 40 的时候会被 A 已经持有的读锁挡住，等到 A 提交才能继续。因此从 A 看，结束前的读取都是 40，结束后的新事务才是 75。

实现上，读已提交和可重复读会建一个读视图，查询以视图里的结果为准。可重复读的视图在事务启动时建立，整个事务复用。读已提交则在每条语句开始时重建。读未提交不做视图，直接拿记录上的最新值。串行化靠加锁，不靠视图躲并发。

Oracle 默认是读已提交。从 Oracle 迁到 MySQL 时，如果希望行为和原来一致，要把 MySQL 的隔离级别也调成读已提交。启动参数 `transaction-isolation` 取 `READ-COMMITTED`。当前会话可以用：

```sql
SHOW VARIABLES LIKE 'transaction_isolation';
```

没有哪一档在所有业务里都更“正确”。读已提交的并发通常更好，适合大多数“读到最新已提交值就行”的接口。可重复读则适合一次事务里要反复读、并且前后必须对得上的计算。

库存对账就是后一种。一张表存每月结存，另一张表存本月每一笔出入库。核对时要确认：上月结存和当前结存的差，是否等于本月流水之和。核对过程中如果又进来一笔出库，不希望它只进了流水、还没反映到结存，或者正好相反。事务一开始就固定的视图，能把这次核对和后面的新流水隔开。若用读已提交，先读结存、后读流水，中间插入的那一笔会只出现在后一条语句里，差额就会对不上，而这个“对不上”并不是数据写坏了。

# 事务隔离的实现

可重复读依赖行上的历史版本。每次更新除了写下新值，还会留下一份能把新值撤销回旧值的记录。当前值沿着这些撤销记录往回走，就能得到更早的状态。

假设某个库存从 40 依次被改成 75、90、120。当前行是 120，撤销链上还能推出 90、75 和 40。不同时刻启动的事务带着不同的 read-view：有的事务看见 40，有的看见 75，有的看见已经提交的 120。同一行同时存在多个版本，这就是 MVCC。正在把 120 改成 150 的那个事务，不会和这些旧视图冲突，因为旧视图根本不会去读它尚未提交的新版本。

撤销记录不能无限留着。没有任何读视图还需要某个旧版本时，它就可以被清掉。反过来说，只要系统里还有更老的 read-view，这段撤销记录就得保留。

这也是长事务麻烦的地方。它把一份很老的视图一直握在手里，引擎不敢丢掉它可能读到的历史版本，撤销空间会持续膨胀。历史版本不只占空间，查询若要回到那个旧视图，还得沿着撤销记录多走几步，读延迟也会上去。5.5 及更早的版本里，回滚段和数据字典放在系统表空间 `ibdata` 中，长事务提交、回滚段逻辑上清掉之后，文件也不会缩回去。见过数据本身只有大约 8GB、回滚段却涨到 90GB 的实例，最后只能重建整库才能把空间收回来。较新的版本可以把撤销段单独放到 undo 表空间，空间回收比当年灵活，但“老视图不结束，旧版本就不能丢”这条约束仍然在。长事务还会占着锁，严重时把后续业务堵住。锁的部分后面再展开。

# 事务的启动方式

长事务常常不是有意开的。常见启动方式有两种：

1. 显式写 `BEGIN` 或 `START TRANSACTION`，结束时用 `COMMIT` 或 `ROLLBACK`。
2. `SET autocommit = 0`。这个会话里自动提交被关掉，哪怕只做一条查询，事务也已经开始，而且不会自己结束，直到提交、回滚或者断开连接。

有的连接池在建连之后会默认执行 `SET autocommit = 0`。再叠加长连接，后面的查询就全都挂在同一个事务上，长事务是被框架“送”出来的。

更稳妥的习惯是保持 `autocommit = 1`，需要多语句时再显式开始。有人担心每笔事务多一次 `BEGIN` 的往返。可以在提交时用 `COMMIT AND CHAIN`：当前事务提交，并立刻开启下一个，省掉单独再发一次开始语句，同时从代码上仍能看出语句处于事务之中。

超过一定时长的事务可以到 `information_schema.innodb_trx` 里找。下面这条找出已经持续超过 45 秒的事务：

```sql
SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 45;
```

# 小结

隔离级别决定一个事务能看见什么。可重复读用事务级读视图加行的历史版本实现；读已提交则每条语句换一次视图。长事务会拖住撤销记录和锁。业务侧应避免连接默认关掉自动提交，需要事务时显式开始，并用 `innodb_trx` 把超时事务找出来。

# 上期问题时间

上一讲问的是：全量备份每天做，和每周做，差别落在哪里。

差别主要在最坏情况下要重放的 binlog 有多长，也就是恢复要花的时间。假如每天 0 点做全量，要恢复到昨晚 23 点，最多应用大约一天的日志。改成每周一次，最坏就要重放七天。这项指标就是 RTO。

更密的全量会多占备份存储，也会给源库增加拷贝压力。RTO 是用这些成本换的，按业务能承受的停机窗口来定，而不是越密越好。
