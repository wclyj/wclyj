一张表上可以有多条索引，语句里却常常不写死用哪一条。选索引是优化器的事。多数时候它选得对，偶尔一条本该走索引的查询会变成大范围扫描，耗时明显变长。

用下面这张测量表做实验。主键是 `id`，另外两列各有一条二级索引：

```sql
CREATE TABLE gauge_log (
  id INT NOT NULL,
  zone_code INT DEFAULT NULL,
  batch_code INT DEFAULT NULL,
  PRIMARY KEY (id),
  KEY idx_zone (zone_code),
  KEY idx_batch (batch_code)
) ENGINE=InnoDB;
```

插入 8 万行，三列取同一个整数，从 (1,1,1) 直到 (80000,80000,80000)。用存储过程灌数据：

```sql
DELIMITER $$
CREATE PROCEDURE fill_gauge()
BEGIN
  DECLARE n INT DEFAULT 1;
  WHILE n <= 80000 DO
    INSERT INTO gauge_log (id, zone_code, batch_code) VALUES (n, n, n);
    SET n = n + 1;
  END WHILE;
END$$
DELIMITER ;

CALL fill_gauge();
```

先看这条查询：

```sql
SELECT * FROM gauge_log WHERE zone_code BETWEEN 6000 AND 14000;
```

`zone_code` 上有索引，范围大约 8001 行，正常应走 `idx_zone`。刚灌完数据时，`EXPLAIN` 里的 `key` 也确实是 `idx_zone`，预估行数接近 8001。

接着做一组会把统计信息弄歪的操作。会话 A 开启事务，并对 `gauge_log` 做一次一致性读，事务先不提交。会话 B 把表清空，再调用 `fill_gauge()` 重新插入 8 万行。然后在会话 B 里执行原来的范围查询。这时优化器往往不再选 `idx_zone`。

为了对照，把慢查询阈值调成 0，让这个会话接下来的语句都进慢日志，并强制走一次区号索引：

```sql
SET long_query_time = 0;

SELECT * FROM gauge_log WHERE zone_code BETWEEN 6000 AND 14000;

SELECT * FROM gauge_log FORCE INDEX (idx_zone)
WHERE zone_code BETWEEN 6000 AND 14000;
```

慢日志里可以看到差别：不加提示的那条扫描了大约 8 万行，耗时可以到三十多毫秒，说明走了聚簇索引的全表扫描；强制使用 `idx_zone` 的那条只扫描大约 8001 行，耗时大约一半。优化器选错了索引。

这种“删掉历史再整批写入”的操作在归档任务里很常见。选错并不是范围条件写错了，而是优化器用来估算的信息在这次删除和重插之后偏了。

## 优化器的逻辑

优化器的目标是挑一个它认为代价最低的计划。扫描行数是代价里很重要的一项：扫得越少，读页越少，CPU 也越少。它还会把临时表、排序算进去。上面这条语句既不排序也不建临时表，选错就出在行数估算上。

语句真正执行前，优化器并不知道范围内到底有多少行，只能靠索引统计做估计。统计里的关键是区分度：不同取值越多，索引越有选择性。不同取值的个数叫基数。基数越大，优化器越愿意用它过滤。

`SHOW INDEX FROM gauge_log` 能看到每条索引的基数，对应输出里的 `Cardinality`。这张表三列的值一一对应，按理每条索引的基数都应接近 8 万，但采样结果常常对不齐，三条索引彼此也会有差别。基数只描述“这一列大概有多少不同取值”，还不是某一条语句要扫的行数。优化器下一步才用它去估：`BETWEEN 6000 AND 14000` 这样一段，在区号这一列上大概占全部不同值的多少。基数偏了，这段比例就会偏。

基数用采样，而不是把整棵索引树逐行数一遍。逐行精确，但代价太高。InnoDB 抽出 N 个数据页，数这些页上的不同值，算出一页的平均数，再乘以索引的页数。表还在持续写入，所以变更行数超过约 1/M 时会自动再统计一次。

统计信息放在哪里，由 `innodb_stats_persistent` 决定：

- 设为 on，统计会持久化。默认 N 是 20，M 是 10。
- 设为 off，统计只留在内存里。默认 N 是 8，M 是 16。

无论抽 20 页还是 8 页，基数都可能偏。不过只看基数还解释不了这次选择。`EXPLAIN` 里的 `rows` 是优化器估计的扫描行数。清空重插并且旧事务还开着时，走 `idx_zone` 的计划可能把扫描行数估到两万多甚至接近三万，而聚簇索引扫描的估计仍在八万出头。真实范围只有约 8001 行，是这个偏大的估计把判断带歪了。

还有一个容易忽略的问题：既然二级索引估出来要扫近三万行，全表要扫八万行，为什么反而选了更多的那个？因为用 `idx_zone` 时，每拿到一个主键都要回表取整行，优化器把回表的代价也算进去了。直接扫主键索引则没有这一跳。可以粗算一下它眼里的代价：二级索引路径大约是“扫近三万个索引项，再随机回表近三万次”；聚簇索引路径是“顺着叶子顺序扫八万行”。随机回表在它的代价模型里很贵，于是顺序扫描虽然行数更多，仍可能被判为更便宜。从实际耗时看，这个判断输给了强制走二级索引的计划——真实范围只有约 8001 行，回表次数远没有三万。回表要计入代价，这个原则本身没问题，问题仍是扫描行数估得不准。

行数为什么会在“删除再灌入”之后突然变大，和旧版本还留在索引上有关。会话 A 的事务不结束，被删掉的那些索引项就不能立刻从树上抹去。采样若把这些已删除标记也算进去，区号索引看起来比实际要“厚”。这一层留到下一讲对照实验再拆开。这里先记住：`rows` 是估计，不是执行后的真实行数；慢日志里的扫描行数才是事后事实。

实践里如果 `EXPLAIN` 的 `rows` 和真实扫描差得很远，可以先让引擎重新采样：

```sql
ANALYZE TABLE gauge_log;
```

很多时候执行计划会回到刚建完数据时的样子。统计不准是一类问题，但优化器不只有行数这一个输入。再看另一条语句：

```sql
SELECT *
FROM gauge_log
WHERE zone_code BETWEEN 1 AND 700
  AND batch_code BETWEEN 42000 AND 80000
ORDER BY batch_code
LIMIT 1;
```

按这批数据，`zone_code` 和 `batch_code` 始终相等，两个范围没有交集，结果应是空集。

若走 `idx_zone`，先扫区号最小的大约 700 个索引项，再回表看批次是否落在 42000 到 80000。大约检查 700 行。因为数据里两列相等，这 700 行的批次也在 1 到 700 之间，过滤之后一行都留不下，但引擎仍要把这 700 行看完才能确定。

若走 `idx_batch`，批次条件对应末尾大约 38001 个索引项，同样要回表过滤区号。单看行数，区号索引明显更小。批次索引的优势只在于：它已经按 `batch_code` 排好，配合 `ORDER BY batch_code LIMIT 1`，优化器可能认为不必再单独排序，找到第一条同时满足区号条件的记录就可以停。在这批数据里，根本不存在这样的行，于是它会把那三万多行都走完，事先假设的“很快碰到第一行”并不成立。

`EXPLAIN` 却常常选中 `idx_batch`，`rows` 估在三万八千上下。这里能看出两件事：行数估计仍然不准；优化器又一次没选扫描更少的索引。

## 索引选择异常时怎么处理

多数语句优化器能选对。碰到上面两类“明明有更短的路径却走慢了”的情况，可以考虑下面几种处理。

第一种是 `FORCE INDEX`，像前面对照实验那样写死候选索引。优化器会先根据条件列出可能用到的索引，再逐个估算。如果提示的索引在候选里，就直接用它，不再和其他索引比代价。

第二条语句强制走区号索引后，耗时可以从一两秒降到几十毫秒，差距能到几十倍。提示确实把计划拉了回来。

不少人排斥把它写进业务语句：读起来生硬；索引改名后语句也得改；迁到别的数据库时语法可能不被接受。更麻烦的是时效。选错索引并不常见，开发时通常不会预先写上。等线上已经慢了，再改语句、测试、发布，对生产来说绕了一圈。能在库内解决的，尽量别等发版。还要注意提示只在索引仍是候选时生效。条件若写成让这列用不上索引的形式，`FORCE INDEX` 也变不出一条不存在的访问路径。它纠正的是“候选里选错了”，不是“根本没有可用索引”。

第二种是改写语句，让优化器自己偏向期望的索引。这条语句里把 `ORDER BY batch_code LIMIT 1` 写成 `ORDER BY batch_code, zone_code LIMIT 1`，在“最多返回一行、且按批次取最小”这个前提下，结果和原来一致。

优化器原先偏向 `idx_batch`，是因为批次索引已经按 `batch_code` 有序，用它可以不做额外排序，哪怕估计要扫很多行，也觉得更便宜。排序键变成两列之后，两条索引都满足不了顺序，都得排序。扫描行数重新变成主要因素，计划就会落到大约 700 行的 `idx_zone` 上。

这个改法不通用。这里刚好有 `LIMIT 1`，多加一个排序列不会改变“批次最小的那一行”。没有这个限制时，不要用改排序键去赌计划。

若不想碰排序语义，还可以把范围先收进派生表，让优化器看见批次索引上的大范围并不便宜：

```sql
SELECT *
FROM (
  SELECT *
  FROM gauge_log
  WHERE zone_code BETWEEN 1 AND 700
    AND batch_code BETWEEN 42000 AND 80000
  ORDER BY batch_code
  LIMIT 80
) AS picked
LIMIT 1;
```

内层先限制 80 行，是利用这批数据的分布去影响代价估算，换一组数据可能就不起作用。

第三种是调整索引集合：加一条更贴合条件的索引，或者删掉被误用的那条。这个例子里不容易靠新增索引把计划扳回来。经过仔细设计的库更是如此，再撞上优化器误判时，往往没有一条显然更好的新索引可加。

删掉 `idx_batch` 听起来鲁莽，但确实遇到过：和业务确认之后，发现被选错的那条索引没有任何语句真正依赖，删掉之后优化器回到了正确的路径。动索引之前要把现有语句的访问路径核对完。可以用慢日志或执行计划把引用这列的语句列出来，确认没有人靠它避免排序或做覆盖查询，再删。只凭“这次选错了”就删，可能把另一条本来靠它的语句推成全表扫描。

选错之后的排查可以按固定顺序走，避免一上来改业务代码。先看 `EXPLAIN` 的 `key` 和 `rows`，再强制指定你认为对的索引，比较慢日志里的扫描行数和耗时。若强制之后明显更快，说明问题在选择而不在语句结果。接着 `ANALYZE TABLE`，看计划是否自己回来。统计刷新后仍选错，再考虑改写排序、调整索引或临时加上索引提示。这个顺序把“数据估计过期”和“代价模型偏向了避免排序”分开，两种原因的修法并不一样。

## 小结

索引统计靠采样更新，采样页数和触发行数由 `innodb_stats_persistent` 决定，基数因此可能偏。优化器再拿这个估计去算扫描行数，还要加上回表和排序的代价。估计偏了，就可能放弃其实更快的二级索引。

统计过期时，先 `ANALYZE TABLE`。其他误判可以用 `FORCE INDEX` 指定，也可以改写语句去引导，必要时增加或删除索引。这些现象要追到源码里量化每一步代价，已经超出日常排障需要掌握的范围。上面几条是可以先落地的处理顺序。

思考题：构造第一个例子时，必须有会话 A 开着事务，会话 B 删除并重新插入之后，`EXPLAIN` 给二级索引的 `rows` 才会从大约 8000 涨到两万以上。如果没有会话 A，只依次执行删除、`CALL fill_gauge()` 和 `EXPLAIN`，估计行数仍在 8000 附近。为什么差在这个未提交的事务上？

## 上期问题时间

上一讲问的是：某次写入走了 change buffer，主机随即异常重启，内存里的 change buffer 和对应数据会不会丢。

不会丢。change buffer 当时只改了内存，但事务提交时，这次修改已经写进 redo。崩溃恢复会把 change buffer 里的记录一并找回来。

合并回数据页的过程也可以分开看：

1. 把数据页从磁盘读进缓冲池，此时页上还是旧内容。
2. 找出 change buffer 里属于这一页的记录，可能有多条，按顺序套用，得到新页。
3. 写 redo。这份日志同时覆盖数据页的变化和 change buffer 的变化。

合并到这里就结束了。数据页和 change buffer 对应的磁盘位置都还是旧的，它们在缓冲池里属于脏页。之后各自刷盘，是另一个过程，不在这次合并里完成。
