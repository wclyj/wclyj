锁是为了给并发访问定规矩。按范围，MySQL 里大致有全局锁、表级锁和行锁。这一讲只看前两类，行锁放到后面。重点是遇到锁时能看见什么现象，以及现象背后的规则，不展开锁结构在源码里的字段布局。

# 全局锁

全局锁锁住的是整个实例。`FLUSH TABLES WITH READ LOCK`（常被写成 FTWRL）会让库进入只读：别的线程上的数据修改、建表改表这类定义语句，以及更新事务的提交，都会被堵住。

典型用途是做全库的逻辑备份，也就是把每张表查出来写成文本。早期的做法是先拿全局读锁，再导出。导出期间整库都不能写。

这样做的副作用很直接：

- 锁加在主库上，备份窗口里业务写请求全部停住；
- 锁加在备库上，备库无法应用主库传来的 binlog，主备延迟会在窗口里一直涨。

那备份为什么想加锁？不加的话，导出来的文本可能对不齐同一次业务。

假设会员系统里有两张表：`point_wallet` 存积分余额，`coupon_hold` 存已经领到的券。备份线程先把积分表导完。导出间隙里，用户用 80 积分换了一张券：余额被扣掉，持券表多了一行。接着备份线程才去导持券表。恢复出来的结果是：券已经在账上，积分却还是扣之前的数字。用户等于白拿了一张券。

把两张表的导出顺序对调，会得到另一种错法：积分已经扣了，券却不在备份里。无论哪种，备份都不是同一个逻辑时点上的快照。

可重复读下开启一个事务，就能拿到一致性视图。官方的逻辑导出工具是 mysqldump。加上 `--single-transaction` 时，它会在导出前开始一个事务，靠 MVCC 读到开局那一瞬间的数据，导出过程中业务仍可以正常更新。

那还要 FTWRL 做什么？一致性读的前提是引擎做得到这种隔离。MyISAM 没有事务，备份读到的永远是当下最新值，中途的更新会把快照撕开。这种表只能靠 FTWRL 把写入挡在外面。因此 `--single-transaction` 只适合库里的表都使用支持事务的引擎。库里还混着 MyISAM 时，逻辑备份往往退回全局读锁。这也是推动业务把表换成 InnoDB 的理由之一。

另一种让全库只读的办法是 `SET GLOBAL read_only = ON`。它也能挡住普通账号的写入，但不如 FTWRL 合适，原因有两处：

- 有的高可用脚本用 `read_only` 判断当前实例是不是承接写入的那一台。改这个全局变量会碰到那套判断，影响面超出备份本身。
- 异常退出时的行为不同。FTWRL 由拿锁的会话持有，客户端如果断线，服务器会把这把全局锁放掉，库恢复可写。`read_only` 一旦打开，客户端崩了也不会自动关上，实例可能长时间不能写。

全局锁住之后，给任何一张表加列都会被挡住。即便没有全局锁，加列也还会碰上表级锁。

# 表级锁

表这一层常见两类：用语句显式加上的表锁，以及自动加上的元数据锁 MDL。

`LOCK TABLES ... READ/WRITE` 和 FTWRL 类似，可以用 `UNLOCK TABLES` 释放，会话断开时也会释放。它不只限制别的线程，也限制本线程接下来能碰哪些表。例如某个会话执行：

```sql
LOCK TABLES sku_tag READ, sku_price WRITE;
```

别的线程写 `sku_tag`、读或写 `sku_price` 都会等待。发锁的这个线程在解锁之前，只能读 `sku_tag`、读写 `sku_price`，不能写 `sku_tag`，也不能访问没点名的表。

还没有行锁的时候，表锁是控制并发的主要手段。InnoDB 已经能按行加锁，一般不再用 `LOCK TABLES` 做业务并发，锁整张表的代价太大。

MDL 不需要手写语句。访问一张表时，服务器会自动加上，用来保证读写过程中表结构别被拆掉。设想一个查询正在扫行，另一个线程同时删掉其中一列，查询拿到的列和表定义对不上。

从 5.5 起，对表做增删改查会申请 MDL 读锁；改表结构会申请 MDL 写锁。

- 读锁和读锁不互斥，多个线程可以同时读写数据。
- 读锁和写锁互斥，写锁和写锁也互斥。两个加列语句要排队；结构变更进行时，普通读写也不能插进来破坏定义。

MDL 是默认行为，却很容易把库拖死。给小表加一列，有时比给大表加列更快把连接打满。下面按 5.6 的行为来看，表 `sku_tag` 很小：

1. 会话 A 开启事务，对 `sku_tag` 做一次查询。查询结束，但这笔事务还没提交，MDL 读锁继续持有。
2. 会话 B 同样只做查询，要的也是 MDL 读锁，可以立刻执行。
3. 会话 C 对 `sku_tag` 执行加列。它需要 MDL 写锁，被 A 的读锁挡住，开始等待。
4. 此后任何新的查询、插入、更新，都要先拿 MDL 读锁。写锁请求已经排在队列里时，这些新的读锁请求也会排在它后面。表等于不能读也不能写。

如果这张表的语句很密，客户端超时后又会新开连接重试，线程数会很快被打满。

要记住：事务里的 MDL 在语句开始时申请，语句结束并不释放，要等到整个事务提交或回滚。

给小表加列，可以按这个顺序降低风险：

- 先处理长事务。事务不结束，MDL 就一直占着。`information_schema.innodb_trx` 能列出正在执行的事务。目标表上如果挂着长事务，先停掉这次 DDL，或者把那个事务停掉。
- 热点小表上，查询一条接一条，刚杀掉旧事务，新请求又把读锁拿上了。更理想的做法是给加列语句一个等待上限：在限定时间内拿到 MDL 写锁就继续，拿不到就放弃，不要把后面的业务语句堵在队列里。应用或 DBA 再重试。

MariaDB 已经合入 AliSQL 的写法，这两条分支都支持在改表语句上声明不等待或最多等若干秒：

```sql
ALTER TABLE sku_tag NOWAIT ADD COLUMN tag_note VARCHAR(40) NULL;

ALTER TABLE sku_tag WAIT 3 ADD COLUMN tag_note VARCHAR(40) NULL;
```

# 小结

全局锁主要用于逻辑备份。表全部使用 InnoDB 时，优先用 `--single-transaction`，备份期间业务仍能写。

显式表锁多出现在引擎没有行锁的年代。业务代码里如果还有 `LOCK TABLES`，常见两类情况：库里仍在用 MyISAM 这类不支持事务的引擎，需要安排换掉；或者引擎已经换了，代码还留着旧习惯。后一种把加锁和解锁改成事务的开始和提交，往往就能去掉整表锁。

MDL 会留到事务结束。做结构变更时要避免一份读锁把后续查询和更新全排到写锁后面。

# 上期问题时间

上一讲留下的是联合主键和二级索引里“主键列会不会被重复带上”。把读者答案改写成下面这组数据。

表 `ship_leg` 的列是 `lane`、`hop`、`weight`、`memo`，主键为 (`lane`, `hop`)。六行数据如下：

| lane | hop | weight | memo |
| --- | --- | --- | --- |
| 3 | 1 | 8 | m |
| 3 | 5 | 4 | m |
| 3 | 8 | 8 | m |
| 7 | 2 | 4 | m |
| 7 | 6 | 6 | m |
| 7 | 9 | 1 | m |

聚簇索引按主键排序，等价于先排 `lane` 再排 `hop`，`weight` 不参与这段顺序。

只在 `weight` 上建二级索引时，叶子上实际带着主键里还没出现的列，顺序是 `weight`、`lane`、`hop`。排出来是：

- (1, 7, 9)
- (4, 3, 5)
- (4, 7, 2)
- (6, 7, 6)
- (8, 3, 1)
- (8, 3, 8)

再看 (`weight`, `lane`) 这个索引。它自己已经包含 `lane`，叶子上补的是主键里剩下的 `hop`，顺序仍是 `weight`、`lane`、`hop`。和上面那份完全一样，因此 (`weight`, `lane`) 是多余的。

(`weight`, `hop`) 则不同。叶子顺序是 `weight`、`hop`，再补上主键里剩下的 `lane`。同样的重量下会先比 `hop`，例如重量 4 的两行会变成 (4, 2, 7) 然后才是 (4, 5, 3)，和只按 `weight` 排出来的顺序不一致。这个索引提供了另一套排序，应该保留。
