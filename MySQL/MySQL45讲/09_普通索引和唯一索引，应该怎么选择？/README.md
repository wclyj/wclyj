# 普通索引和唯一索引差在更新，不差在查询

业务如果已经保证某个编号不会重复，这一列上还要不要建成唯一索引？查询结果两边一样，差别在写入路径能不能走 change buffer。

档案库按证件号查姓名：

```sql
select person_name
from resident
where cert_no = '310101199204183215';
```

证件号很长，不适合当主键，但需要一棵索引。应用层已经挡住了重复写入。此时唯一索引和普通索引在逻辑上都对，性能上却不该随便选。

下面借用一棵二级索引来比。表 `parcel` 的主键是 `parcel_no`，普通或唯一地索引了 `route_code`，现有键值 `(8,10)`、`(15,30)`、`(22,50)`、`(41,80)`、`(63,120)`，路线码互不重复。叶子上存的是 `(route_code, parcel_no)`。

## 查询几乎没有差别

语句是 `select parcel_no from parcel where route_code = 41`。从根走到叶子页之后，页内用二分找到记录。

- 普通索引找到 `(41,80)` 之后还要再看下一条，确认下一条已经不是 41，才能停。
- 唯一索引知道 41 至多一条，找到之后直接停。

多出来的那一眼，几乎测不出来。InnoDB 以页为单位读写，默认一页 16KB。记录所在的页已经在内存里，多看下一条只是页内指针移动和一次比较。

只有一种边缘情况会贵一点：命中的记录刚好是这一页的最后一条，下一条在相邻页，普通索引必须再读一页。整型键一页能放下近千个，记录恰好卡在页尾的概率很低。平均下来，查询性能可以当成没有差别。

选择依据不在读，在写。

## change buffer 是什么

更新某个数据页时，如果页已经在缓冲池里，直接改内存。如果页不在内存里，并且这次修改不破坏一致性约束，InnoDB 可以把这次修改先记在 change buffer 里，避免为了改几个字节去把整页从磁盘读上来。

以后真有查询碰到这一页，再把页读进内存，把 change buffer 里关于它的操作补上。这个补做的过程叫 merge。除了读页会触发 merge，后台线程会定期做，正常关闭实例时也会把剩下的 merge 做完。

change buffer 这个名字容易让人以为它只活在内存里。它是可以落盘的：内存中有一份，系统表空间里也有一份。事务提交时，相关修改进入 redo，崩溃之后还能补回来。

能省掉一次随机读，更新语句就会快一截；页不必为了这次写入进缓冲池，内存也可以留给真正会被读到的数据。

唯一索引用不上这条路径。插入 `(route_code, parcel_no) = (30, 70)` 之前，必须确认树上还没有 30。确认的唯一办法是把目标页读进内存来看。页已经在内存里，就地插入比先记一笔 change buffer 更直接，所以唯一索引的更新不会走 change buffer。能用 change buffer 的是普通二级索引。

change buffer 占用的是缓冲池里的内存，不能无限涨。`innodb_change_buffer_max_size` 按缓冲池的百分比限制它，设成 50 表示至多拿缓冲池的一半。这个值可以动态改。

## 同样是插入，页在不在内存里完全两样

还是插入 `(30, 70)`，位置在已有的 22 和 41 之间。

目标页已经在内存中：

- 唯一索引：在 22 和 41 之间确认没有 30，插入，结束。
- 普通索引：找到同一位置，插入，结束。

差别只是一次唯一性判断，多一点点 CPU，不是讨论的重点。

目标页不在内存中：

- 唯一索引：先把数据页读进来，确认没有冲突，再插入。
- 普通索引：在 change buffer 里记上“往这一页插入这一行”，语句就可以返回。

把页从磁盘随机读进内存，是数据库里最贵的动作之一。普通索引把这次读推迟到以后真的需要这页时再做，写入就被拉开差距。

实际里见过这样的转折：一张插入很多的表，缓冲池命中率原来大约 98%，有人把其中一棵普通二级索引改成唯一索引，第二天命中率掉到 70% 附近，更新语句开始排队。原因不是磁盘突然变慢，而是每次插入都被迫把不在内存里的叶子页读上来做唯一性检查，缓冲池被这些本来不会被读到的页冲掉了。

## 什么业务吃得上这块收益

merge 才是真正改数据页的时刻。change buffer 里为同一页攒下的修改越多，省下的随机读就越值。

写多读少时，页写完之后很快被读到的概率低，记录可以在 change buffer 里多待一会儿，收益最大。账单、操作日志、采集流水都是这种形态。

反过来，如果每次写入之后立刻按同一列查回去，页马上被读入，merge 立刻发生。随机读一次也没少，还多了维护 change buffer 的开销。这种读紧跟写的模型里，change buffer 帮倒忙，应该关掉。

## 怎么选

查询能力上，两类索引可以看成一样。在应用已经保证不会插入重复值的前提下，从性能出发优先建普通索引，把 change buffer 留给它。

如果所有更新后面都紧跟着对同一行的查询，关掉 change buffer。其余情况，它都能减轻更新时的随机读。

数据量大、磁盘又是机械盘时，这个差距尤其明显。机械盘的随机 IOPS 只有几百，少一次随机读就少一次寻道。归档库、历史库若还在用机械盘，二级索引尽量用普通索引，并把 change buffer 的上限调大，让批量写入少碰数据页。

正确性仍然排在性能前面。业务并不能保证不重复，或者产品要求数据库来当最后一道约束，那就建唯一索引，没有商量。这篇的意义是：当大批插入变慢、命中率往下掉时，多一条排查线索，看看是不是有人把本来可以普通的索引改成了唯一。

归档库是个明确的例外。线上只留近半年，历史行已经确认没有重复键。为了灌库更快，可以把归档表上的唯一索引改成普通索引，让 change buffer 生效。线上那张仍要约束的表不必跟着改。

## change buffer 和 redo 不是一回事

两者都在减少随机 I/O，所以容易混。redo 把随机写变成顺序写；change buffer 省的是随机读。放进同一次插入里看就清楚了。

```sql
insert into parcel (parcel_no, route_code) values
  (70, 30),
  (90, 55);
```

假设定位之后，路线码 30 所在的叶子页已经在缓冲池，55 所在的叶子页不在。这次更新碰到四块地方：缓冲池内存、redo 日志文件、表空间里的数据页、系统表空间里的 change buffer 持久化区域。

按发生顺序：

1. 第一页在内存中，直接改内存里的页。
2. 第二页不在内存中，只在 change buffer 里记下“要往这一页插入一行”。
3. 上面两件事都写进 redo。两笔日志可以合在一次顺序写里刷下去。

做完这些，事务就能向客户端确认。成本是两处内存修改，加上一次顺序的日志写。随后把脏页和 change buffer 页写进表空间的动作在后台进行，不占这次插入的响应时间。

把两次写入拆开看，才不会把两种日志记混。第一页的修改已经在缓冲池里，redo 只是为了崩溃后能把这次内存修改重做出来，它并不代替数据页。第二页的修改连数据页都还没碰，change buffer 记下的是“将来读到这一页时要补做的插入”，redo 再把这条 change buffer 记录保护下来。所以崩溃恢复先恢复 change buffer 里的那条意图，而不是直接去改磁盘上的第二页。第二页仍然要等下一次被读到，或者后台 merge，才会变成缓冲池里的脏页。

紧接着读 `route_code in (30, 55)`：

1. 第一页仍在内存里，直接用内存里的版本返回。磁盘上的页可能还是旧的，但内存才是当前结果，不需要先把 redo 重放到磁盘再读。WAL 之后的读，不一定要读盘。
2. 第二页内存里没有。从磁盘把旧页读进来，再把 change buffer 中关于它的操作 merge 上去，得到正确版本后返回。在这次读发生之前，那一页可以一直躺在磁盘上。

所以一句话：redo 省的是随机写，change buffer 省的是随机读。数据页最终仍然来自内存里的页被刷下去，而不是由 redo 直接改磁盘上的页。

## 小结

普通索引查询时多看一条相邻记录，因为整页已经在内存里，这点成本可以忽略。唯一索引的更新必须读页才能判断冲突，因此走不了 change buffer。写多读少的普通索引把随机读推迟，收益明显；写完立刻读，则应关闭 change buffer。

业务守不住唯一性时，仍然建唯一索引。性能讨论的前提，是重复值根本不会被送进来。

## 掉电会不会把 change buffer 弄丢

change buffer 先写在内存里。如果还没来得及把数据页 merge 完就断电，会不会丢更新？

不会。记入 change buffer 的那个动作，和直接改内存页一样，在事务提交路径上写进了 redo。重启后先按 redo 把 change buffer 恢复出来，以后再读到对应数据页时，merge 仍然发生。丢掉的是还没刷盘的数据页，不是这笔记账。若 change buffer 本身没进 redo 就崩溃，事务也不会被当成已提交。

## 和“读到旧版本”有关的一个补充

有一种现象是：另一个会话明明把值改过了，当前会话却仍然看见改之前的内容。除了“对方还没提交、当前读用的是自己的快照”这一类常见原因，还有一条时间线容易漏掉：写事务比读事务更早开始。

读事务创建视图的那一瞬间，如果写事务仍然处于活动状态，这个写事务产生的版本对这份视图算“尚未提交”，因此不可见。即便后来写事务先提交，这份已经生成的一致性视图也不会把它算进来。判断可见性时，除了版本号本身，还要看视图生成那一刻哪些事务还活着。
