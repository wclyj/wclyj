# 随机抽三行，为什么 order by rand() 会越来越慢

首页要随机展示三张词卡。词表变大以后，这个接口把首页拖慢了。下面把需求收成：从一张词表里随机拿 3 行，看哪种写法在扫多少行、做多少排序。

```sql
create table vocab_card (
  card_id int not null auto_increment,
  spelling varchar(64) default null,
  primary key (card_id)
) engine=InnoDB;

delimiter ;;
create procedure fill_vocab()
begin
  declare n int default 0;
  while n < 8000 do
    insert into vocab_card(spelling)
    values (concat('w', lpad(n, 4, '0')));
    set n = n + 1;
  end while;
end;;
delimiter ;

call fill_vocab();
```

表里有 8000 行。先看最容易写下的那句在做什么，再换成按主键位置抽取。

## 内存临时表上的随机排序

```sql
select spelling from vocab_card order by rand() limit 3;
```

语义是给每行一个随机数，按随机数排序，取前 3。`explain` 的 Extra 里通常同时有 `Using temporary` 和 `Using filesort`：要建临时表，还要在临时表上排序。

InnoDB 表做排序时，优化器更倾向把要用的列放进排序缓冲区，避免排完序再按主键回表、多读一次磁盘。内存表没有这层顾虑。回表只是按位置访问内存，不碰磁盘。于是优化器改成让参与排序的行尽量短，选择 rowid 排序：排序缓冲区里只放排序键和行位置。

这句的执行可以分成几步：

1. 建一张 Memory 引擎的临时表，两列，没有索引。一列是 `double`，记为随机值 R；一列是 `varchar(64)`，记为拼写 W。
2. 按主键扫描 `vocab_card`，对每行调用 `rand()` 得到一个 0 到 1 之间的小数，把小数和拼写写进临时表。这一步扫描 8000 行。
3. 临时表现在有 8000 行，接下来按 R 排序。
4. 准备 sort buffer，里面两列：一个 `double`，一个整数位置。
5. 把临时表再扫一遍，取出 R 和这行在内存表中的位置，放进 sort buffer。扫描行数变成 16000。
6. 在 sort buffer 里按 R 排序。这一步不读表，扫描行数不变。
7. 取最小的 3 个位置，回到临时表取出拼写，返回客户端。再访问 3 行，总扫描行数 16003。

慢查询日志里能对上这个数，例如 `Rows_examined: 16003`、`Rows_sent: 3`。先按步骤把行数加出来，再用慢日志核对，比直接看语句是否“看起来简单”可靠。

这里的位置不是 InnoDB 的主键。每种引擎用自己的方式标记一行：

- 有主键的 InnoDB 表，rowid 就是主键。
- 没有主键时，InnoDB 会生成一个 6 字节的隐藏 rowid，表仍然能定位行。删掉主键不等于不能回表。
- Memory 引擎不是索引组织表，可以看成数组，这里的 rowid 就是数组下标。

所以 `order by rand()` 的代价是：全表写进临时表，再对临时表做一次 rowid 排序。行数上来之后，这个代价线性增长。

## 临时表放不下时，以及为什么不用把 8000 行都排完

`tmp_table_size` 限制内存临时表的大小，默认 16MB。超过之后改用磁盘临时表。磁盘临时表的引擎由 `internal_tmp_disk_storage_engine` 决定，默认是 InnoDB。此时排序就变成对一张没有显式索引的 InnoDB 临时表做排序。

把几个参数调小，可以逼出这条路径，并看优化器留下的痕迹：

```sql
set tmp_table_size = 2048;
set sort_buffer_size = 24576;
set max_length_for_sort_data = 24;
set optimizer_trace = 'enabled=on';

select spelling from vocab_card order by rand() limit 3;

select * from information_schema.optimizer_trace\G
```

`max_length_for_sort_data` 设成 24，小于 `spelling` 的定义长度，排序模式会是 rowid：排序行只有随机值 R（8 字节）和 rowid（6 字节）。8000 行大约 11 万字节，已经超过 `sort_buffer_size` 的 24576。若走归并排序，应该出现临时文件。`optimizer_trace` 里却常常看到 `number_of_tmp_files = 0`，并且 `filesort_priority_queue_optimization` 的 `chosen` 为 true。

语句只要 3 个最小的 R，不需要其余 7997 行的顺序。归并排序会把 8000 行全部排好，多做的有序性没有人用。优先队列只维护一个大小为 3 的堆：

1. 取前 3 个 `(R, rowid)` 建成堆。为了随时知道当前最大的 R，堆顶保持最大值，这是一个最大堆。
2. 读入下一行，若它的 R 比堆顶小，就用它替换堆顶，并重新调整堆。
3. 重复到第 8000 行。

堆里留下的就是最小的 3 个 R。再按 rowid 回临时表取拼写，和前面的 rowid 排序后半段一样。因为堆只有 3 行，放得进 sort buffer，不需要临时文件。

用六个随机值可以把这个堆走一遍。假定依次读到的 R 是 0.70、0.20、0.55、0.10、0.80、0.15，只要最小的三个。前三个先入堆，堆顶保持当前最大的 0.70。读到 0.10，比堆顶小，替掉 0.70，堆里变成 0.55、0.20、0.10，堆顶调整为 0.55。读到 0.80，比堆顶大，丢掉。读到 0.15，比 0.55 小，替掉堆顶。最后留下 0.20、0.10、0.15。全程只比较、替换这三格，不会去排 0.80 和 0.70 谁更大。行数从 6 变成 8000 时，比较次数仍然是每个元素进堆一次，而不是把 8000 个数做成完全有序。

这也解释了扫描行数接近时，两种写法仍然差很远。`order by rand()` 先把 8000 行写进临时表，再对每一行做堆操作或归并，CPU 和内存带宽都花在用过即弃的随机数上。按行号抽取时，第二段扫描只是顺着主键往后读，读到目标行就停，不做比较器，也不给每行分配一个随机键。慢日志里的 `Rows_examined` 相同，不代表排序缓冲区和临时表的开销相同。

不是所有带 `limit` 的排序都走优先队列。例如：

```sql
select depot, courier, years
from route_staff
where depot = '宁波'
order by courier
limit 800;
```

若排序行是 `(courier, rowid)`，堆里要维持 800 行，体积超过 `sort_buffer_size` 时，优化器放弃优先队列，改回落临时文件的归并。`limit` 很大时，优先队列省不下内存。

不论临时表在内存还是在磁盘，`order by rand()` 都要碰全表、写临时表、再维护排序结构。它不适合放在每次打开首页都执行的路径上。

## 按主键位置抽，少做一次全表排序

先考虑只抽 1 行。

算法甲：取出主键的最大值 H 和最小值 L，在这个闭区间里随机一个整数 P，再取主键不小于 P 的第一行。

```sql
select max(card_id), min(card_id) into @hi, @lo from vocab_card;
set @pick = floor((@hi - @lo + 1) * rand() + @lo);
select spelling from vocab_card where card_id >= @pick limit 1;
```

`max` 和 `min` 走索引端点，第三句是一次索引定位。可以粗略看成只碰了 3 行。它不均匀。主键若有空洞，空洞后面的那一行会被更多的随机数命中。主键是 3、4、7、8 时，落到 7 的概率大约是落到 3 的两倍，因为 5 和 6 都不存在，随机数取到 5、6 时都会停在 7。若主键是 5、6、80000、80001，几乎总会抽到后面两行。空洞一大，这个算法就不能叫随机。

算法乙为了均匀，改成按行号而不是按主键值：

1. `count(*)` 得到总行数 C。
2. `Y = floor(C * rand())`，Y 落在 `0` 到 `C-1`，每一行概率相同。
3. `limit Y, 1` 跳过前 Y 行，返回下一行。

`limit` 的偏移在语句文本里需要是可计算的整数。稳妥的做法是在应用里把 Y 拼进 SQL，或者用 `prepare` 执行拼好的文本。MySQL 处理 `limit Y, 1` 的方式是沿主键顺序读，丢掉前 Y 行，再返回一行，所以这一步扫描 Y+1 行。加上统计总行数的 C 行，一共大约 C+Y+1 行。

`count(*)` 在只有主键、没有过滤条件时，走的是索引上的行数统计，不必把 8000 行的 `spelling` 都读出来。贵的是第二段：偏移越大，丢掉的主键越多。抽 3 行如果各自从第一行重新数，最坏会把表头重复扫描三遍。这也是后面要把三个偏移排序后再做一次顺序扫描的原因。

这比算法甲贵，因为 Y 可能接近 C。它仍然比 `order by rand()` 便宜得多。即使 Y 很大，扫描行数看起来接近 16000，也不等于代价接近：`order by rand()` 要写临时表，还要对 8000 个随机数做堆或归并；算法乙的第二段只是主键顺序扫描，扫到第 Y 行就停，没有排序，没有临时表。扫描行数只是代价的一部分，排序和临时表才是那句随机排序慢的原因。

抽 3 行时把算法乙做三遍，称为算法丙：

1. 数出 C。
2. 独立取 Y1、Y2、Y3。若三者有重复，就重新取，避免抽到同一行。
3. 执行三句 `limit Yn, 1`。

总扫描行数大约是 `C + (Y1+1) + (Y2+1) + (Y3+1)`。偏移的拼接放在应用里做，数据库只负责按偏移读一行。业务上的随机、去重、拼语句，都留在应用代码里，库只做读写。

## 小结

`order by rand() limit 3` 会建临时表并做 filesort。内存临时表选用 rowid 排序，因为按位置取内存很便宜，排序行越短越好。临时表超过 `tmp_table_size` 就落到磁盘。只要的行数很少时，排序可以用大小固定的优先队列，不必把全表排成有序文件。

要均匀地随机一行，按 `count(*)` 得到行号再 `limit` 偏移，代价是 C+Y+1，但没有全表排序。主键区间随机更快，却会被空洞扭曲概率。抽多行时，用多句按行号取出，比一句 `order by rand()` 好控制。

## 三行还可以少扫一些

算法丙的三次 `limit` 各自从头开始。把 Y1、Y2、Y3 先排序，假定 `Y1 < Y2 < Y3`。一次按主键顺序扫描，跳过 Y1 行取一行，再跳过 `Y2-Y1-1` 行取一行，再跳过 `Y3-Y2-1` 行取一行，扫到最大的那个偏移就可以停。

扫描行数变成 `C + Y3 + 1`，也就是总行数加上最大偏移，而不是三个偏移之和。三句独立查询若无法合成一次扫描，至少也可以在应用里按主键递增保存上一行的 `card_id`，下一句改成 `where card_id > 上一行主键 limit (Yn - Y前) , 1`，避免重复读取前面的行。有重复的随机行号要在排序前去掉并重抽，否则偏移会并到同一行。

## 两个城市各有序，合在一起仍要排序

`(depot, courier)` 上有联合索引时，单个城市内部 `courier` 是有序的。下面这句却做不到免排序：

```sql
select *
from route_staff
where depot in ('成都', '西安')
order by courier
limit 60;
```

两个城市各自有序，拼在一起的 `courier` 并不是一段递增序列。优化器不能靠索引直接取出全局前 60 名，语句需要排序。

把一句拆成两句，每句都能用上联合索引：

```sql
select person_id, courier
from route_staff
where depot = '成都'
order by courier
limit 60;
```

西安同样取 60 行。两个结果都已按 `courier` 有序，在应用里做归并，取出最小的 60 个即可。数据库不做跨城排序。

若是 `limit 5000, 60`，每一端要取到第 5060 行，两句都写成 `limit 5060`，再用归并丢掉前 5000 个，留下后面 60 个。数据量变大时可以两个连接同时往外读，不必等两端全部进应用内存再开始比较。

这个拆法的损失是返回给应用的行变多。行本身很宽时，两句只取 `person_id` 和 `courier`，归并得到目标的 60 个主键，再按主键把整行查回来。多一次主键查询，少搬很多无关的列。
