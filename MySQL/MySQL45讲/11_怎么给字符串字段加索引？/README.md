登录名、邮箱、证件号这类字符串，经常被拿来做等值查找。索引若按整列来建，能精确匹配，也可能很占地方。这一讲用邮箱和证件号看几种建法的差别。

用户表可以简单定义成：

```sql
CREATE TABLE acct_login (
  uid BIGINT UNSIGNED PRIMARY KEY,
  mail_addr VARCHAR(80),
  nick VARCHAR(32)
) ENGINE=InnoDB;
```

登录时会出现类似的等值查询：

```sql
SELECT uid, nick
FROM acct_login
WHERE mail_addr = 'linqiao92@northmail.co';
```

`mail_addr` 上没有索引时，这条语句只能扫全表。MySQL 允许只把字符串的前一段拿来做索引。创建时不写长度，索引里就是完整字符串。下面两条分别是整列索引和前缀索引：

```sql
ALTER TABLE acct_login ADD INDEX mail_full (mail_addr);

ALTER TABLE acct_login ADD INDEX mail_head (mail_addr(8));
```

`mail_full` 的每个索引项保存完整地址。`mail_head` 对每行只取前 8 个字节。地址是纯英文和数字时，8 个字节就是前 8 个字符。例如 `linqiao92@northmail.co` 在前缀索引里只留下 `linqiao9`。项变短，同样大小的页能放下更多键，这是前缀索引省空间的原因。代价是可能多扫一些并不等于目标值的行。

假设地址里有多条都以 `linqiao9` 开头，其中 `linqiao92@northmail.co` 对应 `uid = 418`。用 `mail_full` 执行时：

1. 在整列索引上找到等于该地址的项，取出 418。
2. 回主键核对地址，把这一行放入结果。
3. 再看索引的下一项，已经不等于这个地址，结束。

回表一次，优化器认为扫描了一行。

用 `mail_head` 时，前缀 `linqiao9` 命中了 4 个账号：

1. 在前缀索引上找到第一个 `linqiao9`，假设主键是 401。
2. 回表发现完整地址不是目标，丢掉。
3. 下一项仍是这个前缀，取出 418，回表后地址匹配，放入结果。
4. 继续向后，直到前缀不再是 `linqiao9`。

这一过程回表 4 次。如果前缀改成 9 个字节，`linqiao92` 只对应一行，就可以一次回表结束。前缀索引要省空间，又不要把额外扫描放大，长度就得单独算，不能凭感觉取一个固定值。

区分度是选择长度的依据。不同取值越多，重复键越少。先数整列有多少个不同地址：

```sql
SELECT COUNT(DISTINCT mail_addr) AS full_cnt
FROM acct_login;
```

再比较几种前缀长度。例如看 5 到 9 个字节：

```sql
SELECT
  COUNT(DISTINCT LEFT(mail_addr, 5)) AS p5,
  COUNT(DISTINCT LEFT(mail_addr, 6)) AS p6,
  COUNT(DISTINCT LEFT(mail_addr, 7)) AS p7,
  COUNT(DISTINCT LEFT(mail_addr, 8)) AS p8,
  COUNT(DISTINCT LEFT(mail_addr, 9)) AS p9
FROM acct_login;
```

先定一个能接受的损失，比如 4%。在 `p5` 到 `p9` 里找第一个不小于 `full_cnt` 的 96% 的长度。若 8 和 9 都达标，就取 8，让索引更短。

# 前缀索引怎么影响覆盖索引

多扫描行只是一方面。再看一条只返回主键和邮箱的语句：

```sql
SELECT uid, mail_addr
FROM acct_login
WHERE mail_addr = 'linqiao92@northmail.co';
```

若走 `mail_full`，索引项里已经有完整地址，主键又会附在二级索引叶子上，结果可以直接从这棵索引返回，不必回表。这就是覆盖索引。

若走 `mail_head`，索引里只有前 8 个字节，服务器无法确认它等于完整地址，必须回表取出 `mail_addr` 再比较。即便把前缀加长到 40，已经装得下这列里实际出现的所有地址，优化器仍然会回表。它只知道索引定义是“截断后的前缀”，不能证明截断没有丢掉信息。因此一旦用了前缀索引，这条查询就用不上覆盖索引。选前缀方案时要把这一点算进代价。

# 前缀区分度不够时的两种改法

邮箱的前半段往往已经比较散，前缀索引效果可以接受。有些编号正好相反，越靠前越重复。

居民证件号共 18 位，前 6 位是地区码。库里如果只存一座城市的数据，长度为 6 的前缀几乎把所有人分进少数几个篮子，区分度很差。按上面的比例去试，可能要取到 14 位甚至更长才达标。键越长，一页里的项越少，树的层数和查找的页数都会上去。

如果业务只按证件号做等值查询，没有范围扫描，还有两条更省的路。

第一条是倒序存放。写入时把证件号反转，查询时也对输入做一次反转：

```sql
SELECT holder_name, region_name
FROM staff_cert
WHERE cert_no = REVERSE('输入的证件号');
```

证件号末尾没有地区码那种大段重复，反转之后原来的末尾变成了前缀，较短的前缀就可能分开大多数人。上线前仍要用 `COUNT(DISTINCT LEFT(cert_no, n))` 对实际数据核对，不要只凭编号规则下结论。

第二条是增加一个整数散列列，并只在这个整数上建索引：

```sql
ALTER TABLE staff_cert
  ADD COLUMN cert_crc INT UNSIGNED,
  ADD INDEX idx_cert_crc (cert_crc);
```

插入时用 `CRC32(cert_no)` 填进 `cert_crc`。不同证件号有可能算出同一个整数，所以查询必须再比对原列：

```sql
SELECT holder_name, region_name
FROM staff_cert
WHERE cert_crc = CRC32('输入的证件号')
  AND cert_no = '输入的证件号';
```

索引键变成 4 个字节，比十几位的前缀短很多。

两种做法的相同点是都不支持范围。倒序之后的字典序不再是证件号原来的大小关系，没法用索引找出某一段连续号码。散列值的大小和原字符串的顺序也无关，只能等值查找。

不同点主要有三处：

1. 空间。倒序不增加列，主键索引里仍是那一串字符。散列要多一列，再加一条整数索引。若倒序后仍不得不取很长的前缀，占用会逐渐接近多出来的这一列。
2. 计算。倒序在读写时调用反转，散列在读写时调用 `CRC32`。只比这两个函数的话，反转更轻。
3. 扫描行数。散列冲突很少，平均每次等值查询接近只检查一行，耗时更稳。倒序加前缀本质仍是前缀索引，前缀相同的行还是要逐条回表。

# 小结

字符串列上常见四种索引策略：

1. 整列索引，匹配精确，也便于做覆盖索引，空间占用最大。
2. 前缀索引，更省空间，可能多回几次表，并且做不了覆盖索引。
3. 先倒序再取前缀，用来避开“前几位高度重复”的编码。
4. 额外的散列列，等值查询的扫描行数稳定，多占空间和一次计算，和倒序一样不能做范围扫描。

按列的分布和查询是等值还是范围来选，而不是所有字符串都取同一个前缀长度。

思考题：学校登录名的形式是“证号@campus.edu”。证号固定 16 位，前 2 位是校区，接着 3 位是院系，再 4 位是入学年份，最后 7 位是顺序号。系统只在登录时按整个登录名做等值校验。只考虑这个查询的话，登录名上的索引你会怎么设计？用前面的区分度方法说明理由。

# 上期问题时间

有人按上一讲的步骤做了，却没看到 `EXPLAIN` 的行数估计变坏。先核对两件事：隔离级别是不是可重复读，表是不是 InnoDB。差一个，旧版本的保留方式就不一样。

上一讲的问题是：为什么必须有一个未提交的事务配合，删除再灌入之后，估计行数才会明显变大。

`DELETE` 把 8 万行删掉，`fill_gauge()` 又插入 8 万行，看起来像原地表被覆盖了。会话 A 的事务还开着，这些旧行不能被清理。每一行因此同时留着删除前的版本，以及标记为已删除的新版本。二级索引 `idx_zone` 上等于有两份数据，优化器按索引采样去估范围行数时，就会把扫描行数估得明显偏大，从大约 8000 涨到两万以上。

主键上的旧版本同样不能立刻清掉。那为什么不强制索引时，`EXPLAIN` 看到的扫描行数仍在 8 万附近，而不是也翻倍？主键这条路径的行数，优化器直接取表统计里的行数估计，也就是 `SHOW TABLE STATUS` 那一类结果，而不是按二级索引上翻倍的版本去数。表统计仍然认为表里大约有 8 万行，于是全表扫描的估计没跟着翻倍。二级索引的代价被高估之后，优化器就更倾向于放弃它。
