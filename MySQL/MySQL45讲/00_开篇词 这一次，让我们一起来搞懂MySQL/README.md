先把这门课的来路对齐。后面几讲反复出现事务、日志和索引，作者把“先讲机制、再拿案例核对”放在口号前面，是有原因的。

作者早期在百度做权限相关的业务，后来到阿里参与云上关系型数据库的内核，并负责过开源分支 AliSQL。从第一次为了一个说不清的慢查询钻进源码，到能把散点收成一张网，中间大约十年。

入门时卡住他的问题很小，也很具体。有一条查询平时十几毫秒就能返回，偶尔却要拖过一百毫秒。主管追问原因，公开资料里找不到能落地的解释；当面承认没想明白又觉得难堪，于是只好直接读代码。那一次并没有立刻变成通用理论，只是把“这条语句慢在哪一层”从猜测收成了能指认的路径。同类缺口后来一次次出现，读源码就从救急变成了默认动作。

这个习惯改变的是写语句时的手感。岗位即便仍是使用方，敲下一条访问时也会先在脑子里过一遍：它会进哪些模块、代价大概落在哪个量级、换一种写法路径会不会更短。哪些汇总交给引擎更合适，哪些留在缓存层更合适，边界也会清楚一些。建表时会提前替以后的查询着想，比如主键要不要递增、把哪一列放进聚簇索引，而不只图眼下好写。

新的别扭马上跟着来。点状结论留不住。一个问题刚查完很透，过几周又淡了，再遇到近亲现象还得把代码重新翻开。能修一次，却修不成可复用的判断。

做内核的那几年把这个洞补上了。内部系统和公有云客户带来的故障足够密，再对照手册把缺口补齐，散点才连得起来。回头看，如果起步时就有一条从机制走到实验的路，很多重复读代码的时间可以省掉。

专栏立项时他并不积极。十几年前，线上出问题几乎只能进代码，公开材料很少。近十年这套数据库在国内已经很普及，文章多到搜不完。把常见知识点再串一遍，增量在哪里，为什么还值得做成一门课？

把读者说清楚之后，理由才具体。数据库背后是几十年的理论，同时它又是被业务每天调用的程序。不少人写了两三年，语句能完成功能，却说不清那些被当成惯例的做法究竟省了什么、防了什么。

课想帮的是这几类人：语句在逻辑上是对的，但不敢确定它是不是代价更低的写法；听过一串实践建议，更想要依据；库偶尔抖动或者数据对不上，希望很快把范围圈到某个机制，而不是只靠重启碰运气。

带应届同事时，要求先把机制讲清，再用实验核对。这批人里有好几位不到两年就能独立撑住一块业务。社招里也见过排障记录不错、动手很熟的候选人，一问到隔离、日志或索引为什么这样设计，就只剩名词，最后没能通过。所以课不铺冷门开关，主线放在日常反复碰到的三块：事务、索引、锁。每个点先说明它是什么、引擎内部怎么做，再接一个从线上问题改写来的追问。

点认全之后连成线。后面的实践部分回头用这些线解释某种写法为什么成立。读者可以按自己的业务把点收成一张网，而不是收藏一堆对不上号的片段。

没有这张网时，慢查询的处理常常是换一个索引名、把返回条数改小，然后看监控是否回落。有了机制之后，会先问这句是在排序、在回表，还是被一份迟迟不结束的读视图拖住。同样写着限制返回行数，有的计划能提前停，有的仍要把符合条件的行都摸一遍，只是少传给客户端。后面几讲反复练的就是这种区分。建索引、开事务、加字段，表面上是语法，底下都连着同一组选择：多读多少页、锁会握多久、崩溃之后能不能对上账。

目录能看到整门课的骨架。这些机制大多不新，有的形态十年里几乎没变。弄清它们的用处，是在做选择时心里有底：知道有哪些路径，也知道取舍落在哪里。底子清楚，业务上的变通才有依据。
