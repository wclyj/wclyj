# 两阶段提交的几个追问，以及互相关注怎么加锁

redo 和 binlog 若各写各的，崩溃之后主库和备库会对不上。两阶段提交用来把它们绑在同一个事务上。真正让人犹豫的是：提交走到一半机器重启，已经写出去的那半边怎么处理。

## 先分清两种 commit

图上的流程经常画成：执行器改引擎 → redo 处于 prepare → 写 binlog → redo 标成 commit。有人会问，图里明明是一句 `update`，为什么出现 commit。

这是两个不同的词。

- 客户端发出的 `commit` 语句，用来结束一个显式事务，和 `begin` 配对。
- 流程末尾那个 commit 步骤，是存储引擎把事务标成已提交的内部动作。这一步做完，事务才算提交完成。

`commit` 语句执行时，会走进这个内部步骤。若没有显式 `begin`，一句 `update` 自己就是一个事务，语句结束时同样要走 prepare、binlog、commit 这三小步。下面说的崩溃时刻，都是指这一步内部，不是指用户有没有敲 `commit`。

## 崩溃落在两个时刻

时刻 A：redo 已经写下 prepare，binlog 还没写，进程崩溃。

恢复时这件事务既没有 commit 标记，binlog 里也没有完整记录，于是回滚。备库不会收到它，主库上它也不留下。这一侧没有争议。

时刻 B：binlog 已经写完并刷好，redo 还没标 commit，此时崩溃。恢复时这件事务会被提交，而不是回滚。规则可以收成两条：

1. redo 里这个事务已经有 commit 标记，直接提交。
2. redo 里只有完整的 prepare，就去看对应的 binlog 是否存在且完整。完整就提交，否则回滚。

时刻 B 落在第 2 条的“提交”分支。

## 怎么判断 binlog 完整

一个事务的 binlog 有固定的结尾。statement 格式最后有 `COMMIT`；row 格式最后有 XID 事件。结尾不在，这段就不算完整。

5.6.2 之后还可以打开 `binlog-checksum`。日志若在中间被磁盘写坏，校验对不上，恢复时能发现，而不是把半截事件当成合法事务。

## 两边靠什么对上号

靠同一个 XID。恢复时按顺序扫 redo：

- 既有 prepare 又有 commit 的，提交。
- 只有 prepare 的，拿 XID 到 binlog 里找这一事务。找到完整事件就提交，找不到就回滚。

XID 在两边各写一次。redo 进入 prepare 时就把这个事务号放进日志；binlog 在 row 格式的结尾事件里也带上同一个号。恢复程序不靠语句文本去对，因为同一句 SQL 可能执行过多次。事务号对上，并且 binlog 那段通过了完整性检查，才认为备库将来一定会重放它，主库也就必须留下同样的结果。

## 为什么时刻 B 要提交而不是丢掉

时刻 B 的 binlog 已经写出，复制线程或用这份 binlog 做恢复的库都会执行它。主库若在恢复时把它回滚，主库没有这行改动，备库却有，主备就分叉了。让主库也提交，两边才仍然一致。这个选择和“binlog 已经对外可见”绑在一起，不是为了少写一次回滚。

## 为什么不能先把 redo 提交了再写 binlog

若 redo 先到达 commit，InnoDB 就认为事务完成，不能再回滚，否则可能覆盖别的事务已经基于这个提交做出的更新。此时 binlog 若写失败，引擎退不回去，数据和 binlog 再次分叉。

两阶段提交给的是一个共同的决定点：redo 先只承诺 prepare，binlog 写成功之后，才把 redo 推进到 commit。任何一边还没就绪，事务都还可以按“binlog 不完整则回滚”处理。分布式系统里这是同一类问题，不是 MySQL 单独发明的手续。

## 能不能只留 binlog

只靠 binlog 做崩溃恢复，流程想象成：改内存 → 写 binlog → 提交。这样仍然不够。

历史上，MySQL 最早的引擎是 MyISAM，没有崩溃恢复。InnoDB 在作为插件接进来之前，自己已经用 redo 提供了事务和恢复。binlog 当时并不承担把页修回来的工作，于是继续用 InnoDB 自己的日志。

实现上也补不上。binlog 记的是逻辑变化（哪一行改成什么），不是数据页里哪些字节变了。考虑下面的时间点：事务 1 的 binlog 已写、事务已视为提交，但它的脏页还没刷盘；事务 2 的 binlog 刚写完、还没提交；此时崩溃。

重启后事务 2 可以回滚，再重放它的 binlog 补回来。事务 1 在系统看来已经提交，不会再重放一次。可 WAL 的含义是：提交时只保证了内存页和日志，页完全可能没落盘。事务 1 的页若丢了，binlog 里没有页的物理增量，修不回来。

把页想成一块 16KB 的格子，事务 1 只改了格子里的几个字节。redo 记下的是“这一页的这个位置要改成什么”，恢复时把整页读进来再打补丁。binlog 记下的是“某一行的某一列现在等于多少”。行格式的日志并不知道这一行落在页的哪一段，也不知道页上其他未提交的修改是否还在。只重放行变更，无法把一块已经丢了一半写入的页拼回提交完成时的样子。所以即使用 binlog 把事务 2 补齐，事务 1 那一页仍然可能是旧的。

若把 binlog 扩成记录页的前后镜像，那就是另写了一份 redo。以现在 binlog 的内容，它支撑复制和归档，支撑不了页级恢复。

## 能不能只留 redo

从崩溃恢复看可以。关掉 binlog，就没有两阶段提交，InnoDB 仍然 crash-safe。

生产库几乎都不关。redo 是环形覆盖的，写到尾部就绕回开头，旧日志留不住，不能当归档。MySQL 的主备复制从一开始就吃 binlog。很多分析系统、搜索索引也在消费 binlog。关掉之后，这些下游没有输入。高可用这套生态建在 binlog 上，redo 替代不了。

## redo 留多大

太小的话，写位置很快绕回检查点，被迫不停刷脏页，WAL 等于没发挥作用。磁盘已经是数 TB 时，不要把日志省成几十 MB。比较稳妥的起点是 4 个文件、每个 1GB，再按写入速率观察检查点是否老被追上。

## 正常运行时，页是谁写进数据文件的

redo 并不保存整页，它没有能力自己把磁盘上的数据页改掉。不存在“最终落盘是由 redo 写进 ibd 文件”这条路。

正常运行时，内存页和磁盘页不一致就叫脏页，落盘就是把缓冲池里的页写出去，这件事可以和某一次 redo 写入无关。

崩溃恢复时，若判断某一页可能丢了提交后的更新，就把页读进内存，用 redo 把内存里的页补到正确版本。补完之后它变成脏页，接下来仍走第一条路，由刷脏页写入数据文件。

## redo log buffer 先记在哪里

一个事务里的日志会写很多次：

```sql
begin;
insert into ledger values (11, 40);
insert into ledger_ext values (11, 'ok');
commit;
```

两条插入各自产生 redo，但不能在用户还没提交时就把这些日志当作已提交写死。redo log buffer 是一块内存，用来先攒这些记录。执行第一句 `insert` 时，数据页在内存里被改掉，对应的 redo 也写进这块 buffer。

把 buffer 写到 `ib_logfile` 这类文件，发生在 `commit` 的时候（自动提交的单条语句，则是语句结束时）。事务执行中间不会为了每条语句主动刷一次日志文件，用来减少 IO。仍可能被动写盘：buffer 本身满了，或者其他事务提交时把缓冲一起刷出去。单条自动提交语句只是把“改内存、写 buffer、提交时落日志”压进了一句。

## 互相关注：记录还不存在时，行锁锁不住

需求是：两人互相点了关注，才写成好友。原设计有关注表和好友表。关注表上 `(actor_id, target_id)` 是唯一键。甲关注乙时先查乙有没有关注甲，有则插好友，没有则只插一条单向关注。

把两次调用按时间摊开就能看见漏判发生在哪里。时刻 1，甲的事务查询“乙是否已经关注甲”，结果为空。时刻 2，乙的事务查询“甲是否已经关注乙”，结果仍为空，因为甲还没插入。时刻 3，两边各自插入一条单向记录并提交。两个查询都没撒谎，合在一起却把“互相已经关注”弄丢了。好友表少了一行，之后再点一次关注也不会自动补上，因为每边都认为关系已经记下。

先做 `select ... for update` 也没用：行还不存在，没有行可锁，两个事务都以为自己是第一个。间隙锁在可重复读下能挡住别人往同一个间隙插入，但这里两个方向的键是 `(甲, 乙)` 和 `(乙, 甲)`，根本不是同一个间隙，锁不住对方那条尚未出现的记录。

把两行收成一行，并用插入去占锁。给关注表加一个整数标记 `link_flag`：1 表示编号较小的人关注了较大的人，4 表示较大的人关注了较小的人，5 表示两边都关注了。应用先比较两个用户编号，让较小的编号总是放在 `actor_id`。

较小编号一方执行：

```sql
begin;
insert into follow_edge (actor_id, target_id, link_flag)
values (801, 1560, 1)
on duplicate key update link_flag = link_flag | 1;

select link_flag
from follow_edge
where actor_id = 801 and target_id = 1560;
```

读到 1，说明只有这一方向，提交即可。读到 5，再插好友：

```sql
insert ignore into buddy_pair (user_lo, user_hi)
values (801, 1560);
commit;
```

较大编号一方把标志写成 4，冲突时用 `link_flag = link_flag | 4`。因为两边都把较小的编号放在前面，甲关注乙和乙关注甲打到同一条唯一键。后到的那句 `insert ... on duplicate key update` 会等先到的事务释放行锁，而不是各自插入一条。锁是插进去之后才拿到的，所以“行还不存在”不再让两个事务同时通过。

按位或保证重复调用不会把已有的位清掉。`insert ignore` 保证好友行重复执行时不会因为唯一键失败把事务打坏。两边都跑完，关注表里只有一行，`link_flag` 为 5，好友表里也有对应的一对。

这里使用唯一索引，和“能用普通索引就别用唯一索引”不冲突。那条建议的前提是业务保证不会有重复键，只想换取 change buffer。这个设计恰恰要数据库拒绝第二行，唯一约束是功能的一部分，必须建。

表名不要用 `like` 这种关键字。好友两边的列也要有唯一键，否则同一对人会插入多次。

## 小结

prepare 之后、binlog 之前崩溃，事务回滚。binlog 完整而 redo 尚未 commit，恢复时要提交，否则备库会多出这段变更。binlog 的完整性靠结尾事件和校验，两边用 XID 对齐。

只留 binlog 修不了数据页，只留 redo 则没有归档和复制。正常落盘来自缓冲池里的脏页；redo log buffer 是提交前攒日志的内存。

互相关注这类“先查再插”的并发漏洞，要用一个稳定的行序把两个方向收成同一条唯一键，让后到的事务堵在 `insert on duplicate` 上，再在锁内读取标志位。

## 值没变的 update，引擎做了没有

```sql
create table meter (
  meter_id int not null primary key auto_increment,
  reading int default null
) engine=InnoDB;

insert into meter values (1, 2);
update meter set reading = 2 where meter_id = 1;
```

客户端看到匹配 1 行、修改 0 行。内部有三种可能：

1. Server 读出来发现原值就是 2，直接返回，不调用引擎。
2. 调用了引擎，引擎发现值相同，不加锁也不写。
3. 引擎照样加锁、写新版本，该走的更新路径都走了。客户端的“修改 0 行”只是协议层在比较新旧值。

实际走第 3 种。可以用两个会话证明：会话 A `begin` 之后执行上面这句 `update` 并不提交；会话 B 再执行同一句。若前两种成立，B 不需要等锁。事实上 B 会被堵住，直到 A 提交或回滚。说明这句仍然在主键上加了排他锁，并走了写路径。

这样做是为了锁和复制的语义稳定。可重复读下，更新要靠引擎里的锁挡住并发写。statement 格式的 binlog 也会记下这句更新，备库必须执行同样的加锁和写入。若主库因为值相同就跳过，备库当前值若并不相同，两边会走出不同结果。客户端显示 Changed 为 0，只说明比较之后值没有差别，不说明引擎什么都没做。

## 计数表应该先插业务行还是先加计数

用一张计数表记录业务表有多少行。插入业务数据时要在同一事务里把计数加一。从并发看，两句谁先谁后？

先插业务行，再更新计数表。

计数那一行是热点，谁先锁它，谁就把锁持有到整个事务结束。若一上来就 `update` 计数，后面插入业务行的时间里，别的事务都在等这把行锁。先完成插入，最后再加计数，热点锁的窗口只剩事务末尾。

即使一张计数表存了多张业务表的行数，也不该因此把 `update` 提前。给表名加主键即可：

```sql
create table table_tally (
  table_name varchar(64) not null,
  row_cnt int unsigned not null,
  primary key (table_name)
) engine=InnoDB;
```

更新时带上 `where table_name = 'parcel'`，行锁落在这一行。不同业务表更新的是不同主键，彼此不加锁。会互相等待的，只是往同一张业务表插入的那些事务，而这正是两阶段锁要尽量缩短的那段。
