这篇笔记按后来重写过的版本整理。早期讲可见性时一次塞进的名词太多，读起来容易绕住。旧讨论里出现过 `up_limit_id` 这种内部字段名，下面不再用它做入口，只保留低水位、高水位和活跃事务数组这套说法，避免和旧稿对不上号。

可重复读下，事务启动时会建立一份 read-view。之后别的事务再改数据，这个事务里的普通查询仍应看到启动时的样子，像是不受外面影响。

可是更新没有这么超然。要改的那一行如果正被别的事务锁着，当前事务只能等。等锁拿到、真的去改的时候，它读到的又是哪一个版本？

先建一张只有两行的表：

```sql
CREATE TABLE shelf_cell (
  cell_no INT NOT NULL,
  hold_qty INT DEFAULT NULL,
  PRIMARY KEY (cell_no)
) ENGINE=InnoDB;

INSERT INTO shelf_cell (cell_no, hold_qty) VALUES (6, 14), (9, 40);
```

后面的实验都盯着 `cell_no = 6` 这一行，起始数量是 14。三个事务的时间关系是：

- 事务 C 没有显式开始和提交，一条更新自己就是一个事务，语句结束就自动提交。它把数量从 14 改成 19。
- 事务 B 先更新同一行，再查询。
- 事务 A 只做查询，而且查询发生在 B 的查询之后。

如果结果是 B 读到 27、A 读到 14，看起来就像两个人看的不是同一行。这一讲要解开的就是这个差别。实验默认 `autocommit = 1`。

还要先分清事务什么时候真正开始。单独的 `BEGIN` 或 `START TRANSACTION` 还不是起点，之后第一条访问 InnoDB 表的语句执行时，事务才启动，读视图也在那时建立。若希望一开始就拿到视图，用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。前一种是“第一条快照读时建视图”，后一种是“这条开始语句执行时就建视图”。

MySQL 里“视图”有两个意思，不要混：

- 一种是 `CREATE VIEW` 定义的虚拟表，查询时把视图定义展开再执行。
- 一种是 InnoDB 为实现 MVCC 准备的一致性读视图，没有单独的物理拷贝，作用只是规定“这个事务能看见哪些版本”。读已提交和可重复读都靠它。

前面讲隔离时，用撤销链说明过同一行可以有多个版本。这里把读视图拆开，专门对比普通查询和更新。

## 快照在 MVCC 里怎么工作

可重复读在事务开始时做一次“快照”，范围是整个库，不是某一张表。若库有 100GB，启动事务却很快，说明并没有把 100GB 复制一份。

每个事务有一个严格递增的 transaction id，在事务真正开始时向 InnoDB 申请。每一行也可以有多个版本。更新生成新版本时，会把当前事务的 id 写进行版本的 `row trx_id`，旧版本通过 undo 还能找回去。所以一行在逻辑上是一条版本链，而不一定是磁盘上并列的好几份完整行。

用另一行上的数量变化看这条链。最新版本记为 R4，数量 28，`row trx_id` 是 64。沿着撤销记录往回，可以算出 R3 的数量是 17、R2 是 9、R1 是 3。这三段箭头就是 undo。需要旧值时，从 R4 依箭头倒推，而不是事先把四个版本都存成独立的行。

某个读视图的低水位是 50、高水位是 60。它访问这一行时从 R4 看起：64 不小于高水位，属于视图建立之后才出现的版本，不可见；再算出 R3。若 R3 的 `row trx_id` 是 47，低于低水位，可见。于是这行在该事务眼里是 17。此时若还有事务正把 28 改成 35，只要新版本对这个读视图不可见，就不会和这次快照读冲突。

引擎怎样在不拷贝数据的前提下定义那份“全库快照”？可重复读的约定是：启动时已经提交的结果我认，启动之后别人提交的更新我不认；如果某个版本不认，就继续找它的上一个版本。自己更新产生的版本，自己总是认。

实现上，事务启动瞬间会做一份数组，装下当时所有已经开始、尚未提交的事务 id。数组中的最小值称为低水位。系统里已经分配过的事务 id 的最大值再加 1，称为高水位。数组加上高水位，构成这个事务的 read-view。

拿数据版本的 `row trx_id` 和这份视图比，可以分成三段：

1. 低于低水位：版本来自更早已经结束的事务，或者就是当前事务自己写下的，可见。
2. 不小于高水位：版本由视图建立之后才启动的事务生成，不可见。
3. 落在两道水位之间：若 id 还在活跃数组里，说明建视图时那个事务还没提交，不可见；若 id 不在数组里，说明那时已经提交，可见。

因此，视图建立之后别人再产生的版本，要么落在高水位之外，要么属于“当时仍活跃、后来才提交”的那一类，对这个事务都等于不存在。快照看起来是静态的。InnoDB 能在很短时间里建好快照，靠的就是“行本来就有多版本”，而不是拷贝全库。

回到 `shelf_cell` 的三个事务，解释 A 为什么读到 14。假设：

1. A 开始前，系统里只有一个活跃事务，id 为 580。
2. A、B、C 的事务 id 分别是 581、582、583，期间没有别的事务。
3. 这一行在三个事务开始前的 `row trx_id` 是 470，数量是 14。

A 启动时的活跃数组是 [580, 581]，低水位 580，高水位 582。B 的数组是 [580, 581, 582]。C 的数组是 [580, 581, 582, 583]。

和 A 的查询直接相关的写入只有两笔。C 先把 (6, 14) 改成 (6, 19)，最新版本的 `row trx_id` 变成 583，470 那个版本变成历史。B 再在当前值上把 (6, 19) 改成 (6, 27)，最新版本的 `row trx_id` 变成 582，583 退成历史。注意链的顺序跟事务 id 的大小不是一回事：B 的 id 更小，但 B 写得更晚，所以 582 排在链头，后面才是 583。

A 查询时，B 可能还没提交，(6, 27) 已经是链上的当前版本。这个版本对 A 必须不可见，否则就成了脏读。A 的读取过程是：

- 看到 (6, 27)，`row trx_id` 为 582，不小于高水位 582，不可见；
- 沿 undo 看到 (6, 19)，`row trx_id` 为 583，同样不小于高水位，不可见；
- 再往前是 (6, 14)，`row trx_id` 为 470，低于低水位，可见。

所以不管查询发生在两次更新的哪一段之后，A 在这个事务里看到的数量都是 14。这就是一致性读。

用事务 id 比较适合对着规则演算，口头判断则容易算错。可以收成三条，自己写的版本另外算，永远可见：

1. 版本还没提交，不可见。
2. 版本已经提交，但提交发生在读视图建立之后，不可见。
3. 版本在读视图建立之前就已经提交，可见。

用这三条再看 A： (6, 27) 属于第 1 条；(6, 19) 虽然提交了，但晚于 A 的视图，属于第 2 条；(6, 14) 早于视图，可见。后面都按这个时间顺序来判断。

## 更新逻辑

B 的更新如果也走一致性读，结果会对不上。B 的视图比 C 的提交更早，快照里这一行仍是 14，按快照加 8 应该得到 22，而不是实际写下的 27。

B 在更新前若先做一次普通查询，确实会得到 14。可是更新不能在历史版本上改。那样 C 已经提交的 +5 会被盖掉。所以 `hold_qty = hold_qty + 8` 必须基于当前已提交的 19 来算，得到 27，新版本的 `row trx_id` 是 582。

这里的规则是：更新都是先读再写，而这个读只能读当前最新的已提交版本，称为当前读。

B 随后再查询时，发现最新版本的事务 id 就是自己，属于自己的更新，直接可见，所以读到 27。

当前读不限于更新。普通查询一旦加锁，也是当前读。把 A 的语句改成下面两种之一，都会读到 B 写下的版本，数量是 27。前者加共享锁，后者加排他锁：

```sql
SELECT hold_qty FROM shelf_cell WHERE cell_no = 6 LOCK IN SHARE MODE;

SELECT hold_qty FROM shelf_cell WHERE cell_no = 6 FOR UPDATE;
```

再把 C 改成不立即提交的 C'。C' 已经生成 (6, 19)，锁还没放。B 的更新必须做当前读并且加锁，于是等到 C' 结束。这就是两阶段锁：锁在事务结束时才释放，而不是语句一结束就放。C' 提交后，B 才能在 19 的基础上继续加 8。

一致性读、当前读和行锁就串上了。可重复读的“反复读到同一结果”，指的是一致性读。事务要改数据时只能当前读；当前版本上的行锁被别人占着，就进入锁等待。

读已提交和可重复读的差别主要在视图的寿命：

- 可重复读只在事务开始时建一次视图，后面的普通查询都用它。
- 读已提交在每条语句执行前重新建视图。

因此在读已提交下，`START TRANSACTION WITH CONSISTENT SNAPSHOT` 留不住贯穿全事务的快照，效果和普通的 `START TRANSACTION` 一样。

仍用 C 立即提交、B 尚未提交的时间线。A 的那条查询若在读已提交下才创建视图，则：

- (6, 27) 还没提交，不可见；
- (6, 19) 已经提交，而且早于这条语句的视图，可见。

A 得到 19。B 查询自己的更新，得到 27。同一个事务里前后两条查询可以看见不同的已提交结果，这就是“不可重复读”被允许之后的样子。

## 小结

InnoDB 的行有多个版本，每个版本带自己的 `row trx_id`。事务或语句持有一份一致性视图。普通查询做一致性读，用 `row trx_id` 和视图决定该看链上的哪一节。

- 可重复读只承认事务启动前已经提交的数据，再加上自己的更新。
- 读已提交只承认这条语句启动前已经提交的数据，再加上自己的更新。

当前读总是读已经提交的最新版本，并且会加锁。

表结构做不到可重复读。结构信息没有行版本，也没有 `row trx_id`，只能走当前读。8.0 把数据字典放进了 InnoDB，以后是否给结构变更也做快照，是另一件事；就现有行为来说，改表对所有事务都是“看见最新定义”。

## 上期问题时间

上一讲问的是，怎样删掉一张大表里靠前的 12000 行。比较下来，在一个连接里循环执行小批量删除更合适。

一次执行 `DELETE FROM audit_evt LIMIT 12000`，单条语句占用时间长，锁持有得也久，大事务还会把备库的应用进度拉开。

在大约 24 个连接里同时各删 `LIMIT 500`，这些语句会互相等锁，等于自己制造冲突。

一个连接里分 24 轮执行 `DELETE FROM audit_evt LIMIT 500`，每轮事务短，锁很快释放，对复制也更友好。若业务要求删掉的是确定的那一段，还要加上有序条件，否则没有 `ORDER BY` 的限量删除，每一批命中的行并不稳定。
