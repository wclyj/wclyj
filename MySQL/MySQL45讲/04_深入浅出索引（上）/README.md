# 索引在解决什么问题，InnoDB 又为什么用 B+ 树

查询变慢时，最常听到的建议是“给那一列加索引”。加之前得先知道索引到底是什么结构，否则加完仍然走全表，或者把写入拖垮，都说不清原因。

索引要解决的事很单一：少翻数据就定位到行。一本按笔画排的字典，你不会从第一页线性翻到目标字；数据库也一样，不愿意为了一行把整张表读完。

索引模型不止一种。下面先比较三种基础结构各自擅长的访问，再看 InnoDB 为什么落在 B+ 树上，以及这棵树在插入、删除时要付出的维护成本。

## 三种常见模型

### 哈希

哈希把查找键算成一个槽位，值放进那个槽。碰撞时拉出链表，后写入的键挂在同一槽后面。

假设按工牌号查姓名。工牌 `E-2048` 和 `E-7731` 可能被哈希到同一个槽 17，查找 `E-2048` 时先算槽号，再沿链表比对。新增一名员工只是追加到某个槽，写入很便宜。

代价是槽与槽之间没有大小关系。要找工牌号落在 `E-2000` 和 `E-3000` 之间的所有人，只能把全部槽扫一遍。所以哈希索引适合等值查找，Memcached 和一部分 NoSQL 走的就是这条路。范围扫描不是它的场。

### 有序数组

把工牌号排成递增数组，等值和范围都很好。等值用二分，复杂度 O(log N)。范围则先二分到左端点（没有精确值就落到第一个更大的位置），再向右扫，直到超过右端点。

查询几乎是这三种里最漂亮的。更新很疼：在数组中间插入一条，后面的元素都要后移。因此它只适合不再改动的静态数据，比如已经封存的某一年普查名册。在线业务天天插入，这个结构撑不住。

### 搜索树

二叉搜索树要求左子小于父节点、右子大于父节点。查找、以及为了保持平衡而做的旋转，复杂度都是 O(log N)。

树可以是二叉，也可以是多叉。数据库更在意磁盘，而不是 CPU 指令。一棵 100 万个节点的平衡二叉树，高度大约 20。机械盘随机读一个数据块常常要 10 毫秒量级的寻道，查一行就可能变成 20 次随机读，延迟直接到几百毫秒。

少读盘的办法是让每个节点分叉更多，一次读入的一个数据页里放下大量键。分叉数 N 由页大小和键的宽度决定。InnoDB 里，一个整型二级索引页的分叉大约能到 1200。树高为 4 时，大约能放下 1200 的 3 次方，也就是 17 亿左右的键。根页通常常驻内存，10 亿行级别的整型索引，定位一个值最多再读 3 次盘；第二层也经常在缓冲池里，平均还更少。

N 叉树配合了“一次 I/O 尽量多带些键”的磁盘访问方式，所以成为引擎里的主流。跳表、LSM 树在别的引擎里也会出现，判断一个新数据库时，先看它的数据模型，再谈它适合点查、范围还是追加写。

把同一次“按工牌查人”放进三种结构里，差别主要在维护顺序要挪动多少数据。哈希算出槽号之后只沿着那一条链表比对，链上还有别的工牌就多比几次，它不必知道新工牌比旧工牌大还是小，所以追加很快，区间却无处下脚。有序数组用二分定位很快，左端点找到之后向右扫就能交出整个区间；可是在两个工牌之间插入一个新号码时，后面每一个元素都要向后挪一格，写入成本和数据量成正比。搜索树取中间：查找只走从根到叶子的一条路径，插入也只改这条路径附近的节点，再把树转平衡，不必搬动所有更大的键。

放到磁盘上时，节点大小要对齐一次读写的块。InnoDB 默认一页 16KB。非叶子页里装的是分隔键和子页地址，叶子页里才是索引键以及要交给查询的内容。同样一页，键越短，能挂出的子页越多，树就越矮。整型键大约能到 1200 路，是因为页头之外剩下的字节刚好放下这么多“键加指针”，不是算法写死了这个常数。主键若是很长的字符串，每页能装的键变少，树变高，定位一行要多读几次盘。后面会看到，这也是更倾向短主键的原因。

## InnoDB 怎么组织索引

InnoDB 的表按主键顺序存放，叫做索引组织表。每个索引各自是一棵 B+ 树。

看一张包裹表：

```sql
create table parcel (
  parcel_no int primary key,
  route_code int not null,
  receiver varchar(20),
  index (route_code)
) engine=InnoDB;
```

现有五行，`(parcel_no, route_code)` 分别是 `(10,8)`、`(30,15)`、`(50,22)`、`(80,41)`、`(120,63)`。

主键这棵树的叶子放整行：包裹号、路线码、收件人全在叶子上。这种索引也叫聚簇索引。

`route_code` 那棵树的叶子不放整行，只放路线码和对应的主键 `parcel_no`。非主键索引叫二级索引。

两种查找因此不一样：

- `select receiver from parcel where parcel_no = 80` 只搜主键树，叶子上直接有收件人。
- `select receiver from parcel where route_code = 41` 先在路线码树上找到 `parcel_no = 80`，再拿 80 去主键树取整行。第二次查找叫回表。

二级索引查询比主键查询多走一棵树。能用主键定位时，就少一次树搜索。

## 插入时树要做什么

B+ 树的叶子按键有序。沿用上面的数据：

- 插入 `parcel_no = 150`，比现有最大值还大，追加在最后一条后面即可。
- 插入 `parcel_no = 60`，要落在 50 和 80 之间，这一页里后面的记录得在逻辑上让出位置。

更贵的情况是目标页已经写满。假设这一页已经紧挨着放着 50、80、120 这几条附近的记录，再插入 60 时没有空位。B+ 树会新申请一个页，把大约一半记录搬过去，这叫页分裂。一次分裂既要写新页，也要改父节点里的分隔键，原来挤在一页里的数据散到两页，空间利用率大致掉到一半。随后若还按乱序主键继续插入，新页也会很快再裂，表空间膨胀会比行数增长更快。自增主键因为总是追加在最右叶，通常只在最右页写满时才分裂，不会把中间页反复拆开。

删除则可能让相邻两页都变得很空。空到一定程度，引擎把它们合并，可以看成分裂的逆操作。分裂和合并都是为了维持有序和页的填充率，不是业务能直接看见的语句，但会体现在写入抖动和表空间膨胀上。

## 主键用自增还是用业务号

很多建表规范要求主键写成自增：

```sql
parcel_no bigint not null primary key auto_increment
```

不显式给值时，引擎取当前最大值再加一。新行总是往尾部追加，既不用给中间记录腾位，也不容易把叶子页撑裂。用业务字段当主键，插入顺序往往是乱的，页分裂会频繁得多。

还有空间上的差别。每一棵二级索引的叶子都要带上主键。主键若是 18 位字符串的证件号，叶子里这一段大约要 20 字节；换成 `int` 只要 4 字节，`bigint` 是 8 字节。二级索引越多，这条差距被乘的次数越多。主键短，所有普通索引一起变瘦。

所以从追加写和空间两边看，自增主键通常更合适。

也有该用业务字段当主键的时候，条件很窄：

1. 整张表只有这一个索引；
2. 这个索引必须唯一。

这就是典型的键值查询：用唯一业务号查整行，没有别的二级索引。此时不存在“主键太长会撑大其他索引”的问题。若再套一层自增主键，每次查询都要先查业务号索引再回表。直接把业务号设成主键，一次树搜索就够了。

## 小结

哈希适合等值，有序数组适合只读，多叉 B+ 树同时照顾了范围查询和磁盘页。InnoDB 用索引组织表：主键叶子是整行，二级索引叶子是主键，所以二级索引查整行要回表。

自增主键让插入变成追加，并让所有二级索引更短。只有“单一且必须唯一”的键值表，才更适合把业务列本身当成主键。

## 重建索引时两句 alter 是否都合适

沿用 `parcel`。重建路线码索引可以写成：

```sql
alter table parcel drop index route_code;
alter table parcel add index (route_code);
```

重建主键如果写成：

```sql
alter table parcel drop primary key;
alter table parcel add primary key (parcel_no);
```

这两件事不要看成同一类操作。

删除或页分裂会在叶子页里留下空洞，页很占空间但装的行不多。重建二级索引会新建一棵树，按顺序把条目插进去，页被填满，索引变紧凑。上面第一对语句达到的就是这个目的，做法成立。

主键树就是表本身。删主键和加主键各自都会把整张表重做一遍。连着执行两句，第一句白做，数据被搬了两次。想把主键索引也压紧，用一次表重建即可：

```sql
alter table parcel engine=InnoDB;
```

它按当前行顺序重写聚簇索引，空洞被收掉，只搬一次。

## 上一讲留下的长事务问题

长事务占着锁和撤销日志不放，业务上要两边一起收。

应用侧：

1. 查有没有人把 `autocommit` 设成 0。测试环境打开 `general_log`，跑一遍正常业务流程，看会话是不是悄悄关掉了自动提交。框架若暴露了开关，把它调回默认的自动提交。
2. 去掉没有必要的只读事务。有的框架习惯用 `begin` / `commit` 把一切包起来，连几句纯查询也放进事务。没有一致性读需求时，这些空壳事务应该拿掉。
3. 按业务能接受的上限，用 `SET MAX_EXECUTION_TIME` 给单条语句封顶，避免一条走错索引的查询把事务拖成几分钟。

数据库侧：

1. 盯 `information_schema.innodb_trx`，事务时长超过阈值就告警或杀掉。
2. 可以用 Percona 的 `pt-kill` 按规则清理长事务。
3. 功能测试阶段把 `general_log` 留下，上线前先看出不该存在的长事务。
4. 5.6 及更新版本把 `innodb_undo_tablespaces` 设成 2 或更大。真出现大事务把回滚段撑大时，单独的 undo 表空间更好回收。
