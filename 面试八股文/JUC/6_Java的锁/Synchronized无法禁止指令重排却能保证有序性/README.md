# 为什么 synchronized 不禁止指令重排，却仍然保证有序

## 前言

这道题看起来只有一句，拆开之后至少要能说清下面几件事，否则答案会停在“加了锁就安全”：

- Java 内存模型到底约束了什么
- 并发里的有序性指哪一种顺序
- 编译器和 CPU 为什么会重排指令
- synchronized 是一把什么样的锁
- 可重入与互斥分别解决什么
- as-if-serial 语义保护的是谁
- 单线程观察与多线程观察的差别

## 标准解答

CPU 和编译器会为了流水线、缓存、指令级并行去调整语句的实际执行次序。这些优化一进到多线程，就可能让另一个线程看见“写还没发生，标志却已经变了”这类乱序，这就是有序性被破坏。

最直接的修法是像 volatile 那样插入内存屏障，告诉编译器和处理器：屏障两侧的指令不许交叉。synchronized 并没有走这条“全面禁止重排”的路。

Java 给所有优化加了一条底线，叫 as-if-serial：无论内部怎么重排，单线程看来，结果必须和源码顺序执行一致。编译器、运行时和处理器可以合作制造一种错觉——这段代码就是按书写顺序跑完的。因此只写单线程程序的人，不必担心重排把局部结果打乱，也不必担心自己线程内部的可见性。

synchronized 是 JVM 提供的互斥锁，也是可重入锁。线程进入被它保护的代码前必须先拿到监视器，离开时再释放。持有期间，别的线程进不来；同一个线程因为重入计数还可以再次进入。

互斥把临界区收成“同一时刻只有一个线程在执行”。as-if-serial 需要的前提恰好就是单线程观察。临界区里虽然仍可能发生不影响该线程结果的重排，但其他线程要么完全没进入，要么在解锁之后才进入，并通过锁的 happens-before 看见完整写入。于是从并发正确性上看，这段代码是有序的：后进入的线程不会看到半成品。

一句话：volatile 用屏障禁止重排；synchronized 用互斥把临界区变成单线程区间，再靠 as-if-serial 和锁的释放/获取顺序，保证别人看到的是一份已经完成的结果。
