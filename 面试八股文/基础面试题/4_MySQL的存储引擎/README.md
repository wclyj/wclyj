# MySQL 的存储引擎

## Mysql默认搜索引擎

5.5 之后，新建表默认用 InnoDB。更早的默认引擎是 MyISAM。

MyISAM 锁整张表，没有事务，也不支持外键。它把数据文件和索引文件分开，计数一类的全表统计可以很快，崩溃后的修复却比较笨重。

InnoDB 单表上的索引个数有上限，常见配置下是 16 个二级索引之外还要算上主键，具体以版本为准。和 MyISAM 比，差异集中在这几条：

- InnoDB 有事务。单条语句也会被当成一个自动提交的事务，来回提交会拖慢批量写入，所以成批修改应放在一次显式事务里。MyISAM 没有提交的概念，语句成功就改了盘
- InnoDB 能声明外键，把子表换成 MyISAM 会直接失败。外键有检查成本，高写入的表有时改在应用里校验
- InnoDB 的数据和主键长在一起，叫聚簇索引。按主键找行很快；走二级索引要先找到主键，再按主键找行，所以主键太宽，所有二级索引都会变宽。MyISAM 的索引叶子放的是行在数据文件里的位置，主键索引和二级索引互不包含
- 早期 InnoDB 没有内建全文索引，MyISAM 有。现在 InnoDB 也能做全文，但中文分词和相关性排序仍常交给专门的检索引擎

选引擎先看要不要事务和崩溃恢复。要，就用 InnoDB。几乎只追加日志、又能接受表锁时，才值得评估别的引擎。

## 硬盘

表和索引都在磁盘上的页里，内存只是缓存。一次随机读要等盘片或闪存寻址，数量级远高于内存访问。缓存把热点页留在内存里，所以同样的查询，第二次往往快很多。纯内存的键值存储省掉了这趟读盘，延迟才会差出一截。引擎再好，工作集如果远远大于缓冲池，瓶颈仍在磁盘。

## 索引

官方对索引的定位是：帮助存储引擎尽快找到行的数据结构。它不是表的副本那么简单，而是按查找算法组织好的目录。

实现上是一棵排好序的 B+ 树。名字里的 B 来自平衡，不是二叉树的“二”。平衡指的是叶子深度尽量一致，避免变成一条斜链。

## 检索原理

引擎在数据之外另存一棵树。结点里是键，叶子上挂着找到整行的办法。查找不再从第一行扫到最后一行，而是从根比较下来，复杂度跟着树高走。

例如按价格找书。没有索引时要看遍每一行。有了索引，根上放几个分隔键，决定去哪一棵子树，最后在叶子拿到主键或行地址。比较次数大约是树的高度，而不是行数。

## 聚簇索引和非聚簇索引

- 聚簇：行数据和索引放在一起，叶子结点就是行
- 非聚簇：叶子只保存指向行的地址或主键，行放在别处

InnoDB 里，主键那棵树是聚簇索引。在它之外再建的索引用主键当叶子里的“地址”，这些叫二级索引，包括联合索引、前缀索引和唯一索引。走二级索引拿到主键之后，还要再查一次主键树，这一步叫回表。

按主键等值查找时，从根走到叶子就能取出整行。按书名查找则要两步：先在书名那棵树上走到叶子，得到主键；再用主键到聚簇树取出价格、库存等其余列。

聚簇索引全表只有一棵，因为行只能按一种顺序紧挨着存放。行的物理相邻关系和这棵树的叶子顺序一致。应当先定下这棵树，再建立别的索引，否则后建聚簇索引会把行重排，其它索引也要跟着改。

如果建表时没写主键，引擎会挑一个非空唯一索引代替。连这个都没有，就生成一个隐藏的行号当聚簇键。已经用主键聚簇、又想换成别的列时，要先去掉主键，再建目标索引，最后把主键以二级唯一索引的形式加回来。日常更简单的做法是：主键就用紧凑的自增整数，别的列需要唯一时另建唯一索引。

MyISAM 两棵树的结点形状一样，叶子都是“键加上数据文件里的地址”。通过书名索引可以直接跳到行，不必再查主键树。地址是各自独立的，行的存放顺序和任何一棵索引都没有必然关系。

### 使用聚簇索引的优势

二级索引要查两次树，看起来比“叶子直接放地址”更费。收益在页和缓存，不在单次比较。

1. 同一片叶子页上挨着多行。按主键顺序扫描时，读进缓冲池的一页可以服务多行，下一行不必再读盘。主键和行一起进内存，走到叶子就能返回。

2. 二级索引只存主键。行被更新、页发生分裂时，只要维护聚簇树；二级索引里的主键如果没变就不必改。主键通常比“文件地址加若干列”更短，二级索引也更小，同样大的缓冲池能放下更多索引页。

一次读取以页为单位。InnoDB 默认一页 16KB，里面能放很多个键。落在同一页的多次查找只是内存操作。只有要找的键不在已缓存的页里，才会再发起读盘。人们有时把操作系统的 4KB 块和引擎的 16KB 页混在一起说，引擎真正申请空间时会凑满自己的页。

3. 非聚簇索引拿到的地址如果在磁盘上东一块西一块，范围扫描就会变成大量随机读。聚簇索引的范围扫描是顺着叶子链表走，顺序读更多，机械盘上差别尤其大。

4. 全表计数、大范围排序如果只依赖一块紧凑索引，MyISAM 那种“索引小、行另放”有时更省内存。事务和崩溃恢复仍然让大多数业务留在 InnoDB。计数不要养成 `COUNT(*)` 扫全表的习惯，可以另做汇总。

### 聚簇索引需要注意的地方

主键不要用无序的长字符串。新行的键会落在树的中间，引起页分裂，已经排好的页被反复拆开。自增整数总是追加在最右边，分裂少，碎片也少。

主键越宽，每个二级索引的叶子都要重复存一份。页里能放下的索引项变少，树变高，读盘次数跟着上升。

自增主键让逻辑顺序和物理顺序一致：相邻的号在叶子上也相邻，插入多半写在同一页的末尾。随机主键则不断把旧页拆开，缓冲池里挤满刚分裂、装得不满的页。

## B+树

B 树是多路平衡查找树，一个结点可以有很多孩子，用来把高度压矮。B+ 树是在它上面的调整：数据全部挪到叶子，叶子之间再串成链表。

口头说的 B-树就是 B 树，中间的短横不是减号。不要把它理解成“比 B 树少一点”的另一种结构。

## Mysql搜索引擎的发展之路

InnoDB 的索引不是一开始就长成现在的样子。按“为什么上一种不够用”来记，比死背定义清楚。

- 逐行扫描
- 哈希
- 二叉树
- 平衡二叉树
- B 树
- B+ 树

### 全部遍历

没有目录时，只能从第一行看到最后一行，行数上去之后每次查询都和表一样大。

### Hash

哈希把等值查找的平均代价压到常数级，插入和删除也是。平衡二叉树则是对数级。只看等值，哈希更快，为什么索引仍做成树？

等值可以：

```sql
select title from book where price = 48;
```

范围不行。哈希打散了顺序，相邻价格在表里并不相邻，下面这种条件只能退化成把条目扫一遍。

```sql
select title from book where price > 48 and price < 60;
```

排序、分组同样吃不到哈希的好处。树因为键是有序的，范围仍然是对数加上“沿着叶子走一段”。InnoDB 不提供用户可建的哈希索引；自适应哈希是引擎自己对热点页做的加速，不能在建表语句里指定。内存引擎才把哈希当主要结构，它同样不适合范围。

### 二叉树

特点：

- 每个结点最多两个孩子
- 左孩子更小，右孩子更大或相等

查找次数等于结点深度。六个结点的一棵小树，若深度分布是 1、2、2、3、3、3，平均查找长度大约是 `(1+2+2+3+3+3) / 6 = 2.3`。

问题是输入顺序。主键如果是递增插入，新结点永远挂在最右边，树退化成链表，查找回到 O(n)。数据库索引必须扛住这种递增主键，所以不能直接用会歪掉的二叉树。

### 平衡二叉树（AVL）

插入或删除后通过左旋、右旋把左右高度差拉回不超过 1，避免退化成链表。

它仍然不适合做磁盘索引：

- 每插一个键都可能旋转，维护成本高
- 一个结点只放一个键和两个指针，高度仍是对数底为 2 的那种，一亿行时树高二十多
- 磁盘一次按块读取。操作系统常见 4KB，一个二叉树结点远填不满，读一次盘只换回一个键

树有多高，最坏就要读多少次盘。把树从瘦高压成矮胖，才能减少读盘，而不是减少那一点内存里的比较。

### B树

多路的意思是一个结点里放很多键、分出很多孩子。有的教材用 2-3 树做入门，结点里可能是一个键两个孩子，也可能是两个键三个孩子。数据库里的阶数要大得多，目标是让一个结点刚好占满一页。

索引可能有几个 GB，不能整棵装进内存。查找时只把经过的那几个页读进来。页就是引擎管理磁盘的最小单位。

```sql
SHOW VARIABLES LIKE 'innodb_page_size';
```

默认能看到 16384。操作系统一次交换的块往往更小，引擎会申请一段连续空间，凑满自己的 16KB 再当作一页。一页里的键越多，同样的数据量树就越矮。

检索可以沿着一棵三层的树来想。根页在内存里，要找的键是 48：

- 读根页，发现 48 落在 30 和 70 之间，顺着中间那个指针走下去。这是第一次读盘
- 读到中间页，48 落在 40 和 55 之间，再顺着对应指针走。这是第二次读盘
- 读到叶子页，在有序的键里找到 48，取出后面的数据。这是第三次读盘

页内的键是有序的，可以用二分，但和读盘相比，内存里的比较几乎可以忽略。B 树比平衡二叉树矮，是因为每一层一次读盘能带回成百上千个键，而不是一个。

B 树的非叶子结点也保存记录。记录一大，每个结点能放的键就变少，树又会变高。范围扫描还得在树里来回上下，不能顺着底层直接走。

### B+树

B+ 树规定记录只放在叶子上，非叶子只留键和指针，用来导航。叶子之间用指针串起来，范围扫描变成顺着链表走。

于是三种需求一起被照顾到：等值仍从根往下，排序就是叶子的天然顺序，范围不用再中序遍历整棵树。

和 B 树相比：

- 非叶子不放整行，同样一页能放更多键，树更矮
- 叶子互相连接，遍历不必回到根
- 查找性能更稳，因为任何记录的深度都一样

非叶子只放键之后，假设一页能放下四个键和对应指针，扇出立刻变大。若把整行也塞进去，一页也许只能放两个键，层数就上去了。真实的页远不止四个键，这里只为了看清“键变小、孩子变多”。

## Mysql为什么是B+树

所有记录都按键的顺序放在同一层叶子上，上面的层只做路由。路由结点能装下的键远多于“键加整行”，三层往往就能覆盖百万到千万级的行。高度稳定在三层左右时，一次主键查找大约就是三次读盘，而且根页和第二层经常留在缓冲池里，实际读盘更少。

引擎的最小单位仍是页。页既可以放数据，也可以放“键加指针”。聚簇索引里，叶子页放的是整行；内结点放的是键和子页号。查找用二分在页内定位，再沿着指针进入下一页，直到叶子。

和 B 树的差别可以收成三条：

- 内结点只保留路由用的键
- 叶子串成双向链表，既能从某把钥匙向右扫一个范围，也能支持从左边顺序导出
- 记录都在叶子，所以每条记录的查找代价相同

从“能查”走到“适合放在磁盘上”，关键就是扇出和叶子链表。哈希缺范围，二叉树太高，平衡二叉树填不满一页，B 树把记录放在内结点里浪费了扇出。B+ 树把这几处都避开了。
