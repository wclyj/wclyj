# 方法区

## 前言

方法区是运行时数据区里最后一块需要单独说清的区域。从线程是否共享来看，堆和方法区由所有线程共用；程序计数器、虚拟机栈、本地方法栈则一人一份。

线程之间若只想共享“当前这条线程自己的上下文”，例如数据库连接或会话标识，用的是 `ThreadLocal`，它把数据放在线程对象能找到的结构里，不是放进方法区。方法区里放的是类一级的元数据，对所有线程都可见。

## 栈、堆、方法区的交互关系

访问一个实例时，三块区域同时出现。以 `Person p = new Person()` 为例：

- `Person` 这个类的类型信息在方法区，JDK 8 之后具体落在元空间。
- 变量 `p` 在 Java 栈的局部变量表里，它是一个引用。
- `new` 出来的实例在堆上，对象头里的类型指针再指回方法区中的类元数据。

所以方法调用在栈上推进，对象本体在堆上，类的结构信息在方法区。任何一块对不上，字段偏移和虚方法分派都无法完成。

## 方法区的理解

《Java 虚拟机规范》把方法区描述为堆的逻辑组成部分，同时允许实现不做收集、也不做压缩。HotSpot 给它另起了一个名字叫 Non-Heap，就是为了和真正存放实例的 Java 堆分开。阅读日志和监控时，应当把方法区看成堆之外的一块独立空间，不要用 `-Xmx` 去推断它的上限。

方法区主要保存已被加载的类型，堆主要保存这些类型的实例。两者都是线程共享的，也都在虚拟机启动时创建。物理内存上它们都可以不连续。容量可以固定，也可以按使用量扩展。

能装下多少类，由方法区的容量决定。类太多就会溢出。JDK 7 及以前的提示是 `java.lang.OutOfMemoryError: PermGen space`，JDK 8 及以后是 `java.lang.OutOfMemoryError: Metaspace`。典型场景包括：依赖的第三方包非常多、一个进程里部署了大量 Web 应用、运行期用反射或字节码框架不断生成新类。虚拟机退出时，这块内存随进程一起释放。

### HotSpot 中方法区的演进

JDK 7 及以前，HotSpot 用永久代实现方法区。JDK 8 起，永久代被元空间替换，元空间放在堆外的本地内存里。

方法区和永久代不是同一个概念。永久代只是 HotSpot 曾经的实现。规范没有规定方法区必须长什么样，JRockit 和 J9 就从来没有永久代。把类元数据放进一块有硬上限的永久代，后来被证明容易溢出：只要超过 `-XX:MaxPermSize`，进程就因类型信息而失败，和堆里还有多少空闲无关。

JDK 8 彻底去掉永久代，改成和 JRockit、J9 一样用本地内存实现的元空间。两者都是方法区的一种实现，差别在于元空间不占用虚拟机预先划给堆的那块保留内存。名字换了，内部布局也换了：字符串常量和静态变量的位置在 JDK 7 就已经调整，并不是等到元空间才一起搬走。

若方法区不能满足新的分配，虚拟机抛出 `OutOfMemoryError`。换成元空间之后，这个规定仍然有效，只是错误信息里的区域名字变了。

## 设置方法区大小与 OOM

方法区不必一开始就固定死。虚拟机可以按加载量把容量往上抬，直到碰到上限或操作系统给不出更多内存。

### JDK 7 及以前

永久代用两个参数：

- `-XX:PermSize` 设置初始容量，常见默认值大约是 20.75MB。
- `-XX:MaxPermSize` 设置上限。32 位客户端默认大约 64MB，64 位大约 82MB。

加载的类元数据超过上限，就会报 `OutOfMemoryError: PermGen space`。这两个默认值在不同小版本上可能有出入，以 `PrintFlagsFinal` 为准。

### JDK 8 以后

元空间用 `-XX:MetaspaceSize` 和 `-XX:MaxMetaspaceSize`。

`MetaspaceSize` 不是“启动时就提交这么多”，而是一个高水位。64 位服务端默认大约 21MB。一旦提交量触及高水位，会触发 Full GC，并尝试卸载不再存活的类，也就是加载它们的类加载器已经不可达。收集之后，高水位会按释放掉的量重新计算：释放得少，就在不超过 `MaxMetaspaceSize` 的前提下把水位抬高；释放得多，就把水位降低。

`MaxMetaspaceSize` 默认是 -1，表示不另设上限，只受本地内存剩余量约束。因此不写这个参数时，泄漏式的类生成会把机器内存慢慢吃掉，而不是停在一个很小的永久代上限上。真的没有本地内存时，仍然抛出 `OutOfMemoryError: Metaspace`。

高水位若设得太低，上述调整会反复发生，GC 日志里能看到连续的 Full GC。类很多的服务应当把 `-XX:MetaspaceSize` 提到一个更接近稳态占用的值，减少刚启动时的整堆收集。压缩类空间还有单独的上限，溢出时信息是 Compressed class space，它和 Metaspace 相关，但不是同一条错误。

### 如何解决这些 OOM

处理溢出或 heap space，第一步是用内存映像工具看转储，确认堆里的对象是不是业务还需要的。先区分泄漏和溢出：泄漏是大量对象已经不会再被使用，却仍从 GC Roots 可达；溢出是对象确实都还要活着，只是容量不够。

若是泄漏，就从泄漏对象反向走到 GC Roots，看它经过了哪个静态字段、哪条线程、哪个类加载器。类型和路径都清楚之后，才能定位到还在写入的那段代码。

若不是泄漏，对象都该活着，就检查 `-Xmx` 与 `-Xms` 相对物理内存还有没有上调余地，同时看有没有对象被持有得过久。方法区溢出则要换一套检查：是不是动态生成的类没有卸载，对应的类加载器是否被缓存。把堆调大解决不了 Metaspace 被类撑满的问题。

## 方法区的内部结构

不少教材把这块区域要记住的东西概括成四类：类型描述、各种常量、静态字段，以及编译器在运行期产出的机器码。HotSpot 的实际布局要再拆一层。类型元数据在元空间；静态字段从 JDK 7 起随 `Class` 对象放在堆上；JIT 生成的机器码放在独立的代码缓存里，并不塞进元空间。下面按“虚拟机必须记住什么”来列，更接近规范要求的内容。

### 类型信息

对每一个加载过的类、接口、枚举和注解，方法区至少要保存：

- 全限定名，也就是包名加类名。
- 直接父类的全限定名。接口和 `java.lang.Object` 没有父类。
- 修饰符，例如 public、abstract、final 的组合。
- 直接接口的有序列表。

### 域信息

每个字段都要记录，并且保留声明顺序。相关项包括字段名、字段类型、修饰符。修饰符可以是 public、private、protected、static、final、volatile、transient 的子集。实例字段的值不在这里，这里只有“有这样一个字段”的描述；值在堆上的实例里。

### 方法信息

每个方法同样按声明顺序保存：

- 方法名。
- 返回类型，没有返回值就是 void。
- 参数的个数和类型，顺序敏感。
- 修饰符，可以包括 public、private、protected、static、final、synchronized、native、abstract。
- 字节码、操作数栈深度、局部变量表规模。abstract 和 native 方法没有字节码。
- 异常表。同样不适用于 abstract 和 native。异常表的每一项包含起始位置、结束位置、处理代码的程序计数器偏移，以及被捕获异常在常量池中的索引。

这些信息是解释器和 JIT 的原料，不是某一条线程的运行现场。

### 非 final 的类变量

静态变量属于类，不属于某一个实例，随类的加载进入准备阶段，并在初始化阶段被赋予源码里的值。它们在逻辑上是类数据的一部分。即使没有任何实例，也可以通过类型名访问。所有实例看到的是同一份静态变量。

```java
public class TicketOrder {
    public static int sold = 3;
    public static final int CAP = 9;

    public static void greet() {
        System.out.println("ready");
    }

    public static void main(String[] args) {
        TicketOrder order = null;
        order.greet();
        System.out.println(order.sold);
    }
}
```

`order` 已经是 null，调用 `greet` 和读取 `sold` 仍然不会空指针。编译器把这两次访问都编成对类的静态访问，不需要对实例解引用。实例字段若这样访问则会失败。

### 全局常量

这里的全局常量指 `static final`。编译期就能确定的常量，例如基本类型和字符串字面量，会写进使用它的类的常量池，调用点往往直接内嵌这个值，甚至不触发声明类的初始化。若 `static final` 的右边是运行期才算出来的表达式，它仍然是静态字段，只是不能在编译期折叠。

### 运行时常量池与常量池

两者容易被当成同一个池。字节码文件里有一张常量池表，类被加载之后，虚拟机会在方法区里为这个类型建立运行时常量池，并把那张表的内容装进去。要看懂方法区，得先看 class 文件；要看懂运行时常量池，得先看 class 文件里的常量池。

### 常量池

一份合法的字节码除了版本、字段、方法和接口，还有常量池表。表里是各种字面量，以及对类、字段、方法的符号引用。

#### 常量池存在的理由

源码编译成字节码之后，字节码指令本身很短，但它依赖的名字可能很长：类名、方法描述符、字符串文本。这些数据若全部内嵌进每条指令，字节码会膨胀，相同的名字也会重复出现。常量池把它们收成一张表，指令只保存索引。动态链接时，运行时常量池再把符号引用解析成直接引用。

例如一个只打印固定文本的方法：

```java
public class Greeting {
    public void say() {
        System.out.println("ping");
    }
}
```

类文件并不大，里面却已经引用了 `String`、`System`、`PrintStream` 和 `Object`。方法再多一些，外部类型会更多。这些名字集中放在常量池，指令用编号去查。

#### 常量池里有什么

- 数值字面量。
- 字符串字面量。
- 类和接口的符号引用。
- 字段的符号引用。
- 方法的符号引用。

再看一段分配：

```java
public class AllocProbe {
    public static void main(String[] args) {
        Object item = new Object();
    }
}
```

对应字节码的核心是：

```text
new #2
dup
invokespecial #3
astore_1
return
```

`new` 的操作数不是类名文本，而是常量池第 2 项，那一项再指向 `java/lang/Object` 的名字。`invokespecial` 同样通过索引找到 `<init>` 的符号引用。

#### 小结

常量池是一张表。虚拟机指令靠索引找到要使用的类名、方法名、参数描述符和字面量。没有这张表，字节码里的操作数就没有意义。

### 类加载之后的常量池

这张池子划在方法区里。class 文件里的常量表在编译期生成，装的是字面量和符号引用；类加载之后，这些项进入方法区中对应类型的那一份池。

每个已加载的类或接口都有自己的一份。项通过索引访问，这一点和数组类似。池里既有编译期就确定的数字和字符串，也有要到解析阶段才变成真实地址的字段引用和方法引用。解析之后，符号引用被替换成可以直接使用的地址或偏移，后续执行不必反复按名字查找。

相对 class 文件常量池，运行时常量池多出来的能力是动态性。运行期间仍可以放入新的常量，例如 `String.intern` 把字符串纳入字符串表，`invokedynamic` 的调用点也会在运行期把引导方法的结果写回来。它因此比传统编译器的符号表更宽：符号表主要服务链接，运行时常量池还要服务字节码的持续执行。

创建这份池时，若需要的内存超过方法区还能给出的上限，虚拟机抛出 `OutOfMemoryError`。

## 方法区使用举例

用整数运算看栈帧如何引用运行时常量池。数字改成 840、40 和 21，商是 21，再加 21 得到 42。

```java
public class ArithmeticFrame {
    public static void main(String[] args) {
        int x = 840;
        int y = 40;
        int a = x / y;
        int b = 21;
        System.out.println(a + b);
    }
}
```

执行可以按栈的变化来读。

`sipush 840` 把 840 压进操作数栈，随后 `istore` 把它弹进局部变量表的一个槽。40 用 `bipush` 走同样的路径，进入另一个槽。两条 `iload` 把 840 和 40 重新压栈，`idiv` 弹出它们，压回商 21，再 `istore` 写进存放 `a` 的槽。21 同样进栈、进槽。

打印时不能只靠操作数栈。`getstatic` 要从运行时常量池取出 `System.out` 这个字段的解析结果，栈上才出现 `PrintStream` 引用。然后把 `a` 和 `b` 压栈，`iadd` 得到 42，`invokevirtual` 按常量池中 `println` 的方法引用做虚调用。调用期间，当前方法的程序计数器被设到 `println` 的字节码，返回地址被保存在栈帧里。`println` 结束后，计数器回到 `main` 里 `invokevirtual` 的下一条，最后 `return`。

程序计数器始终指向当前线程正在执行的字节码。方法返回要靠它找回调用点；线程被换下再换上，也靠它回到原来的指令，而不是靠方法区。方法区提供的是 `getstatic` 和 `invokevirtual` 要查的那张运行时常量池。

## 方法区的演进细节

只有 HotSpot 曾经有永久代。JRockit、J9 没有这个概念。方法区怎样实现，属于虚拟机自己的细节，规范不要求统一。

HotSpot 的变化可以收成一张表：

| 版本 | 方法区实现 | 静态变量与字符串表 |
| --- | --- | --- |
| JDK 6 与更早版本 | 永久代仍在 | 静态字段当时也放在永久代 |
| JDK 7 | 仍有永久代，但开始撤出 | 字符串常量池和静态变量挪到堆 |
| JDK 8 | 永久代移除，类型信息、字段、方法、运行时常量放在本地内存的元空间 | 字符串常量池和静态变量仍在堆 |

JDK 8 的元空间只受本地内存和 `MaxMetaspaceSize` 影响，不再有永久代那种很小的默认上限。

### 永久代被换掉的理由

HotSpot 与 JRockit 融合时，对方没有永久代，永久代就成了需要被拿掉的特殊实现。JDK 8 之后，类的元数据还在，只是搬到了一块与堆不相连的本地内存，这块区域叫元空间。

这么做主要有两个原因。

一是永久代的大小很难事先估准。动态加载一多，就会出现 PermGen space。真实的 Web 进程因为功能多、运行中不断生成类，曾经反复死在这个错误上，异常栈里能看到某个连接线程抛出 `OutOfMemoryError: PermGen space`。元空间默认以本地内存为界，不再被一个几十兆的上限提前截断。

二是永久代调优困难，而且容易把 Full GC 拉多。永久代满了就会促使整堆收集。元空间把类元数据移出堆的保留空间之后，日常的堆收集不必再为“类信息放在哪”支付同一种代价。类卸载仍然可能伴随 Full GC，但触发条件和容量模型变了。

规范对方法区的收集要求很松，甚至允许不实现。也确实有收集器在一段时期里不做类卸载，例如 JDK 11 当时的 ZGC。这个区域的回收成绩常常一般，尤其是类型卸载，条件很苛刻。它又不是可有可无：早期 HotSpot 因为没把这里收干净，出现过多次被当成泄漏的缺陷。

方法区里值得回收的主要是两类：常量池中已经没有引用的常量，以及不再使用的类型。

### 字符串表为何离开永久代

JDK 7 把字符串表从永久代挪到堆。永久代的回收很弱，常常要等到 Full GC，而 Full GC 又要等老年代或永久代真的不够才发生。应用里会创建大量字符串，表若只能在这种低频收集里被清理，永久代会先被耗尽。放到堆里之后，普通的年轻代和老年代收集就有机会处理那些只被字符串表弱引用着的项，回收及时得多。

### 静态变量存放在哪里

静态引用所指向的对象实例，始终在堆上。JDK 9 引入的 `jhsdb` 可以用来核对地址落在哪一代。实验的布局通常是：静态字段的“声明”随类型信息走，实例字段的值随对象走，局部变量在栈帧里。三个对象若都是 `new` 出来的，它们的数据地址会落在 Eden 的范围里。结论是：只要是被物化的对象实例，就在 Java 堆分配。

顺着静态字段找引用，会找到一个 `java.lang.Class` 实例，里面有对应的静态字段。规范的概念模型把与类相关的信息都放在方法区，但没有规定方法区的实现。JDK 7 及以后的 HotSpot 选择把静态变量和作为语言镜像的 `Class` 对象放在一起，存储在堆中。类型的元数据本身仍在元空间，`Class` 对象这个实例则在堆上。两者不要再合成“静态变量整份都在方法区”。

## 方法区的垃圾回收

有人认为元空间或永久代不做收集。规范的态度是宽松的：可以不要求在方法区实现垃圾收集。也存在未完整实现类型卸载的收集器，JDK 11 时期的 ZGC 就是例子，后来的版本才补上类卸载。

这个区域的回收效果通常有限，类型卸载尤其难，但有时必须做。早期 HotSpot 的一些严重缺陷，就是低版本没有把这里收干净，造成持续上涨。

方法区收集主要处理两部分：常量池里废弃的常量，以及不再使用的类型。

常量池里的常量大体分两类。字面量接近语言层面的常量，例如文本字符串、声明为 final 的常量值。符号引用是编译和链接用的名字，一类是类型的完整名字，一类是字段名加上类型描述，还有一类是方法名加上方法描述符。

HotSpot 对常量的策略比较明确：常量池中的某一项若已经没有任何地方引用，就可以回收。这和回收堆里的普通对象类似。真正难的是类。

判定一个类型“不再使用”，需要同时满足三个条件：

- 该类的所有实例都已被回收，堆上不存在该类及其任何子类的实例。
- 当初负责加载它的类加载器也已经不可达。除非加载器本身可以换掉，例如某些 OSGi、JSP 的重新加载，否则这个条件很难成立。应用加载器和系统加载器通常活到进程结束。
- 堆上那个代表该类的 Class 镜像已经没有引用，反射也找不到它。

三个条件都满足，虚拟机只是被允许卸载，不是必须卸载。是否回收类型，可以用 `-Xnoclassgc` 关闭。观察加载和卸载，可以用 `-verbose:class`，以及 `-XX:+TraceClassLoading`、`-XX:+TraceClassUnloading`。在大量反射、动态代理、CGLIB、运行期生成 JSP、或频繁创建自定义类加载器的进程里，必须让虚拟机具备类型卸载能力，否则方法区的占用会只增不减。

## 总结

方法区是线程共享的类型信息区。HotSpot 用永久代实现过它，JDK 8 起改为本地内存中的元空间。实例在堆上，引用在栈上，类结构在方法区，运行时常量池是方法区里供字节码索引的那张表。字符串表和静态字段指向的对象在 JDK 7 之后位于堆。收集器对这块区域并不积极，类卸载要同时满足实例、加载器和 `Class` 对象三个条件。

### 常见面试题

下面按公司做过的问法改写成检查点，用来确认自己能不能把区域职责说完整。

百度会要求直接讲运行时内存由哪些区域构成，每一块做什么。

蚂蚁金服常追问 JDK 8 对分代做了什么改动，五个运行时区域各自的职责，栈和堆的差别，堆的内部结构，以及为什么年轻代要有两块 Survivor。Eden 和 Survivor 的比例也经常被单独问。

小米的问题更短：内存怎么分区，为什么要分成年轻代和老年代。

字节跳动会让人讲 Java 的内存分区，或者把运行时数据区按线程私有和共享重新说一遍，并追问对象什么时候进入老年代。

京东关注内存结构、Eden 与 Survivor 的比例，以及为什么要有年轻代、老年代和当年的永久代。年轻代内部为什么又要拆成 Eden 和 Survivor，需要用复制算法来回答。

天猫要求内存模型细到每一块放什么，并问 JDK 8 改了哪一部分。回答应当落到永久代移除、元空间、字符串表和静态变量的位置，而不是只说“把永久代换成了元空间”这一句。

拼多多的问法是区域有哪几块、每块的作用是什么。

美团会问内存怎样分配，永久代里会不会发生收集，以及为什么要有年轻代和老年代。永久代或元空间会收集，只是频率低、类卸载条件严。
