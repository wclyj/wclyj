# 执行引擎

## 它处在什么位置

执行引擎位于虚拟机的下层。解释器、即时编译器以及垃圾收集器，都从这里介入“字节码怎样被跑起来”。收集器管的是内存死活，解释器和即时编译器管的是指令怎样变成处理器能执行的动作。

虚拟机相对物理机而言：两边都能执行程序，但物理机一侧依赖的是芯片、高速缓存、该平台指令集以及操作系统，虚拟机这一侧则是一段软件。因此它可以规定一套硬件并不直接认识的指令格式，再在运行时翻译成当前平台的机器码。Java 字节码就是这套格式。

虚拟机的首要工作之一是把字节码装进自己的运行时。字节码不能交给操作系统当成本地可执行文件，因为它不是某一种 ISA 的机器指令，里面是操作码、常量池索引、符号引用和辅助属性。要让程序真正动起来，执行引擎必须把这些操作码解释执行，或者编译成当前平台的机器指令。它扮演的是翻译，而不是业务逻辑本身。

### 执行引擎的工作流程

下一拍执行哪条字节码，完全由当前线程的程序计数器决定。一条指令做完，计数器被改成后续地址，解释器或已编译代码再按新地址继续。

方法执行期间，引擎还会顺着局部变量表和操作数栈里的引用，找到堆上的实例；再顺着对象头里的类型指针，找到元空间中的类元数据，完成字段偏移计算和虚方法分派。从外面观察，各家虚拟机这块部件吃进去的都是字节码，中间完成与规范等价的计算，吐出来的是状态变化和返回值。

## Java 代码的编译和执行过程

源码要变成处理器能跑的指令，中间有好几段，并不都发生在虚拟机里。

生成 `.class` 的那一段由前端编译器完成，和运行中的 JVM 无关。类加载、字节码校验、解释执行、即时编译，才是虚拟机要负责的部分。

前端大致经过词法分析、语法分析、符号表填写、语义检查与注解处理，最后吐出字节码。后端则是：类被装入后，解释器可以立刻逐条执行；热点积累起来之后，即时编译器把整段方法或一段循环变成机器码，后续调用直接走机器码。

解释器和编译器因此是并存的两条路径，而不是二选一的历史阶段。

### 什么是解释器

虚拟机启动之后，可以按规范把字节码一条条翻译成当前平台的本地指令并立刻执行。翻译结果通常不长期保留，下一次遇到同一条字节码，解释器会再做一遍对应的模板或例程。优点是第一条指令几乎不用等待。

### 什么是 JIT 编译器

JIT 是 Just In Time Compiler，即时编译器。它不是把 `.java` 直接变成机器码的 javac，而是在运行期把已经是字节码的方法编译成与本机相关的机器码。编译需要时间，但产物可以反复执行，单元成本被摊薄。

### 为什么说 Java 是半编译半解释

JDK 1.0 的年代，把 Java 说成“解释执行”大体成立。随后出现了在运行期把字节码收成机器指令的编译器。当下的 HotSpot 在跑 Java 时，默认把两条路叠在一起：冷代码解释，热代码编译。编译结果可以缓存在代码缓存里，同一方法的后续调用不必再次解释。所以“半编译半解释”描述的是运行期的混合策略，不是源码到字节码那一步。

## 机器码、指令与汇编

### 机器码

用二进制编码的处理器指令叫做机器指令，全部由这种指令构成的程序就是机器语言。处理器能直接取它执行，因此在同一颗 CPU 上它最快。它和人的语言距离远，难读也难改，写错一位就是另一条指令。机器指令还绑死在具体 CPU 上，换一种微架构，编码就可能变。

### 指令

机器码全是 0 和 1，于是人们给固定的位模式起了助记名字，例如 `mov`、`add`、`inc`。这就是指令。同一条助记符在不同硬件上可能对应不同的机器码，因为寻址方式和操作码布局并不统一。

### 指令集

一种平台所支持的指令全体，叫做该平台的指令集。常见的 x86 指令集服务 x86 架构，ARM 指令集服务 ARM 架构。Java 字节码可以看成虚拟机自己的指令集，和这两种硬件指令集都没有一一对应关系。

### 汇编语言

助记符仍然不好组织程序，汇编语言就在指令之上加了标签、符号地址和少量伪指令。不同硬件的汇编对应不同的机器指令集，汇编器负责把助记符翻成目标机器码。处理器只认机器码，汇编文本必须先被汇编，才能执行。

### 高级语言

为了让人用更接近问题域的语法写程序，又出现了高级语言。机器执行它们之前，仍要把文本变成指令。承担这件事的程序，要么是解释器，要么是编译器。许多编译器并不直接从高级语言跳到机器码，而是先降到汇编或某种中间表示，C 和 C++ 的工具链就是这样。

### C 与 C++ 源程序如何变成机器码

这条工具链通常分成编译和汇编两段。编译读入字符流，做词法和语法分析，生成功能等价的汇编。汇编再把汇编文本翻译成目标文件里的机器指令，链接器最后把多个目标文件和库拼成可执行映像。Java 的 javac 停在字节码，不负责这最后一跳；最后一跳留给每个平台上的虚拟机。

### 字节码

字节码是中间形态的二进制，比机器码更抽象，必须再经解释或编译才能变成某个 CPU 的指令。它的目的就是让程序正文与具体硬件脱钩：编译器把源码收成字节码，特定平台的虚拟机再把字节码变成可以执行的本地指令。Java bytecode 是最常见的一种。也有人会问，为什么不让 javac 直接产出当前机器的机器码。直接产出会把发行物绑到一种操作系统和一种指令集上，体积也会因为具体寻址模式而变大，运行期再按真实剖面做优化的机会也没了。字节码把“写一次”和“在哪跑”拆开，所以多这一层是有意的。

## 解释器

虚拟机早期为了跨平台，刻意不在发布前做静态的本地编译，而是在运行时逐条解释字节码。解释器就是这个运行时的翻译员：读一条操作码，完成规范规定的栈和局部变量变化，再按程序计数器去翻译下一条。

源文件先变成字节码而不是某台机器的可执行文件，原因已经在上一节说过：同一份类文件要能在不同 ISA 上运行。

### 解释器的两类实现

历史上出现过两套解释执行方式。早期的字节码解释器完全用软件模拟操作数栈，每条指令都走一段通用分派逻辑，调用开销很大。现在 HotSpot 使用的模板解释器为每条字节码准备一个模板函数，模板里直接放出这条字节码对应的机器码片段，分派成本低一截，解释器才有了能用的性能。

在 HotSpot 源码结构里，解释器主要由两块配合：Interpreter 模块实现解释器的核心逻辑，Code 模块管理运行期生成的本地指令，模板机器码也放在这套代码缓存机制里。

### 现状

解释器实现相对直接，Python、Ruby 等语言的早期实现也以解释为主。今天如果一门语言只能解释、不能把热点变成机器码，性能谈话里就会吃亏，也常被拿来和 C/C++ 对比。虚拟机的回应是即时编译：不要在每次调用时重复解释，而是把整个方法编译成机器码，之后只跑机器码。执行时间里的大头因此被换掉。

解释执行并没有因此被删掉。它仍然是冷启动阶段的执行方式，也是编译假设失败时退回的路径。中间表示加解释器，是后来许多语言运行时的共同骨架。

## JIT 编译器

### Java 代码的两条执行路径

第一条路：源码编译成字节码，运行时由解释器转成机器行为。第二条路：运行中把热点方法编译成机器码再执行。现代 HotSpot 两路都留着，并用热点探测决定谁上场。

HotSpot 是高性能虚拟机里很有代表性的一款，架构就是解释器与即时编译器共存。两边互相补位：解释器省掉编译等待，编译器负责稳态吞吐。比较的是“现在花时间编译”和“继续解释”哪一个更合算。

经过这种混合，Java 在长时间运行的服务里，性能已经可以和 C/C++ 放在同一量级讨论。差距更多来自算法、分配速率和收集停顿，而不是“因为解释所以必然慢一个数量级”。

### 既然有 JIT，为何还留着解释器

JRockit 曾经去掉解释器，字节码全部交给即时编译器。它主要部署在服务端，可以忍受启动后一段时间的编译，换取之后更高的峰值。桌面或短生命周期进程若照搬，启动阶段会把时间耗在编译上，用户先看到的是慢。

所以要分清两端：进程刚起来时，解释器马上能跑，没有编译延迟；编译器要先观察、再优化，本地代码生成之后单次执行才更快。服务端可以偏编译，在意启动时间的场景就需要两者并存，找一个平衡点。

虚拟机启动后先解释，不必等全部方法编译完。随着运行，越来越多的热点变成本地代码，稳态效率上去。解释器还有一个角色：编译器做过激的优化，比如错误的内联假设，可以用去优化退回解释，解释器是这扇“逃生门”。

### HotSpot 的实际执行方式

默认路径就是上面说的混合。启动先解释。运行时间变长之后，热点探测把值得编译的字节码交给 JIT，换更高的执行效率。不是所有方法都会被编译，只编译被判定为热的那些。

### 冷机与热机

同一台机器，代码缓存已经热起来之后能承受的流量，高于刚启动、仍在解释执行时的流量。按热机容量把流量一次性切到冷进程上，进程可能在 JIT 完成之前就被打满，表现为超时甚至假死。

发布因此要分批。每批机器占集群的比例必须留下余量，常见做法是单批只占一小部分，给新进程预热。曾经有故障把整个集群只划成两批：热机时一半容量勉强够，但新起来的一半还没有完成热点统计和编译，解释执行扛不住那一半流量，刚发布成功的机器随即大面积超时。这个事故说明 JIT 不是日志里的装饰，它决定冷启动之后吞吐要多久才能回到基线。

### 三种“编译期”

Java 口语里的“编译”其实指向三段互不相同的过程。

- 前端编译：把 `.java` 收成 `.class`。javac，以及 Eclipse 使用的增量编译器 ECJ，都属这一段。
- 后端的运行期编译：JIT 把字节码收成机器码。HotSpot 里是 C1 和 C2。
- 运行前的静态编译：AOT，Ahead of Time，直接产出本地代码。历史上的 GCJ、Excelsior JET 属于这一类。

三段可以同时存在于一个工程的不同阶段，不能拿 javac 的耗时去代表 JIT 的耗时。

### 热点探测

被多次调用的方法，或者方法里次数很多的循环，都叫热点代码，JIT 会把它们编译成机器码。循环的编译发生在方法还在栈上的时候，叫做栈上替换，英文是 On Stack Replacement，简称 OSR。方法还没返回，循环体的后续迭代就已经改走编译后的本地代码。

次数必须有阈值，否则所有方法都会在第一次调用时付编译成本。HotSpot 经典的探测手段是计数器，而不是定时采样。每个方法带两个计数：方法调用计数器 Invocation Counter，以及回边计数器 Back Edge Counter。前者统计方法被进入的次数，后者统计字节码向后跳转的次数，也就是循环回绕。

### 方法调用计数器

调用计数器统计方法进入了多少次。在不启用分层编译的前提下，Client 模式的默认阈值大约是 1500，Server 模式大约是 10000。超过阈值就提交编译。可以用 `-XX:CompileThreshold` 改这个数。

调用发生时，先看这个方法有没有已经编译好的版本。有则走本地代码。没有则把调用计数加一，再看调用计数与回边计数之和有没有越过阈值。越过了，就向编译器提交一个编译任务。编译通常异步进行，当前这次调用仍可能继续解释，等编译完成，后续调用才切换。

JDK 8 以及之后的 HotSpot 默认开启分层编译，触发条件改由各层阈值控制，`CompileThreshold` 不再是唯一门槛。查一个具体进程时，以 `-XX:+PrintFlagsFinal` 里的分层参数为准。

### 热点衰减

若不另做设置，调用计数器记的不是进程生命周期内的绝对次数，而是一段时间里的相对热度。过了半衰周期，次数仍不足以触发编译，计数会被减半。这个过程叫计数衰减，那段时间叫半衰周期。名字借自物理里的半衰期，这里只是一个衰减时间窗，和同位素无关。

衰减动作搭在垃圾收集的时机上顺手做。`-XX:-UseCounterDecay` 可以关掉衰减，计数变成绝对次数，进程跑得够久时，大多数被调用过的方法最终都会被编译。`-XX:CounterHalfLifeTime` 用来设置半衰周期，单位是秒。

### 回边计数器

回边计数器统计方法体内循环执行了多少次。字节码里控制流往回跳的那条边叫回边。单独统计它，是为了让一个调用次数不多、但内部循环极热的方法也能触发 OSR，而不必干等调用计数。

回边阈值由虚拟机根据运行模式计算，和编译阈值、堆栈上是否已经有 OSR 版本有关。循环每绕一圈，计数增加；达到阈值且还没有可用的本地代码时，提交 OSR 编译。编译完成之后，解释器在回边处把执行权交给本地代码，局部变量和操作数栈的状态被映射进编译后的帧。

### 用参数选择执行方式

HotSpot 默认是解释器加即时编译器的混合模式。也可以用启动参数把策略说死：

- `-Xint`：完全解释。不生成 JIT 代码，适合对照基线，不适合当生产配置。
- `-Xcomp`：尽量把方法都编译后再执行。编译失败或需要去优化时，解释器仍会补位。启动会更慢。
- `-Xmixed`：混合模式，也就是默认值。

生产环境保持混合，再用预热和分层编译解决问题，而不是全局改成纯编译。

### C1 与 C2

HotSpot 内置两套 JIT。Client Compiler 简称 C1，Server Compiler 简称 C2。

- `-client` 让虚拟机偏客户端，使用 C1。C1 只做较快、较稳的优化，编译时间短，代码质量中等。
- `-server` 使用 C2。C2 优化更激进，编译更慢，生成的代码在稳态下更快。C2 本身用 C++ 写成。

64 位 JDK 默认就是服务端风格，并叠加分层编译，所以很少再手动写 `-server`。

### 两种编译器的优化侧重

C1 的典型手段包括方法内联、去虚拟化、局部冗余消除。内联把被调方法的字节码嵌进调用点，省掉一次栈帧和跳转。去虚拟化是在能证明只有一个实现类时，把虚调用变成可以直接内联的调用。冗余消除则在运行路径上折掉不会执行或重复计算的部分。

C2 在更大的范围内做优化，逃逸分析是底座。基于“对象没有逃出当前线程或当前方法”的结论，它可以做标量替换：用若干标量代替一个聚合对象的字段。教材里还会写栈上分配，意思是未逃逸对象不必进堆；HotSpot 的实际落地主要是标量替换，字段直接变成寄存器或栈槽，而不是在栈上放一个带对象头的完整实例。同步消除则是去掉不可能被其他线程观察到的锁，常见于锁对象没有逃逸的 `synchronized` 块。

### 分层编译

分层编译把两条编译器接成一条流水线。代码先解释执行，此时可以不带性能监控。调用变热后进入 C1，快速生成带少量优化的机器码，并打开计数和类型剖面。剖面足够之后，C2 再按这些信息做激进优化，产出最终的稳态代码。若激进假设后来被打破，例如出现了新的实现类，虚拟机可以去优化，退回解释或较低层。

Java 7 之后，一旦以服务端方式运行，默认就会打开分层编译，由 C1 和 C2 分工，而不是只留一个编译器。Java 8 起这就是普通安装包的默认行为。

### 小结

同一种机器码，JIT 产物的稳态速度通常高于解释执行。C2 的启动和编译都比 C1 慢，系统进入稳定流量之后，C2 的代码又通常快于 C1。分层编译用 C1 填中间这段空白，避免“要么解释、要么干等 C2”的两极。

### AOT 编译器

JDK 9 引入过实验性的提前编译工具 jaotc，借助 Graal 把类文件编译成机器码，放进动态共享库。路径可以写成：

```text
.java -> .class -> jaotc -> .so
```

AOT 和 JIT 相对：JIT 发生在进程已经跑起来之后，AOT 发生在进程启动之前。虚拟机若直接装入已经编译好的二进制库，第一次请求就不必等待编译预热，能减轻“第一次调用特别慢”的感觉。

限制同样明显。每个操作系统和每种指令集都要单独出包，“一份字节码到处运行”被打破。链接期的动态性下降，编译时看不见的类无法被提前收进来。早期实现还只覆盖 Linux x64 上有限的基础模块。jaotc 只在中间若干 JDK 里作为实验功能存在，随后被移除。今天若要在启动前得到本地代码，更常见的是独立的本地镜像工具链，而不是那个实验命令。

### Graal

从 JDK 10 起，HotSpot 可以通过 JVMCI 接入 Graal 编译器，用它替代 C2 的角色。它在几年里把生成代码的质量追到了与 C2 可比的程度，但在标准 HotSpot 里长期带着实验性质，需要显式打开：

```text
-XX:+UnlockExperimentalVMOptions -XX:+UseJVMCICompiler
```

是否在某个具体 JDK 构建里可用，要看该构建有没有带 Graal。打开之后，分层编译的顶层可以由 Graal 承担，解释器和 C1 的角色不变。
