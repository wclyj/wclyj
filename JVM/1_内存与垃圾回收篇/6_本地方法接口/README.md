# 本地方法接口

## 它指的是什么

本地方法是声明在 Java 里、实现却落在 Java 之外的方法。方法体通常由 C 或 C++ 提供，经 JNI 注册给虚拟机。这个思路并不专属于 Java：C++ 也可以用 `extern "C"` 按 C 的调用约定去链接另一门语言写出的函数。用一句话概括：native 方法的签名是 Java 的，可执行的机器码不是 Java 编译器生成的。

书写上它很像接口里的方法，只有签名、没有 Java 方法体，因为真正的指令在动态库里。本地接口的设计目的，是让 Java 运行时能够接住其他语言已经写好的能力，最初主要是为了吃进 C 和 C++ 的代码。

声明时可以带上绝大多数方法修饰符，唯独不能和 `abstract` 一起用。抽象方法要求子类给出 Java 实现，native 则表示实现在虚拟机外部，两者语义冲突。下面换一组签名示意合法组合：

```java
public class NativeHooks {
    public native void openSensor(int channel);
    public static native long readClock();
    private synchronized native float scale(Object sample);
    native void pushSamples(int[] data) throws Exception;
}
```

`native` 可以和 `public`、`static`、`synchronized`、`private` 并存，也可以声明受检异常。编译后的字节码里这些方法带有 `ACC_NATIVE`，没有 Code 属性。

## 为什么使用 Native Method？

Java 的可移植和内存安全让业务代码写起来省事，可一旦任务落到硬件寄存器、特殊系统调用，或者某一小段必须压到接近 C 的开销，纯 Java 要么做不到，要么代价过高。本地方法就是这条退路。

### 与 Java 环境外交互

运行中的 Java 程序并不是封闭的。它要问操作系统要文件描述符、网络缓冲、线程优先级，偶尔还要和设备驱动交换状态。本地方法把这些交互收成一个窄接口：调用方只看见 Java 签名，不必自己处理调用约定、指针宽度和结构体对齐。这是它存在的主要理由。

### 与操作系统交互

虚拟机支撑着语言和核心类库，自身却不是一个完整操作系统。解释器负责字节码，一批本地库负责和内核打交道。即便标准库的大部分类用 Java 写成，边界上仍会落到 native。虚拟机的若干底层模块本身就是 C++。当 JDK 没有封装某项操作系统能力时，应用也可以自己写 JNI，直接使用那项能力。

### Sun 的实现路径

早期 Sun 的解释器以 C 实现，因此和普通 C 程序一样能调用系统 API。核心类库多数是 Java，再通过少量本地方法探出运行时。以线程优先级为例：`java.lang.Thread` 里对优先级的 Java 封装，最终会进到同类中的一个本地入口，由虚拟机用 C 实现，再映射到当前平台的调度接口。在 Windows 上，这条路径会落到系统的优先级 API。有的本地方法由虚拟机直接提供，更多则放在外部动态库里，启动时由虚拟机加载并按名字绑定。

## 现状

业务系统里手写 JNI 已经少见。跨进程、跨语言的需求，多数改用套接字、HTTP 或 RPC，不必把 C 指针引进同一个进程。本地方法仍留在两个地方：一是 JDK 自己的底层，例如 I/O、压缩、部分数学库；二是必须驱动硬件或嵌入现有 C 库的场景，例如工业设备、本地推理库。这些场景继续用 JNI 或更新的 Panama 外部函数接口，而不是在普通企业工程里随手声明 native。
