# 垃圾回收相关概念

## 如何理解 System.gc()

默认情况下，`System.gc()` 和 `Runtime.getRuntime().gc()` 是同一次调用的两种写法，会向虚拟机建议做一次整堆收集，年轻代和老年代都在考虑范围内，试图把已经不可达的对象所占空间还回去。

这个建议带有免责声明：规范不保证收集器立刻运行，更不保证在调用返回前已经完成。具体怎么响应，由虚拟机实现决定。常规业务里回收应当自动发生，不必手写。编写性能基线、希望两轮测量之间把堆清干净时，才偶尔调用它。显式请求还会拉长停顿，生产代码里更常见的是用 `-XX:+DisableExplicitGC` 把它关掉。某些收集器还可以用额外参数，把这次显式请求转成并发周期，而不是一次完全停顿的整堆收集。

下面的小类只用来观察“建议”会不会赶上终结方法。类名换成 `HintGcDemo`，避免和常见示例撞名。

```java
public class HintGcDemo {
    public static void main(String[] args) {
        new HintGcDemo();
        System.gc();
        // System.runFinalization();
    }

    @Override
    protected void finalize() throws Throwable {
        System.out.println("HintGcDemo.finalize");
    }
}
```

有时能看到那行输出，有时看不到。`System.gc()` 只是建议。若还调用 `System.runFinalization()`，虚拟机会更积极地去跑那些已经失去引用、正在排队的终结方法，但这仍然不是“立刻回收内存”的保证。

### 用手动收集观察不可达对象

局部变量槽会不会继续把数组留在根上，可以用一组对照看出来。数组改成 8MB，五个方法的差别只在引用还活着没有。

```java
public class SlotLifetimeLab {
    public void stillOnStack() {
        byte[] buf = new byte[8 * 1024 * 1024];
        System.gc();
    }

    public void clearedBeforeGc() {
        byte[] buf = new byte[8 * 1024 * 1024];
        buf = null;
        System.gc();
    }

    public void blockEndedSlotKept() {
        {
            byte[] buf = new byte[8 * 1024 * 1024];
        }
        System.gc();
    }

    public void slotReused() {
        {
            byte[] buf = new byte[8 * 1024 * 1024];
        }
        int marker = 42;
        System.gc();
    }

    public void framePopped() {
        stillOnStack();
        System.gc();
    }

    public static void main(String[] args) {
        new SlotLifetimeLab().blockEndedSlotKept();
    }
}
```

- `stillOnStack`：局部变量还指着数组，它是可达的。年轻代收集不会把它当垃圾；它体积大，还可能直接进老年代或在随后的整堆收集里被保留。
- `clearedBeforeGc`：调用收集前已经把变量写成 null，数组不可达，这一轮可以收掉。
- `blockEndedSlotKept`：花括号结束，Java 源码里的名字消失了，但 javac 往往不会立刻把局部变量表里的槽清掉。槽里仍是那个引用，收集器必须把它当根。所以这次调用经常收不掉数组。
- `slotReused`：后面的 `marker` 复用了同一个槽，引用被覆盖，数组才变得不可达。
- `framePopped`：`stillOnStack` 返回后栈帧弹出，数组的唯一引用随之消失，外层再触发的收集才能把它收走。

看字节码时用 `javap -c -v` 对照局部变量表，比只看源码可靠。不同版本的 javac 对槽复用的策略可能不同，判断标准始终是：收集发生时，栈上还有没有指向它的槽。

## 内存溢出

和泄漏相比，溢出更好理解，但它同样会把进程打崩。收集器一直在进步，所以除非占用涨得比回收更快，否则不容易看到 `OutOfMemoryError`。多数时候，年轻代收集、老年代收集层层做过，实在不够就来一次独占式的整堆收集，把能还的空间尽量还出来。

文档对这个错误的含义是：没有足够的空闲内存，而且收集器也提供不出更多。没有空闲，通常说明堆不够用。原因可以分成两类。

一是堆上限本身偏小。可能真有泄漏，也可能只是要处理的数据量很大，却没设 `-Xms` / `-Xmx`，或者设得过低。这两项就是用来调整堆的初始容量和最大容量的。

二是代码里存在大量大对象，而且它们仍被引用，收集器不能动。例如一个长生命周期的列表不断追加字节数组。

老版本 JDK 的永久代有硬上限，而且对永久代的回收不积极，常量池和不再使用的类都不容易卸掉。运行期大量生成类时，永久代溢出很常见，字符串 `intern` 把永久代撑满也是同一类问题。异常信息是 `java.lang.OutOfMemoryError: PermGen space`。

元空间取代永久代之后，类元数据改放本地内存，同类问题的提示变成 `java.lang.OutOfMemoryError: Metaspace`。直接内存不足则是另一条错误，信息里带 Direct buffer memory。

抛出溢出之前，虚拟机通常会先触发收集，尽力腾空间。软引用指向的对象会在这个阶段被考虑回收；`java.nio.Bits.reserveMemory` 里也能看到，申请直接内存失败前会调用 `System.gc()`，希望清理器把已经不可达的堆外缓冲还回去。

也不是每次失败都会先收集。如果一次申请的数组已经大于整个堆的上限，虚拟机可以判断收集也不可能满足这次分配，于是直接抛出错误。

## 内存泄漏

狭义的泄漏是：对象从业务上再也不会被用到，可收集器仍然到得了它，所以不能回收。广义一点，一些糟糕的写法把对象的寿命拉得和进程一样长，最终也以溢出收场，口语里同样叫泄漏。

泄漏不会在第一时间打崩进程。可用空间被一点一点占住，直到某次分配失败，才抛出 `OutOfMemoryError`。这里说的空间是虚拟地址空间里交给堆的那一部分，上限由堆参数和操作系统愿意给出的内存共同决定，并不等于机器上插着的物理内存条。

用可达性分析看，根走不到的对象才是回收候选。泄漏的形态是：业务已经不用了，链却没断，对象因此继续挂在根上。

### 举例

单例的寿命通常等于进程。若单例的字段抓住了外部请求、会话或巨大的缓存，这些外部对象就跟着单例一直活着，收集器不能收。单例本身不是错误，错误是它无界地持有本该短命的数据。

另一类是需要关闭的资源。数据源取出的连接、套接字、文件流，若没有 `close`，对象和底层原生资源会一起留下。语言层面的收集器即使稍后收掉 Java 包装对象，时机也不可控，连接池会先被耗尽。`try-with-resources` 把关闭放进确定的词法范围，比等终结方法可靠。

## Stop The World

Stop The World，简称 STW，指收集过程中用户线程被暂停的那段时间。暂停期间应用没有响应，看起来像卡住。可达性分析在枚举根时必须如此：分析要跑在一致的快照上，整个执行系统在这段时间里像被冻在某一个时间点。若分析过程中引用还在改，结果就不可信，可能把还要使用的对象标成垃圾。

被暂停的线程在收集完成相应阶段后恢复。停顿若又密又长，使用者的感受就像播放被反复卡住。优化的方向是减少 STW 的次数和每次的时长，而不是幻想哪个收集器完全没有它。

STW 和选用哪一款收集器无关，所有收集器都有。G1、甚至后来的低延迟收集器，也只是把必须停顿的阶段压短，不能从定义上删掉根枚举或对象搬迁时的那一下。它由虚拟机在后台发起，用户代码看不见，正常的工作线程会被一并停住。

开发时不要把 `System.gc()` 当成普通方法调用。它经常引出一次 STW，打乱延迟分布。

## 垃圾回收里的并行与并发

### 并发

操作系统里的并发，指一段时间内有多个程序都处于已开始、尚未结束的状态，哪怕它们共用一个处理器。并发不是同一瞬间的同时执行。处理器把时间切成小片，在几个程序之间切换；切换足够快时，人会觉得它们一起在跑。

### 并行

机器上有多个可以同时执行指令的核时，一个核跑进程 A，另一个核跑进程 B，两边都不把对方从核上挤走，这叫并行。决定能否并行的是可以同时运行的硬件线程数，而不是插座上有几颗物理 CPU。一个 CPU 里的多个核同样可以并行。这种方式和科学计算、后台批处理更合拍，交互式任务还要额外考虑延迟。

### 两者对照

并发说的是多件事在同一时间段内都在推进，并行说的是多件事在同一时间点上同时推进。并发的任务会互相抢时间片，并行的任务在不同的核上不必抢同一个核。没有多个执行单元时，看起来同时发生的事情，实际上只是并发。

### 收集器语境下的含义

把这两个词用到收集器上，含义被收窄了，不能直接照搬操作系统教材。

并行：多条收集线程一起工作，用户线程仍然等着。ParNew、Parallel Scavenge、Parallel Old 属于这一类。它们用多个核缩短停顿，但停顿期间业务代码不跑。

串行：相对并行而言，收集只有一条线程。内存不够时程序暂停，这条线程做完回收，用户线程再继续。Serial 和 Serial Old 是这种模型。

并发：用户线程和收集线程同时推进。两者不一定在不同的核上并行，也可能交替，但目标是收集进行时用户程序不必一直停住。CMS 和 G1 的部分阶段是并发的：标记可以和业务一起做，重新标记和某些转移阶段仍然要短暂停顿。

所以“CMS 是并发收集器”并不表示它没有 STW，只表示它把耗时的标记尽量挪出了停顿窗口。

## 安全点与安全区域

### 安全点

用户线程不是在任意字节码中间都能停下来开始收集。只有特定位置可以，这些位置叫安全点，Safepoint。

安全点太稀，收集器要等最慢的那条线程跑到点上，停顿被拉长；安全点太密，每次检查都要付钱，稳态变慢。绝大多数指令本身极短，选择标准是“会不会让线程长时间停在这里”。方法调用、循环回边、异常跳转这类执行时间可能很长的位置，会被选为安全点。若循环里没有回边检查，一个紧循环可能很久都不进安全点，其他线程就只能干等。

让所有线程都在安全点停住，有两种策略。

- 抢先式中断：先把所有线程挂起，发现某条不在安全点，就恢复它，让它跑到安全点再挂起。没有主流虚拟机再这么做，因为反复挂起的成本高，也不好控制。
- 主动式中断：设一个中断标志，线程跑到安全点时自己轮询。标志为真，线程就把自己挂起。HotSpot 采用轮询。后来的线程局部握手可以只让需要的线程响应，不必每次都停住全部线程，但“在安全点检查”这个前提还在。

### 安全区域

安全点保证正在执行的线程不久会遇到一个可以进入收集的位置。线程若根本没在执行呢？例如睡在 `sleep` 上，或堵在阻塞 IO 上，它无法响应中断请求，也“走”不到下一个安全点。虚拟机不能一直等它醒来。这种情况用安全区域，Safe Region。

安全区域是一段引用关系不会变化的代码。在这段里的任意位置开始收集都是安全的，可以把它看成拉长了的安全点。

执行流程是：

- 线程进入安全区域时先做标记。这段时间里若发生收集，虚拟机忽略已标记的线程，不要求它到达某个点。
- 线程准备离开时，要看收集是否已经结束。结束了就继续；没结束就必须等待，直到收到可以离开的信号。否则它一改引用，正在进行的标记就失效了。

## 再谈引用

有些对象希望这样被对待：内存还宽裕时留着，收集之后仍然紧张时就可以丢掉。JDK 1.2 起，Java 把引用分成四档。先是强引用，其后是软引用，再弱一档是弱引用，最末是虚引用。

强引用就是普通的赋值。其余三种在 `java.lang.ref` 包里，对应 `SoftReference`、`WeakReference`、`PhantomReference`。终结器引用也是 `Reference` 的子类，但它是包内可见的，应用代码不能直接 new。其余三种是公开类。

- 强引用：代码里最普通的引用关系。只要这条强引用还在，收集器就不会回收被指对象。
- 软引用：在即将溢出之前，把这些对象纳入一次回收。这次回收之后内存仍不够，才抛出溢出。
- 弱引用：关联的对象活不过下一次收集。收集器工作时，不管堆还宽不宽裕，都会清掉只被弱引用指着的对象。
- 虚引用：有没有它，都不改变对象的寿命，也不能通过它拿到实例。唯一目的是在对象被收走时收到一个通知。

## 再谈引用：强引用

普通程序里九成以上的引用都是强引用，它也是默认类型。`new` 出来的对象赋给变量，这个变量就是强引用。强引用可达的对象，收集器不会收。

一个普通对象若没有别的引用，只要离开作用域，或者把强引用显式写成 null，就可以在后续收集里被当成垃圾。具体哪一轮才收，仍看收集策略。

与之相对，只被软引用、弱引用或虚引用指着的对象，只能算软可达、弱可达，或者仅仅是虚可达，满足各自条件时就可以收。强引用因此是 Java 泄漏的主要来源：集合、静态字段、单例只要继续强引用着对象，收集器就无能为力。

### 举例

```java
StringBuilder buf = new StringBuilder("alpha-queue");
```

局部变量 `buf` 指向堆上的 `StringBuilder`。通过 `buf` 可以操作这块实例，所以 `buf` 是强引用。

再增加一个别名：

```java
StringBuilder buf = new StringBuilder("alpha-queue");
StringBuilder alias = buf;
```

此时栈上有两个槽指向同一块堆内存。若只执行 `buf = null`，对象仍然可达，因为 `alias` 还在。两个变量都清空，对象才进入可回收状态。

### 总结

本例里的两个变量都是强引用，特征可以归纳成三条：

- 沿着强引用就能操作那块实例。
- 只要强引用还在，虚拟机宁可抛出溢出，也不会收掉它指着的对象。
- 忘记断开强引用，是泄漏的常见形态。

## 再谈引用：软引用

软引用用来表示“还有用，但不是必须”的对象。只被软引用关联的对象，会在系统即将溢出时被放进回收范围，做额外的一次回收。这次仍不够，才抛出溢出。这里说的“额外一次”，是相对已经不可达的普通垃圾而言：普通垃圾每一轮都会被考虑，软可触及对象要等到内存紧张。

它常用来做对内存敏感的缓存。空闲还多时，缓存留着加速后续访问；堆变紧时，缓存被清掉，避免为了命中率把进程撑死。

收集器决定清理某个软可触及对象时，会清掉软引用本身，并可以选择把它放进引用队列。应用线程轮询队列，就能知道哪一项缓存已经失效，下次需要重新装载。

和弱引用相比，虚拟机会尽量让软引用多活一会儿，不到不得已不清理。一句话：内存够用时不收软可触及对象；内存不够时会收。存活长短还和堆里剩余空间有关，可以用策略参数调节“每兆空闲大约允许多活多久”，但不要依赖某个固定秒数。

JDK 1.2 之后用 `SoftReference` 表达：

```java
Object obj = new Object();
SoftReference<Object> soft = new SoftReference<>(obj);
obj = null;
```

最后一行必须有。若 `obj` 这个强引用还在，软引用的存在与否都不影响回收。

## 再谈引用：弱引用

弱引用也描述非必需对象，只是策略更急：下一次收集就会清掉只被弱引用关联的对象，不管当前堆还剩多少。发现即回收，是它和软引用的分界。

收集线程的优先级通常不高，所以“下一次收集”可能来得并不快。弱引用对象因此仍可能在堆里停留一段时间，直到真正发生 GC。不能把它理解成赋值结束就立刻消失。

构造弱引用时同样可以带上引用队列。对象被收掉后，弱引用实例入队，用来跟踪哪些键已经失效。`WeakHashMap` 就是按这个机制做的：键被弱引用包装，键不再被外部使用时，某次收集之后映射项可以被清掉。用它存放可重建的图片或临时元数据，能在内存紧张时把条目放走，降低溢出的概率。它不适合存放必须可靠存在的业务记录，因为收集时机不可预测。

JDK 1.2 之后的写法：

```java
Object obj = new Object();
WeakReference<Object> weak = new WeakReference<>(obj);
obj = null;
```

同样要先去掉强引用。收集发生时，软引用还要按策略判断是否回收，弱引用则总是会被处理。所以弱引用对象通常更快被收掉。

## 再谈引用：虚引用

虚引用也叫幽灵引用或幻影引用，是四档里最弱的一档。对象有没有虚引用，都不决定它能活多久。若一个对象只剩下虚引用，它和没有引用几乎一样，随时可能被回收。

它不能单独使用，也不能靠它取回实例。`get()` 恒为 null。设置虚引用的唯一目的，是跟踪回收过程：对象被收集器处理时，虚引用会被放进引用队列，应用由此得到通知。

因此虚引用在创建时必须传入引用队列。收集器准备回收一个对象、并且发现还有虚引用时，会在回收流程里把这个虚引用入队。应用可以把资源释放的记录放在处理队列的地方，而不是放进 `finalize()`。Java 9 之后，虚引用的清理时机更早，对象不必一直拖到引用对象被手工清理才消失，但 `get()` 仍然拿不到目标。

JDK 1.2 之后由 `PhantomReference` 实现：

```java
Object obj = new Object();
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> phantom = new PhantomReference<>(obj, queue);
obj = null;
```

### 案例

把虚引用、引用队列和终结方法放在一起，可以看到两轮收集的差别。下面的类在终结方法里尝试复活，队列则由一个守护线程监听。

```java
import java.lang.ref.PhantomReference;
import java.lang.ref.ReferenceQueue;

public class GhostTracker {
    public static GhostTracker anchor;
    static ReferenceQueue<GhostTracker> queue;

    @Override
    protected void finalize() throws Throwable {
        System.out.println("finalize called");
        anchor = this;
    }

    public static void main(String[] args) throws Exception {
        Thread watcher = new Thread(() -> {
            while (true) {
                try {
                    if (queue != null && queue.remove(500) != null) {
                        System.out.println("enqueued after phantom reachability");
                        break;
                    }
                } catch (InterruptedException ex) {
                    return;
                }
            }
        }, "ghost-watcher");
        watcher.setDaemon(true);
        watcher.start();

        queue = new ReferenceQueue<>();
        anchor = new GhostTracker();
        PhantomReference<GhostTracker> ref = new PhantomReference<>(anchor, queue);
        System.out.println(ref.get());

        anchor = null;
        System.out.println("gc-round-1");
        System.gc();
        Thread.sleep(800);
        System.out.println(anchor == null ? "anchor cleared" : "anchor present");

        System.out.println("gc-round-2");
        anchor = null;
        System.gc();
        Thread.sleep(800);
        System.out.println(anchor == null ? "anchor cleared" : "anchor present");
    }
}
```

第一次打印 `get()` 的结果是 null，说明虚引用不能把对象取回来。第一次收集会走到终结方法，对象把自身写回 `anchor`，所以它还在，队列里也还没有“已经被收掉”的通知。第二次再清空 `anchor` 时，终结方法不会重入，对象进入回收，虚引用被放进队列，监听线程打印入队信息，`anchor` 保持为 null。

这个顺序依赖终结线程和收集线程的调度，睡眠时间只是提高观察到上述顺序的概率，不是规范承诺的延时。

## 终结器引用

终结器引用用来实现对象的 `finalize()`，应用代码不用自己创建它。它在内部配合引用队列使用：收集时，若对象覆盖了终结方法且还没执行过，对应的终结器引用入队。Finalizer 线程从队列取出引用，找到对象并调用 `finalize()`。方法若没有把对象重新挂到根上，对象要等到再下一次收集才被真正回收。这也是“至少两轮标记”在引用包这一层的实现方式。
