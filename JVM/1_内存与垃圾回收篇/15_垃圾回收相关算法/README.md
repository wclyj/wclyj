# 垃圾回收相关算法

## 用计数做标记

堆上几乎存放着全部 Java 实例。收集器动手之前，得先把活对象和死对象分开。只有被判定为死亡的对象，才可以在随后的清除阶段把所占地址交还分配器。这一步叫标记。

怎样算死亡：从仍在使用的引用出发，已经走不到它。实现这条判断，常见有两类办法，引用计数，以及可达性分析。

引用计数给每个对象加一个整数域，记录还有多少引用指向它。每当有新引用指向对象 A，计数加一；引用被改写或离开作用域，计数减一。计数掉到 0，就认为 A 不会再被用到，可以立刻回收。

好处是规则直观，死亡对象容易认出来，而且判定是局部的，引用一断开就可以回收，不必等一轮全堆扫描。

代价是每个对象都要多占一个计数字段，赋值语句旁边还得跟上加法和减法，时间和空间都不免费。更致命的是环：两个对象互相引用、外界已经没有人指着它们时，计数都不会归零。Java 的收集器因此不把引用计数当作标记手段。

### 循环引用

设左节点的外部引用已经清空，它和右节点却还彼此指着。从程序的后续逻辑看，这两个节点都到不了，计数却停在 1。环越大，泄漏越安静，进程只会慢慢变胖。

### 举例

下面用一对互相指向的对象，看 HotSpot 会不会把它们留下。每个对象带一块 3MB 的数组，方便在日志里看见年轻代的占用变化。类名和负载大小都与常见演示不同。

```java
public class CycleHolder {
    private final byte[] payload = new byte[3 * 1024 * 1024];
    CycleHolder peer;

    public static void main(String[] args) {
        CycleHolder left = new CycleHolder();
        CycleHolder right = new CycleHolder();
        left.peer = right;
        right.peer = left;
        left = null;
        right = null;
        System.gc();
    }
}
```

一次实际运行里，年轻代日志接近下面这种形状（数字会随堆的人体工学变化，这里只保留量级）：

```text
[GC (System.gc()) [PSYoungGen: 9216K->480K(38912K)] 9216K->608K(126976K), 0.0048 secs]
[Full GC (System.gc()) [PSYoungGen: 480K->0K(38912K)] [ParOldGen: 128K->336K(88064K)] 608K->336K(126976K), [Metaspace: 4102K->4102K(1114112K)], 0.0056 secs]
```

年轻代从大约 9MB 掉到几百 KB，说明那两块数组没有因为“互相指向”而留下来。若标记靠的是引用计数，`peer` 会把两边的计数都维持在非零，`System.gc()` 之后它们仍应占据堆。它们被收走了，就可以排除“HotSpot 用引用计数做标记”。

### 小结

引用计数仍是不少语言运行时的选择。Python 就同时维护引用计数和一套专门拆环的收集器：计数负责大多数对象的即时释放，环则交给分代扫描。也有系统在大规模服务里只保留计数，用别的手段换吞吐。

Java 不选它，是因为环这个基本问题要在每次赋值时处理，成本不划算。Python 一侧，程序员可以在合适的时机主动拆开引用，也可以使用标准库 `weakref`，让环上的某一边不增加计数。

## 从根扫描做标记

### 概念

这种从根出发的搜索也叫根搜索，或追踪式垃圾收集。它和引用计数一样，规则可以讲清楚，扫描也能做得很高效；更重要的是，环不再是特殊情况。环上的对象只要没有从根走到它们的路径，就会被标成垃圾。Java 和 C# 选择的是这一类，通常就称为 Tracing Garbage Collection。

### 思路

GC Roots 是一组必须视为活着的引用起点。算法从这组根出发，沿着引用往下走，能走到的对象都是存活对象，走过的边叫做引用链。没有任何引用链能到达的对象是不可达的，标记阶段把它记为垃圾。反过来，只有被根直接或间接连上的对象才算活着。

根本身必须是堆外的确定引用，或者是虚拟机知道“现在一定还要使用”的内部结构。搜索可以理解成从若干入口做图遍历，而不是给每个对象维护一个计数。

### 哪些引用可以当作 GC Roots

- 虚拟机栈上的引用：各线程正在执行的方法里的参数、局部变量、操作数栈中的对象指针。
- 本地方法栈里 JNI 持有的引用，包括 JNI 的局部引用和全局引用。
- 方法区里类的静态字段所引用的对象，例如某个类的静态集合。
- 方法区常量所引用的对象，字符串表里的引用是典型。
- 被 `synchronized` 锁住的对象，监视器还被持有时对象必须算活。
- 虚拟机内部的一些常驻引用：基本类型对应的 `Class`、常驻异常对象、系统类加载器。
- 反映虚拟机状态的 JMX Bean、JVMTI 回调、以及本地代码缓存里登记的引用。

#### 固定根之外

固定根之外，还会按收集器的种类和这次回收的区域，临时把别的对象加进根集合。分代收集和局部收集都要这么做。

只扫年轻代时，年轻代里的对象完全可能被老年代引用。那些跨代指针若被漏掉，活对象会被误标成垃圾。所以收集器要用记忆集或卡表，把“老年代指向年轻代”的那些位置也当成根。区域不是封闭的，根集合必须把外部指进来的边补齐，可达性才可信。

#### 判别口诀

有一个好用的判别：根用栈或方法区这类堆外结构存放指针。一个指针若指向堆内对象，自己却不在堆里，它就是根。堆内对象指向堆内对象，那只是引用链上的普通边。

### 注意

可达性分析必须跑在一个引用关系不再变化的快照上。分析进行到一半时，用户线程若还在改引用，遍历看到的图就会前后矛盾，活对象可能被漏标。这是收集过程必须 Stop The World 的一个核心原因。

即便是停顿很短的 CMS，枚举根节点时仍然要把 Java 线程停住。并发标记可以在停顿之后进行，但根的那一瞬间必须一致。

## 对象的终结机制

Java 允许对象在被回收之前跑一段自定义逻辑，这就是终结，入口是 `finalize()`。收集器发现一个对象已经没有引用链时，并不会立刻腾空它的内存，而会先给这个方法一次执行机会。子类可以覆盖它，做关闭文件、套接字或连接之类的收尾。

### 注意

不要在业务代码里主动调用某个对象的 `finalize()`。它应当只由收集机制触发。原因有三：

- 方法内部可能把 `this` 重新挂到静态变量上，对象会复活，主动调用会把这种副作用提前引爆。
- 它的执行时刻没有保证，完全看终结器线程什么时候跑。若进程里一直不发生 GC，这个方法就没有机会。它的优先级偏低，即便手动点了方法，也不会因此马上回收对象。
- 一个很慢的 `finalize()` 会拖住收集器，放大停顿。

从作用上看，它有点像 C++ 析构函数，但 Java 的内存由收集器管理，两者不是一回事。析构函数在对象离开作用域时同步发生，`finalize()` 只在对象已被判定为不可达之后、由另一个线程异步执行。Java 9 起这个方法被标为过时，新代码应使用 `Cleaner` 或 `try-with-resources`。

因为有这段逻辑，虚拟机里的对象不能简单分成“活着”和“已死”。

### 可触及、可复活、不可触及

从所有根都走不到某个对象时，说明程序已经不再使用它，按理会进入回收。可它未必马上死，中间有一段缓刑：不可触及的对象仍可能在特定条件下把自己重新挂回引用链。若这时就回收，会把复活的对象收掉。因此分成三种状态。

- 可触及：从根出发能够到达。
- 可复活：外部引用都已断开，但 `finalize()` 仍可能把它重新挂上。
- 不可触及：`finalize()` 已经跑过，并且没有复活。这种对象不能再复活，因为该方法对同一个对象只会执行一次。

区分来自终结方法的存在。只有进入不可触及，才可以被回收。

### 具体过程

判断对象 `sample` 能不能回收，至少要标记两轮。

第一轮：若 `sample` 到 GC Roots 没有路径，先做一次标记，并筛选它有没有必要执行 `finalize()`。

- 没有覆盖该方法，或者虚拟机已经调用过它，就视为不必再执行，对象直接进入不可触及。
- 覆盖了且还没执行过，对象被放进 F-Queue。虚拟机会起一个低优先级的 Finalizer 线程，由它触发这些对象的 `finalize()`。
- 这次执行是它躲开回收的最后窗口。之后收集器对 F-Queue 里的对象做第二次标记。若在方法里把 `sample` 重新挂到仍可从根走到的对象上，第二次标记会把它移出“即将回收”集合。
- 以后它若再次失去全部引用，`finalize()` 不会再被调用，对象直接变成不可触及。

所以“只调用一次”既是复活的窗口，也是窗口关闭的原因。

### 代码演示

下面让对象在终结方法里把自己写回静态字段。静态字段属于根能到达的位置，因此第一次收集可以自救，第二次不行。等待时间取 1500 毫秒，只为给低优先级的 Finalizer 线程留出调度空隙。

```java
public class PhoenixDemo {
    public static PhoenixDemo anchor;

    @Override
    protected void finalize() throws Throwable {
        System.out.println("finalize invoked");
        anchor = this;
    }

    public static void main(String[] args) throws InterruptedException {
        anchor = new PhoenixDemo();
        anchor = null;
        System.gc();
        Thread.sleep(1500);
        System.out.println(anchor == null ? "first: gone" : "first: revived");

        anchor = null;
        System.gc();
        Thread.sleep(1500);
        System.out.println(anchor == null ? "second: gone" : "second: revived");
    }
}
```

典型输出是第一次打印 `finalize invoked` 和 `first: revived`，第二次打印 `second: gone`。第一次清除前执行了终结方法，对象把自身写回 `anchor`；第二次外部引用再次清空时，方法不会重入，对象被真正回收。

## 用 MAT 与 JProfiler 追溯 GC Roots

### MAT 是什么

MAT 是 Memory Analyzer 的缩写，用来分析 Java 堆转储，查找泄漏和占用大户。它基于 Eclipse，可以离线打开 hprof 文件，不依赖进程还活着。

### 命令行导出堆转储

进程还在时，可以用 `jmap` 按进程号导出。不同 JDK 的推荐写法略有差别，JDK 8 常见形式是：

```text
jmap -dump:live,format=b,file=/tmp/app-heap.hprof <pid>
```

`live` 表示先做一次可达性分析，只保留活对象，文件更小，也更接近“泄漏还被引用着”的那部分。生产上要意识到这次导出会带来停顿。

### 用 VisualVM 抓堆

VisualVM 抓到的堆转储默认是临时文件，关掉工具会被删掉，需要保留时得另存。入口有两处：在应用程序节点上选择堆转储；或在监视页里点堆转储按钮。本地进程的转储会作为该进程下的一个子页打开，左侧应用树里会出现带时间戳的节点，在节点上另存即可写到指定路径。

### 用 MAT 打开转储

打开之后可以查看哪些对象被当作 GC Roots，常见类别里能看到系统类、线程栈上的局部变量、监视器。沿着线程展开，就能从栈帧走到仍被引用的业务对象。

### JProfiler 里的引用链

排障时很少需要把全部根列出来，更常见的是选定一个疑似泄漏的对象，看它经哪几跳连到根上。JProfiler 的 GC Roots 溯源就是这条路径：从实例出发反向走到栈、静态字段或类加载器。路径若经过一个永远不会释放的静态集合，泄漏点通常就在那个集合的写入处。

### 怎样判断是什么造成了 OOM

溢出之后先留下转储，再看是谁在涨。下面的例子不断把大约 768KB 的对象推进列表，并用较小的堆迫使它失败。堆参数改成 12MB，类名也不再用常见的演示名。

```java
import java.util.ArrayList;

public class ChunkLeak {
    byte[] block = new byte[768 * 1024];

    public static void main(String[] args) {
        ArrayList<ChunkLeak> bin = new ArrayList<>();
        int n = 0;
        try {
            while (true) {
                bin.add(new ChunkLeak());
                n++;
            }
        } catch (OutOfMemoryError err) {
            System.out.println("allocated=" + n);
        }
    }
}
```

启动参数：

```text
-Xms12m -Xmx12m -XX:+HeapDumpOnOutOfMemoryError
```

用 MAT 打开生成的 hprof，按最大对象查看，会看到 `ArrayList` 及其元素数组占据绝大部分堆。再沿合并路径或线程栈看，分配点会落在 `main` 里的循环。这样就区分开了“单个超大数组”和“无数中等对象被集合拽住”。前者调堆或改算法，后者要切断那条还活着的引用链。

## 清除阶段：标记-清除

标记完成后，收集器的下一件事是把垃圾占用的地址交出来，让后续分配有地方可去。虚拟机里常见的三种基础算法是：标记-清除、复制、标记-压缩。

标记-清除由 McCarthy 等人在 1960 年前后提出，并用于 Lisp。它是后面多种算法的底子。

### 执行过程

当可用空间耗尽，或者分配失败需要回收时，用户线程被停住，然后做两件事。

- 标记：从根遍历，把所有仍被引用的对象打上标记。标记写在对象头里。注意标记的是活对象，不是垃圾。
- 清除：从堆的低地址扫到高地址，对象头上没有存活标记的，就把它所占区间登记为空闲。

### 清除到底清掉了什么

这里的清除通常不是把字节抹成零，而是把这段地址记进空闲列表。下次分配时，若某段空闲区间放得下新对象，就在原地址上覆盖。前面讲过：内存若仍然规整，分配可以用指针碰撞；清除之后往往不规整，分配器只好维护空闲列表，按块的大小去匹配。

### 缺点

- 标记和清除都要扫描，效率一般。
- 过程中用户线程停住，停顿直接体现在延迟上。
- 空闲区间不连续，形成外部碎片。总空闲字节数够，却可能没有一块连续空间放下较大的对象。分配器必须维护空闲列表，查找也有成本。有的教材把这种空洞叫成内部碎片，那是不准确的：内部碎片是已分配块内部浪费的对齐空隙，标记-清除留下的是块与块之间的外部碎片。

## 用复制完成清除

### 提出的背景

为了避开标记-清除在效率和碎片上的问题，Minsky 在 1963 年描述了双空间收集，并把它放进 Lisp 的一个实现。后来 Cheney 在 1970 年给出了更实用的非递归复制遍历。人们把这一族算法叫做复制算法。

### 核心思想

把可用空间分成两块，任意时刻只在其中一块上分配。回收时，把正在使用的那块里的存活对象复制到空闲的那块，复制过程中对象被紧凑地排好，然后整块丢弃原来的空间。两块的角色对调，完成这一轮。

可达对象被拷到另一侧之后，原来的区域可以整段视为空白，不必逐个清除垃圾。年轻代里的 Eden 与 Survivor 就是这个想法的变体：每次把 Eden 和 From 里的存活对象拷进 To，再交换 From 和 To 的身份。

### 优点

- 不需要单独的清除扫描，实现直接，存活对象少时非常快。
- 复制完成之后空间连续，没有外部碎片。后续分配又可以回到指针碰撞。

### 缺点

- 需要准备另一块空间，极端情况下内存利用率只有一半。
- 对 G1 这种切成大量 Region 的收集器，复制而不是在本区域里滑动，意味着跨区域的引用要被记住并在移动后修正。记忆集既占内存，也占维护时间。

### 注意

垃圾越多、存活越少，复制越划算。老年代若大部分对象都还活着，复制的体积接近整堆，成本高于就地整理。常规应用的年轻代一次往往能收回七成到九成九的空间，性价比高，所以商业虚拟机用复制算法回收年轻代。HotSpot 用一块较大的 Eden 加两块较小的 Survivor，而不是严格的对半划分，把“多准备一块空间”的浪费压到年轻代的一小部分。

## 清除阶段：标记-整理

### 背景

复制算法快，是因为存活对象少。年轻代经常如此，老年代则经常相反：大多数对象熬过了多次年轻代收集，仍然活着。继续复制会把大量对象搬来搬去。标记-清除可以用在老年代，但它慢，而且留下碎片，所以需要一种既不把空间对半切开、又能消除碎片的办法。标记-压缩因此出现。1970 年前后，Steele、Wise 等研究者发表了把存活对象滑向一端的算法，后来的多种整理收集器都从这里演变。

### 分两步完成

前半段与标记清除一致：从根把还能到达的对象标出来。第二阶段把存活对象紧凑地挪到内存的一端，按地址顺序排好，然后把边界以外的整段空间视为空闲。死亡对象不必逐个登记到空闲列表，它们所在的区域被边界一下切掉。

### 标清和标整的差别

标记-压缩的最终效果，可以看成标记-清除之后再做一次碎片整理，所以也有人把它叫作标记-清除-压缩。本质差别是：标记-清除不移动活对象，标记-压缩会移动。移动与否是一组互相牵制的选择。移动之后，存活对象按地址排紧，分配新对象时虚拟机只要记住一段连续空闲区的起始位置，不必维护空闲列表。不移动则引用不用改，但碎片会留下。

### 标整的优缺点

#### 优点

- 去掉了标记-清除留下的外部碎片。给新对象分配时，持有空闲区起点即可。
- 去掉了复制算法把可用空间大致折半的代价，整段老年代都可以参与分配。

#### 缺点

- 吞吐通常低于复制算法，因为除了标记，还要滑动对象。
- 对象被移动后，所有指向它的引用都要改写成新地址，包括栈上的、卡表里的、其他对象字段里的。
- 移动期间用户线程必须停住，否则会读到搬到一半的对象。也就是整段 STW。

## 小结

单看速度，存活对象少时复制算法最快，但要额外空间。若希望同时照顾速度、空间和碎片，标记-整理更平，却比复制多一次标记，比标记-清除多一次滑动，所以最慢。

| 维度 | 标记-清除 | 标记-整理 | 复制 |
| --- | --- | --- | --- |
| 速度 | 中等 | 最慢 | 存活少时最快 |
| 额外空间 | 小，但积累外部碎片 | 小，不留碎片 | 需要一块对等或按代设计的空闲区 |
| 是否移动活对象 | 否 | 是 | 是 |

没有一种算法在所有代上都最优，只有和对象死亡率匹配的算法。

### 分代收集

前面几种算法谁也不能完全取代谁，于是按对象寿命把堆拆开，不同的代用不同的算法。这就是分代收集。依据是一个经验事实：对象的寿命差得很远。和业务绑定的会话、线程、长连接可以活得很久；计算过程中的临时对象、大量只参与一次拼接的字符串，则很快死亡。把它们放在同一套算法里，要么为少数长寿对象付出复制成本，要么为大量短命对象忍受碎片。

目前实用的收集器几乎都带分代或分代的变体。HotSpot 里，年轻代和老年代的算法选择要跟各自的死亡率匹配。

年轻代相对小，对象活得短，存活率低，回收频繁。复制的成本和当前存活体积成正比，正好合适。双 Survivor 的设计用来缓解复制算法浪费空间的问题：真正空着的只有较小的 To 区，而不是半个年轻代。

老年代空间大，对象活得长，存活率高，回收次数少。这里若仍用复制，要搬走的对象太多。一般采用标记-清除，或标记-清除与标记-整理的组合。

三个阶段的成本和不同的量成正比：

- 标记大致正比于存活对象的数量。
- 清除大致正比于被管理区域的大小。
- 整理大致正比于存活对象的体积。

以 CMS 为例，它的老年代回收基于标记-清除，并发阶段吞吐好，但碎片是固有问题。碎片严重到并发模式失败时，CMS 退回到基于标记-压缩的 Serial Old，做一次整堆收集，把老年代整理干净。这是用一次较长的停顿，换回连续空间。

分代思想被现有虚拟机广泛采用。即便是按 Region 工作的收集器，也会给 Region 贴上年轻代或老年代的角色，算法仍然按死亡率分开。

## 增量收集算法

### 概述

前面那些算法若一次性跑完，应用会处于 Stop The World：所有用户线程挂起，直到收集结束。停顿若长达数百毫秒甚至更久，交互和超时都会受影响。为了把单次停顿压短，增量收集被提出来。

思路是不要一次处理完全部垃圾，而让收集线程和用户线程交替。每轮只标记或只复制一小片，然后把处理器还给应用，反复进行直到这一轮收集做完。底座仍是标记-清除或复制，增量算法额外处理的是线程交替时的引用变化：用户线程可能改写收集器已经扫描过的引用，必须用写屏障把这些改动记下来，下一小段再补扫。

### 缺点

单次停顿变短了，因为中间插进了应用代码。总代价却上升：线程切换、屏障和重复扫描都会吃掉吞吐。系统的 CPU 利用率变差，单位时间里能完成的业务量下降。后来的并发收集器把“交替”推进成“尽量同时跑”，但根枚举和重定位仍免不了短暂停顿，增量收集是这条路上的早期形态。

## 分区算法

同样的收集算法，堆越大，一次扫完整堆的时间越长，停顿也越长。分区算法为了把停顿控制在目标以内，把一大块堆切成许多连续的小区间。每一轮只挑其中若干区间回收，而不是碰整个堆。

分代按寿命把堆切成年轻代和老年代两段；分区则把地址空间切成大量小块，每块独立分配、独立回收。一次回收多少块，可以由暂停时间目标倒推。G1 的 Region 就是这个想法的工程化：堆被切成等大的区域，收集器按垃圾比例挑选若干区域复制回收，从而把单次停顿和选定的区域大小绑在一起，而不是和整堆绑在一起。

## 写到最后

上面是算法骨架。实际收集器都是复合体：年轻代可能用复制，老年代可能并发标记再偶尔整理，分区收集器还会在区域之间维护记忆集。并行指多个收集线程一起干，并发指收集线程和用户线程同时干。现在仍在发展的收集器，两种手段都会用，而不是只停留在某一种教科书算法上。
