# JVM 与 Java 体系结构

## 概念

线上进程突然卡住、接口不再响应，甚至直接抛出内存耗尽，往往不是业务代码“写错一行”那么简单。堆被撑满、回收停顿过长、元空间持续上涨，表面都像是进程失去响应。要处理这些现象，得先知道虚拟机把内存分成了哪些块、回收线程什么时候会把业务线程停住、哪些开关只影响年轻代。

只熟悉上层框架、把虚拟机当成黑盒，排障时会只剩下“把堆调大再观察”。核心类库的 API 像公式，虚拟机的机制则是公式怎么来的。高级语言让人不必直接写机器指令，但处理器并不认识 Java 源码。源码要先变成字节码，再由虚拟机解释或编译成当前平台的机器码。

## 做结构设计时通常在权衡什么

容量和延迟是每天要面对的两个问题：怎样让路径更短，怎样避免某一层先成为瓶颈。岗位描述里反复出现的工作，大致是这些：

- 在现有系统上做性能和稳定性改进，而不是只加功能。
- 按业务量级做技术选型，而不是套用一套固定架构。
- 在大流量下同时满足功能指标和非功能指标。
- 把核心路径的风险提前拆开，包括内存、锁和外部依赖。
- 定位瓶颈，处理偶发的长停顿和资源泄漏。

这些工作和虚拟机参数是连着的。不知道默认收集器是谁，就无法解释一次长达数秒的停顿。

## 为什么要弄清虚拟机

面试会问收集器和内存布局，但更常见的追问是：某个服务的停顿是怎么压下去的、一次内存耗尽的堆转储说明了什么。中高级开发要能看日志、能判断该调堆还是该改分配方式。回收算法、即时编译和对象布局，则是把这些判断从口诀变成依据。

## 和 C++ 的差别

C 和 C++ 由调用方决定何时申请、何时释放。Java 把分配和回收交给虚拟机。这省掉了大量配对释放的代码，也引入了新的故障类型：回收跟不上分配、大对象提前进入老年代、错误的引用让对象永远活着。能设计可扩展的服务、能解释运行期的停顿，前提就是知道内存结构和回收线程怎么工作。自动回收不是“内存问题已经消失”。

## Java 不止是一门语言

Java 同时是平台、一套开放实现和一大批库。作为平台，虚拟机让 Groovy、Scala、JRuby、Kotlin 等语言能共享运行时。作为开放实现，容器、Web 框架和 JDK 自身都有公开源码，OpenJDK 是目前的参考实现，Apache Harmony 则是已经退役的另一条线。作为社区，它覆盖桌面、嵌入式、企业后台和中间件，参与的人和部署形态都很多。

这些语言各自有编译器，产物只要符合虚拟机认识的字节码格式，就能被同一台虚拟机装载。虚拟机不关心源文件是哪种语法。

JDK 7 通过 JSR-292 把这种“语言无关”落到了指令集上：只要编译结果带有虚拟机的指令、符号表和辅助信息，它就是合法的类文件。

## 字节码

平时说的 Java 字节码，严格讲是 Java 语言编译出来的那一种。任何能在这台虚拟机上执行的类文件，格式是统一的，更准确的称呼是 JVM 字节码。不同编译器可以产出同一格式，同一份类文件也可以在不同厂商的虚拟机上运行。

虚拟机和 Java 语言没有绑定关系。它绑定的是 Class 文件：里面有指令集、符号表，以及版本、访问标志等辅助信息。

## 在一个进程里混用多种语言

用不同语言处理不同问题，已经是一种常见拆法。例如并行计算用 Clojure，页面用运行在虚拟机上的 Ruby 实现，中间服务仍用 Java。层与层之间看到的是对方的对象和调用，而不是进程间协议，因为它们最终进的是同一台虚拟机。

JDK 7 之后，Da Vinci Machine、Nashorn、`invokedynamic` 和 `java.lang.invoke` 这些工作，都是在把虚拟机从“只为 Java 语法服务”推向“多语言运行时”。Nashorn 后来在 JDK 15 被移除，方向本身还在，GraalVM 把多语言执行又往前做了一步。

## 虚拟机这个词指什么

虚拟机是用软件实现的一台计算机，用来执行一组约定好的指令。它分成两类。

- 系统虚拟机仿真整台物理机，上面可以跑完整操作系统。VirtualBox、VMware 属于这一类。
- 程序虚拟机只为一类程序服务。Java 虚拟机是代表，它执行的指令称为字节码。

无论哪一类，跑在上面的软件都只能使用虚拟机提供的资源，不能直接绕过它去占有宿主机的全部设备模型。

Java 虚拟机是执行字节码的程序虚拟机。字节码不一定由 Java 编译器产出。各语言共享的是跨操作系统的字节码、垃圾回收和即时编译。技术上的核心是这台虚拟机，因为 Java 程序都跑在它里面。

它负责装入字节码，再解释或编译成当前平台的机器指令。每一条指令在规范里都规定了操作数从哪取、如何运算、结果放回何处。由此得到三个直接后果：源码编译一次即可在多个操作系统上执行，堆内存由虚拟机分配，不再使用的对象由收集器回收。

## 它处在整机的哪一层

虚拟机跑在操作系统之上，不直接驱动网卡、磁盘控制器这些硬件。向下是操作系统调用，向上是类库和业务代码。Java 的结构可以看成四层：语言和类库、字节码、虚拟机、操作系统与硬件。换操作系统时，替换的是虚拟机的本地实现，而不是重写业务源码。

## HotSpot 的整体结构

HotSpot 是目前使用最广的高性能实现之一。它同时带有解释器和即时编译器：方法先解释执行，热点方法再编译成本地代码。执行引擎里通常还把垃圾收集算进去，因为回收会暂停或并发地插入到执行过程中。今天的服务端 Java 在不少计算任务上已经能和 C/C++ 比较吞吐，差距主要来自分配方式、回收停顿和边界检查，而不是“解释执行所以必然慢一个数量级”。

## 从源码到进程

编译器把源码变成类文件。只要文件能被这台虚拟机解释，理论上可以用另一套语法去生成它。进程启动后，加载器把类文件定义成运行时类型，执行引擎从启动类的入口方法开始取指令。解释器逐条执行，即时编译器在后台把热方法换成机器码，收集器按堆的占用情况插入回收。

## 指令集：栈还是寄存器

Java 编译器发出的是基于栈的指令流。另一种常见模型是基于寄存器的指令集。

栈式模型的特点：

- 实现简单，适合资源紧的环境。
- 不用做物理寄存器分配，指令以零地址形式为主，操作数默认在操作数栈顶。
- 指令种类少，编译器容易写。
- 不绑定某一种处理器的寄存器文件，移植成本低。

寄存器模型的特点：

- x86 的机器码，以及早期 Android 的 Dalvik，都按寄存器来设计。
- 指令直接依赖硬件能提供的寄存器，换处理器就要换指令编码，可移植性差。
- 完成同一次运算所需的指令条数更少，单条指令往往携带一个到三个操作数地址。
- 执行密度高，但编译器要处理寄存器分配。

栈式指令的缺点是完成同样的运算要更多次压栈和弹栈，内存访问次数上升。HotSpot 用栈顶缓存缓解这一点，细节放在虚拟机栈一章。

### 同一段加法

计算 `4 + 6` 时，栈式虚拟机大致是下面的过程。

```text
iconst_4
istore_1
bipush 6
istore_2
iload_1
iload_2
iadd
istore_0
```

`iconst_4` 把常量压栈，`istore_1` 弹到局部变量。`6` 超出了 `iconst` 能直接编码的范围，所以用 `bipush`。两个局部变量再装回栈顶，`iadd` 弹出它们并压回和。

寄存器机器上可以收成两条：

```text
mov ebx, 4
add ebx, 6
```

第一条把 `4` 写入 `ebx`，第二条让 `ebx` 加上 `6`。中间结果一直待在寄存器里。

### 用反编译核对

```java
public class AddFrameDemo {
    public static void main(String[] args) {
        int sum = 4 + 6;
    }
}
```

编译后执行 `javap -c -p AddFrameDemo.class`。`main` 的指令区里能看到 `iconst_4`、`bipush 6`、`iadd` 和 `istore`，栈深和局部变量槽数量写在 `Code` 属性里。常量折叠有时会让编译器直接放入 `10`，若要观察未折叠的两条加载，把两个加数改成变量即可。这只说明指令集是栈式的，不代表源码里的每一处加号都会原样留下。

## 为什么不改成寄存器架构

跨平台是首要约束。不同处理器的寄存器数量和调用约定不一样，把字节码绑到某一种寄存器文件上，类文件就不再通用。栈式指令集更小，编译器更好写，代价是完成同样的工作要更多条指令，解释执行时分派次数更高。

嵌入式设备早已不是 HotSpot 的主要宿主，但字节码格式已经固定了二十多年，类库和已编译的第三方包都依赖它。换成寄存器架构等于换一套指令集，生态成本远高于在实现内部做栈顶缓存和即时编译。因此保留栈式字节码，把性能工作放在编译器和运行时，而不是放在指令编码上。

栈式模型可以记成四句话：便于移植，指令种类少，完成一件事的指令条数多，解释执行不如寄存器模型紧凑。

## 生命周期

### 启动

虚拟机通过引导类加载器创建并初始化一个初始类来完成启动。这个初始类由具体实现规定。对普通程序来说，就是命令行指定的、含有 `main` 的那个类。

### 执行

运行中的虚拟机只有一件事：执行 Java 程序。进程在程序开始执行时存在，在程序结束时退出。用户以为自己在跑一个 Java 程序，操作系统看到的是一个虚拟机进程。

### 退出

下列情况会结束这个进程：

- 启动类的 `main` 正常返回，并且没有非守护线程还在跑。
- 某条线程抛出了没有被捕获的异常或错误，导致虚拟机按实现策略终止。
- 操作系统出现致命错误，进程被杀掉。
- 某条线程调用了 `Runtime.exit` 或 `System.exit`，或者调用了 `Runtime.halt`，并且安全管理器允许这次调用。`exit` 会先跑关闭钩子，`halt` 会直接停止。
- 按 JNI Invocation API 把虚拟机装入一个外部进程时，卸载虚拟机也会结束运行。规范描述了这种嵌入方式下的退出条件。

## 各家实现走过的路

具体内存布局由实现决定。不同厂商、同一厂商的不同版本，区域名字和默认收集器都可能不同。下面的机制以 Oracle HotSpot 为主。

### Sun Classic VM

1996 年 JDK 1.0 附带的 Classic VM 是第一款商用 Java 虚拟机，到 JDK 1.4 被完全淘汰。它内部只有解释器。即时编译器要另外挂上，而且一旦挂上就接管执行，解释器不再参与，两者不能按方法热度配合。没有热点探测，循环和冷门代码的代价一样高。

### Exact VM

JDK 1.2 时 Sun 用 Exact VM 补 Classic 的短板。Exact 指准确式内存管理：虚拟机知道某个内存字是整数还是引用，而不是保守地猜。它已经有热点探测，也有解释器和编译器混合执行的雏形。它主要在 Solaris 上短暂使用，其他平台仍是 Classic，随后被 HotSpot 取代。

### HotSpot

HotSpot 最初由 Longview Technologies 设计。1997 年 Sun 收购这家公司，2009 年到 2010 年 Sun 再被 Oracle 收购。JDK 1.3 起 HotSpot 成为默认虚拟机。无论是仍广泛存在的 JDK 6，还是 JDK 8，默认实现都是它；Oracle JDK 和 OpenJDK 都以它为虚拟机。本套笔记里的收集器行为，除特别说明外都指 HotSpot。有的商用虚拟机甚至没有“方法区”这个实现名词，不能把 HotSpot 的区域图套到所有产品上。

从服务器、桌面到嵌入式都能见到它。名字里的 HotSpot 指热点探测：用计数器找出值得编译的方法，触发即时编译或栈上替换，让解释器和编译器一起工作，在启动速度和峰值性能之间取平衡。

### JRockit

JRockit 来自 BEA，面向服务端。它不强调启动速度，因此内部不带解释器，方法都经过即时编译再执行。厂商当时用行业基准宣传它在服务端的吞吐和硬件占用上领先，那些比例依赖具体测试，不能当成所有业务的收益。

它还有面向低延迟场景的 Real Time 变体，以及 Mission Control 这套低开销的监控分析工具，适合对停顿敏感的金融、电信类系统。2008 年 Oracle 收购 BEA 之后，整合方式不是继续并行维护两套虚拟机，而是把 JRockit 的特性移进 HotSpot。这项工作大致在 JDK 8 一代落地，Mission Control 后来也成为 HotSpot 的工具。

### IBM J9

全称 IBM Technology for Java Virtual Machine，内部代号 J9。定位和 HotSpot 接近，覆盖服务器、桌面和嵌入式，广泛用在 IBM 的 Java 产品里，也常被宣传为很快的实现。2017 年前后 IBM 把它公开为 OpenJ9，交由 Eclipse 基金会管理。OpenJDK 是整套 JDK 的公开源码，其中包含虚拟机；OpenJ9 则是可以替换 HotSpot 的另一台虚拟机。

### KVM 与 CDC/CLDC

Oracle 在 Java ME 上提供过 CDC 和 CLDC 两条配置，对应的 HotSpot 实现很精简。KVM 里的 K 表示 kilobyte，是 CLDC 早期的小虚拟机，面向控制器、传感器和功能机。智能手机市场后来主要由 Android 和 iOS 占据，KVM 不再是手机上的主流，但“编译一次、换设备仍能跑同一份字节码”的原则没有变。

### Azul 的虚拟机

Azul VM 和 BEA 的 Liquid VM 都属于跟特定硬件或虚拟化层绑定的实现。Azul 在 HotSpot 上做了大量改动，早期运行在自己的 Vega 硬件上。单个实例可以管理大量处理器和数百 GB 内存，并提供在大堆上仍能约束停顿的收集器。2010 年后 Azul 转向软件，发布 Zing，在通用 x86 上提供接近 Vega 的低延迟能力。

### Liquid VM

Liquid VM 由 BEA 开发，直接跑在自家 Hypervisor 上，也就是后来的 JRockit VE。它不依赖一套通用操作系统，自己实现线程调度、文件系统和网络支持。JRockit 停止独立发展后，这条产品线也停止了。

### Apache Harmony

Apache 做过与 JDK 5、JDK 6 兼容的 Harmony。它由 IBM 和 Intel 推动，和 OpenJDK 同属公开实现。Sun 没有让它通过 JCP 认证，项目在 2011 年退役，IBM 转而参与 OpenJDK。Harmony 没有成为大规模的服务器 JDK，但它的类库代码进入了 Android SDK，影响留在了移动端。

### Microsoft JVM

微软为了在 IE3 里运行 Java Applet，做过只支持 Windows 的 Microsoft JVM，当时在 Windows 上的性能表现突出。1997 年 Sun 以商标和不正当竞争为由起诉并获胜。到 Windows XP SP3，这台虚拟机被移除。现在 Windows 上安装的 JDK 使用的是 HotSpot。

### TaobaoVM

阿里基于 OpenJDK 做了 Alibaba JDK，其中的虚拟机常被称为 TaobaoVM 或 AJDK，用来支撑高并发的电商、支付和物流场景。它在 HotSpot 上做了服务器向的定制，例如 GCIH：把生命周期很长的对象移到堆外，收集器不扫描这块区域，从而减少回收频率；这块区域里的对象还可以被多个虚拟机进程共享。另外还有用 CRC32 指令做内部方法、降低 JNI 开销，以及面向硬件性能计数器的诊断。公开材料里还提到过面向大数据负载的 ZenGC。这些优化绑在特定处理器能力上，换平台就要重新评估，淘宝和天猫曾用它替换官方 JDK。

### Dalvik

Dalvik 由 Google 开发，用在 Android 上，Android 2.2 加入了即时编译。它不遵循 Java 虚拟机规范，不能直接执行 Class 文件，指令模型是寄存器而不是操作数栈，跑的是 dex 文件。dex 可以由 class 文件转换而来，应用仍用 Java 语法编写，并能使用大部分 Java API，所以它是虚拟机，但不是规范意义上的 Java 虚拟机。Android 5.0 用支持提前编译的 ART 替换了 Dalvik。

### GraalVM

2018 年 4 月，Oracle Labs 公开 GraalVM，口号是让程序在更多地方跑得更快，和 1995 年“写一次、到处运行”的方向相呼应。它在 HotSpot 之上做成跨语言的运行平台，覆盖 Java、Scala、Groovy、Kotlin，以及 C、C++、JavaScript、Ruby、Python、R 等。不同语言可以互相调用对象，也可以使用已经编译好的本地库。

实现上，它把源码或中间形式通过解释器转成 Graal 能优化的中间表示。Truffle 用来快速做一种新语言的解释器，运行期再做即时编译。即便 HotSpot 的位置在未来被替代，Graal 这条线的可能性最大，而 Java 已有的类库生态并不需要因此推倒。

## 参数

这一章还没有进入某一块内存的调优，但可以用下面的方式确认“现在跑的是哪一台虚拟机、哪一版 JDK”。

```text
java -version
java -XshowSettings:vm -version
```

`-XshowSettings:vm` 会打印堆的初始值和最大值等虚拟机摘要。第一行里的版本号决定了后面章节哪些标志还存在：JDK 8 的 `-XX:+PrintGCDetails` 在 JDK 9 之后要改成 `-Xlog:gc*`。不要把旧教程里的永久代开关写进 JDK 11 的启动脚本。

## 易错点

- “一次编译”编译的是字节码，不是当前机器的可执行文件。换了操作系统仍要安装对应平台的虚拟机。
- 默认虚拟机是 HotSpot，不代表所有 Java 产品都是它。Android 的 ART、OpenJ9、Zing 的区域和收集器都不能用 HotSpot 的默认值去套。
- JRockit 没有解释器，所以“虚拟机都是先解释再编译”只适用于 HotSpot 这条线。
- JDK 8 没有元空间之前的永久代开关不能继续沿用。`-XX:PermSize` 在 JDK 8 起已经无效。
- 收购和开源的时间线不等于收集器的默认值。G1 在 JDK 7u4 可用，到 JDK 9 才成为默认；JDK 8 的默认收集器仍是吞吐优先的 Parallel。
