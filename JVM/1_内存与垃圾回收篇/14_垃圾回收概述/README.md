# 垃圾回收概述

## 概念

这一篇把注意力放在运行时内存怎样分出去、又怎样收回来。前面几章把堆、方法区、直接内存的边界划清了，回收器真正动手的地方，主要就是这些还会增长的区域。

## 什么是垃圾

先把语言之间的差别说清楚。C 和 C++ 把释放的时机交给程序员：`new` 与 `delete`、`malloc` 与 `free` 成对出现。Java 把不可达对象的回收交给收集器，程序员负责把引用关系写对。动态分配这件事很早就有，1960 年前后的 Lisp 已经同时使用动态内存和自动回收。收集器要回答的仍然是那三个问题：哪些内存是垃圾，什么时刻回收，用什么算法回收。

自动回收显著降低了业务代码的心智负担，也因此成为后来许多语言的默认配置。设备从嵌入式到大堆服务器，对象的寿命分布差得很远，所以收集器一直在换实现。面试里它也是高频题，因为参数、停顿和吞吐能直接对上生产故障。

### 什么是垃圾？

垃圾是运行中已经没有任何引用链能够到达的对象。它占用的堆空间若一直留着，后来的分配就无法复用这块地址；垃圾堆积到申请失败，就会表现为内存溢出。及时收回的是“不会再被程序碰到”的对象，而不是程序员觉得“应该没用了”但引用还挂在静态集合里的对象。

### 和磁盘碎片的类比

机械磁盘用久了，文件被拆到不连续的扇区上，读一次要来回寻道，所以会做碎片整理，坏道则是介质本身的损伤。堆也有类似现象：标记清除之后，空闲空间变成许多小洞，总字节数够、却找不到一块连续区间放下大数组。整理类算法所做的事，很像把仍在使用的对象挪到一端，让空闲空间重新连成一片。坏道没有对应物，堆上的问题是逻辑碎片，不是物理损坏。

### 面试里常被追问的点

下面按公司做过的追问改写成检查清单，用来核对自己能不能把过程和取舍讲完，而不是背原题。

#### 蚂蚁金服

范围铺得比较开：收集器有哪些、各自牺牲了什么；CMS 和 G1 必须能对比；现行 JDK 默认更接近哪一类算法；G1 的一轮回收怎么走；为什么需要 GC；判断死亡用哪两类办法。

#### 百度

问法更收束：把常见算法说一遍，再单独把分代讲清楚，并说明策略如何落到算法上。

#### 天猫

会问回收的原理、CMS 的特征、几种算法的短处，以及这些短处有没有共同点：都要处理可达性，也都要面对停顿或碎片。

#### 滴滴

关注有哪些收集器、G1 适合什么延迟目标，以及年轻代和老年代日常怎样搭配。

#### 京东

会追到 CMS 与 G1 的步骤、优点和失败路径，并要求算法不是只报名字，而是能解释实现要点。

#### 阿里

问法偏决策：算法本身、什么条件下会触发回收、面对一种业务该怎么选；有时也会把收集器收成几类来问。

#### 字节跳动

覆盖面最杂：算法优劣、`System.gc()` 与 `Runtime.getRuntime().gc()` 实际做了什么、GC Roots 有哪些、对象怎样被判定并回收、CMS 要解决的矛盾、回收过程里为什么会有两次停顿。

## 为什么需要 GC

高级语言如果只分配、不回收，堆迟早会被活对象和垃圾一起占满。这和只产生生活垃圾、从不清运是同一类问题。回收器还有第二项工作：把碎片收拢。存活对象被挪到堆的一侧之后，分配器又可以用指针碰撞，而不是在空洞里搜索。

业务规模变大以后，没有自动回收，服务无法长期运行。回收若经常把所有用户线程停住，又会变成延迟故障，所以收集器的演进主线一直是：在吞吐、停顿和内存占用之间重新分配成本。

## 早期的手工回收

C/C++ 时代，申请和释放都写在业务路径上。下面用完全不同的类型名示意：

```cpp
RouteNode* node = new RouteNode();
if (node->attach(kDetach) != kOk) {
    delete node;
}
```

释放点可以精确卡在失败分支上，但每一条路径都要记得配对。漏掉一次，对象就永远留在进程里，运行时间越长，占用越高，最后把进程撑垮。多释放一次，则会碰到悬空指针。

换成自动回收之后，失败分支往往不再手写 `delete`，对象只要变得不可达就会在某一轮收集中被处理：

```cpp
RouteNode* node = new RouteNode();
node->attach(kDetach);
```

Java、C#、Python、Ruby 都走了自动管理这条路。分配仍由语言运行时完成，释放的时机改由可达性决定。这已是这类语言的基础设施，而不是可选库。

## Java 的垃圾回收机制

### 优点

内存的申请和收回不再逐行出现在业务代码里，泄漏和溢出的一类低级错误会少很多。没有收集器的话，Java 一样会面对悬空引用、野指针和忘记释放。自动管理把程序员从配对 `free` 里解放出来，时间可以放回领域逻辑。需要核对某个 JDK 的收集器行为时，以该版本的官方虚拟机调优说明为准，不要拿另一主版本的默认值硬套。

### 担忧

自动并不等于可以不理解。把收集器当成黑盒，一旦出现溢出，就只剩猜测。最糟的结果是现场只看到错误类型，却说不清是堆太小、泄漏，还是元空间被类撑满。

因此要知道虚拟机怎样分配、怎样判定死亡、怎样选择收集器。见到 `OutOfMemoryError` 时，才能根据日志里的区域名字和 GC 原因往下切。当溢出、泄漏或停顿成为容量瓶颈时，还得对这条“自动”路径做监控和参数调整，而不是只把堆调大。

### GC 主要盯住哪些区域

收集器的工作集中在堆，以及方法区里那些可以卸载的部分。程序计数器、虚拟机栈、本地方法栈随线程和栈帧自然消长，不靠 GC 扫描。

同一套收集器可以只收年轻代，也可以收老年代，还可以做整堆收集，并顺带处理方法区。从频率看：年轻代最常收，老年代少很多，永久代或元空间更少，因为类卸载的条件苛刻。堆是收集器的主战场。
