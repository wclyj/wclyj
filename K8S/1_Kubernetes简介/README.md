# Kubernetes 简介

## 来源

术语和对象模型以 Kubernetes 官方文档为准。下文把同一套概念按安装、工作负载、暴露方式、权限和存储这条线重新串了一遍，方便对照后面的实验章节。

## 介绍

Kubernetes 常被写成 K8s：首字母 K 与末字母 s 之间恰好隔着 8 个字母。它负责在多台机器上安排容器，而不是替代容器运行时本身。

## 前置知识

动手前建议先熟悉两件事。

- Linux 上的进程、网络和 systemd
- 镜像、容器以及如何用 Docker 或 containerd 把进程跑起来

## 课程简介

- 先建立集群由谁做决定、工作节点如何干活的图景
- 再从空机器装出一套能 `kubectl` 的环境
  - kubeadm 路径短，适合先跑通
  - 二进制路径把每个控制面进程拆开，便于看证书和启动参数
- 随后是日常会反复碰到的对象
  - Pod：调度与重启的最小单位，别的工作负载都围着它转
  - 控制器：按期望副本数纠偏，覆盖无状态、有状态、一次性任务、定时任务和每节点守护进程
  - Service 与 Ingress：给一组 Pod 稳定入口
  - RBAC：谁能对哪种资源做什么
  - Helm：把多份清单打成可版本化的包
  - 卷：让容器重建后数据还在
- 后面再用指标系统看容量，把控制面做成多副本，并走一遍业务镜像的交付

## K8S 概念和特性

### 部署发展历程

业务上线方式大致换过三次。

早期把进程直接放在物理机上。机器的 CPU 和内存并不按应用切开，某个进程吃满资源时，同机的其它进程一起变慢。若每种程序独占一台机器，空闲又很明显，机房成本抬得很高。

后来用虚拟机把一台物理机切成多台“完整电脑”。每个虚拟机自带内核和系统盘，应用之间隔开，加机器也比买硬件快。代价是每台虚拟机都要背一份操作系统，启动和镜像体积都偏重。

容器继续往下收：进程仍被隔离开，但共享宿主机内核，只携带应用和它依赖的文件。因此镜像小、启动快，同一份镜像可以从笔记本挪到测试环境再挪到云上。它和虚拟机一样拥有自己的文件系统视图、CPU 份额、内存上限和进程空间，只是不再为每个应用复制一整套内核。

容器因此常被拿来做交付单元，常见好处包括：

- 镜像构建比虚拟机模板轻，应用可以更快打出一版
- 镜像内容不可变，出问题可以退回上一层摘要
- 构建阶段就把运行所需文件封进镜像，部署阶段不再在机器上现装依赖
- 除了宿主机指标，还能按容器采集探针和业务指标
- 开发机、测试集群和生产集群跑的是同一份镜像
- 不绑死某家云或某一种发行版，只要运行时兼容即可
- 管理对象从“一台虚拟硬件上的系统”收成“一组逻辑资源上的进程”
- 服务可以拆小，按副本增减，而不是挤在一台巨型进程里
- 资源上限写进规格后，性能更容易预估

### K8S 概述

在容器成为交付单位之后，还缺一个跨主机的调度器：镜像放哪台机器、挂了谁拉起、扩容时副本怎么铺开、配置和存储跟谁走。Kubernetes 就是这件事的开源实现。它在 2014 年由 Google 公开发布，目标是把容器应用的部署、滚动替换、故障拉起和容量调整收成声明式操作，而不是在每台机器上跑一套安装脚本。

脚本安装的问题在于，应用的生命周期粘在当前系统上，升级和回退都要人盯着。虚拟机可以隔离，但太重，搬迁成本高。容器把进程和根文件系统从宿主机拆开，彼此不能随便看见对方的文件，计算资源也能分开计算。

可以把它收成三句话：用声明式 API 描述想要的副本；由控制面持续把实际状态往期望状态推；扩容时改数字，而不是手工登录新机器。

### 平台定位

它是一个可扩展的容器编排平台，不负责编译代码，也不替代镜像仓库。一组相关容器会被收进同一个逻辑单元，方便统一调度、发现和更新。项目吸收了 Google 内部大规模运行容器工作负载的经验，再叠加社区后来补上的接口（CRI、CNI、CSI）。

### K8S 功能

#### 自动装箱

调度器读取每个容器声明的 CPU、内存请求，在还有余量的节点上落位。人不需要先挑好某台机器的 IP。

#### 自我修复

容器异常退出时，按重启策略重新拉起。节点失联或资源不够时，副本会被安排到其它节点。存活探针失败则杀掉容器再重建；就绪探针失败时，这个 Pod 会从 Service 的端点列表里拿掉，恢复之前不接流量。

画面上可以想成：左边一台机器上的进程不再应答，控制面在右边另一台机器上补一个同样规格的 Pod。节点本身不需要人去点“迁移”。

#### 水平扩展

副本数可以用命令、面板或按 CPU 的自动伸缩来增减。请求堆高时把同一套无状态 Pod 从 2 个调到 6 个，前面的 Service 会把新 Pod 算进转发目标。

#### 服务发现

一组 Pod 的 IP 会变，调用方不应写死。Service 给它们一个稳定的虚拟地址和 DNS 名，并在后端之间分摊连接。可以把它理解成集群内部的固定门牌，而不是再外挂一套独立的注册中心。

#### 滚动更新

替换镜像时按批次起新 Pod、停旧 Pod。新副本没有就绪就不会把旧副本全部拆掉，从而避免整组服务同时中断。

#### 版本回退

每次变更都留下修订号。新版本指标异常时，可以把工作负载指回先前的模板，效果类似版本管理里的回退，只是对象是 Pod 模板而不是 Git 提交。

#### 密钥和配置管理

配置和口令放在 ConfigMap、Secret 里，以环境变量或文件挂进容器。改配置通常只要滚动重启 Pod，不必把口令重新打进镜像。

#### 存储编排

有状态进程需要在重建后看到同一份数据。卷可以把本地目录、NFS、Ceph 或云盘挂到容器路径，具体后端由存储类和卷对象描述。

#### 批处理

除了常驻服务，还可以跑跑完即停的任务，以及按时间表重复触发的任务，用来做汇总、清理和报表。

## K8S 架构组件

### 完整架构图

文字版可以把集群画成上下两层。上层是控制面，通常叫 Master 或 control plane，只负责决策和存储期望状态，不跑业务容器。下层是工作节点，真正起容器。用户、面板和 CI 都只跟 API 说话，不直接 SSH 到节点改容器。

控制面里四块紧挨着：

- API 进程是唯一入口，校验请求后把对象写入 etcd
- 调度器盯着还没绑定节点的 Pod，挑选一台合适的机器并写回绑定结果
- 控制器进程里住着许多小循环，各自负责一种资源，发现实际数量偏离期望就补齐或删掉
- etcd 保存集群数据，丢了它就丢了“期望状态”

工作节点上三块：

- kubelet 接收分配给本机的 Pod，调用运行时创建容器，并上报状态
- kube-proxy（或等价的数据面）维护 Service 的转发规则
- 容器运行时按 CRI 接口起停容器

日志采集常以每节点一个代理的形式存在，例如 Fluent Bit，把容器标准输出送到集群外的存储。它不是调度必需品，但没有它就只能上机器翻文件。

### 架构细节

控制面对外提供集群操作，节点只执行落到本机的那一部分。

- **控制面**
  - kube-apiserver：REST 入口，同时处理认证、授权、准入和 API 注册；对象落到 etcd
  - kube-scheduler：为新建 Pod 选择节点
  - kube-controller-manager：后台纠偏，一种资源对应一类控制器
  - etcd：一致的键值库
- **工作节点**
  - kubelet：本机代理，保证容器跑在 Pod 里，并衔接存储插件和网络插件
  - kube-proxy：维护访问 Service 时用的转发
- **容器运行时**
  - 真正创建容器的程序
  - 常见实现有 containerd、CRI-O，以及仍可通过适配层使用的 Docker；只要实现 CRI 即可被 kubelet 调用
- **日志代理**
  - 以守护进程形式跟在每个节点上，把容器日志收走

## K8S 核心概念

### Pod

- 集群里能调度的最小单位
- 里面可以放一个或多个容器
- 这些容器共享网络命名空间，互相用 localhost 通信
- 单个 Pod 不保证永远在，节点重启或被驱逐后，名字和 IP 都会换

### Volume

- 在 Pod 规格里声明一块可挂载的目录
- 同一块卷可以挂进该 Pod 的多个容器
- 后端可以是节点本地盘、分布式存储或云厂商磁盘

### Controller

控制器盯着 Pod 数量和身份：

- ReplicaSet 维持副本个数
- Deployment 管无状态服务，副本可互换，不依赖固定网络身份
- StatefulSet 管需要稳定名字和稳定盘的进程，例如数据库主从
- DaemonSet 保证选定节点上各有一份
- Job、CronJob 分别对应跑完即停和按日历重复

### Deployment

- 声明副本数、Pod 模板和发布策略
- 下面的 ReplicaSet 负责把失败的 Pod 补回来
- 更新时按策略滚动，保留旧修订以便回退

发布时控制面会先按新模板起一份，就绪后再收缩旧副本，而不是把全部 Pod 同时换掉。

### Service

- 用标签选出一组 Pod，给它们一个稳定访问方式
- 后端 IP 变化时，调用方仍用 Service 的地址
- 常见类型有 ClusterIP（仅集群内）、NodePort（节点端口）、LoadBalancer（云负载均衡）

它把多个副本合成一个入口，本身不包含业务进程。

### Label

标签是挂在对象上的键值对，用来筛选和关联。Service、ReplicaSet 都靠选择器匹配标签，而不是靠写死 Pod 名字。

### Namespace

命名空间是集群内的逻辑边界，常用来分环境、分团队和套配额。

- 权限和资源额度可以按空间切开
- 几乎每个对象都属于某个空间
- 同一空间内同类对象不能重名
- 不同空间允许同名

### API

所有操作最终都是发给 API 进程的 HTTP 请求，正文多用 JSON 或 YAML。kubectl、面板和 curl 只是不同的客户端。集群里的对象都可以落成一份清单。

例如一份最小的 nginx Pod 会写明 `apiVersion`、`kind: Pod`、名字，以及容器镜像和端口。提交之后，API 进程校验并保存，调度器和 kubelet 再各自接力。

## 完整流程

以创建副本控制器再暴露服务为例，链路是这样的：

1. 客户端提交一份副本控制器对象，API 进程把它写入 etcd。
2. 控制器管理器监听到这个新对象，发现还没有对应的 Pod。
3. 它按模板补出 Pod 记录，再次经 API 写入 etcd。
4. 调度器看到未绑定节点的 Pod，打分后选定一台机器，把节点名写回去。
5. 目标节点上的 kubelet 读到分配结果，调用运行时把容器拉起来，并持续上报状态直到 Pod 被删除。
6. 随后提交一个 Service，选择器指向这组 Pod 的标签。
7. 端点控制器找出匹配的 Pod 地址，写成 Endpoints（或 EndpointSlice）。
8. 各节点上的代理监听 Service 和端点，在本机装好转发规则，访问 Service 的流量就被送到后面的 Pod。
