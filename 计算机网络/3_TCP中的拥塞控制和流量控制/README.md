# TCP 中的流量控制和拥塞控制

## 流量控制

### 什么是流量控制

流量控制关心的是发送方和接收方这一对端点。发送方若持续以超过接收方处理能力的速度灌数据，接收缓存会被塞满，多出来的段只能丢掉，然后再靠重传补回来。让发送节奏跟得上接收能力，就是流量控制。它是 TCP 可靠性的一部分，目标是少丢段，而不是去猜测整条路径堵不堵。

### 如何实现流量控制

实现手段是滑动窗口，和连续 ARQ 结合在一起。接收方在 ACK 里携带自己当前的接收窗口 rwnd，告诉对方“我还能再收多少字节”。发送方的发送窗口不能超过这个值。窗口为零时，发送方停止推进，等待窗口更新；为避免双方互相干等，发送方之后会用窗口探测段询问窗口是否已经恢复。

窗口滑动还保证了按序、不丢、不重复：已确认的字节从窗口左缘划出，新的可发送字节从右缘补入。

## 拥塞控制

### 什么是拥塞控制

拥塞控制关心的是路径上的网络，而不是某一台接收主机的缓存。若过多发送方同时向网络注入数据，路由器队列溢出，延迟和丢包会一起上升。TCP 用一组算法约束自己的发送量：

- 慢开始
- 拥塞避免
- 快重传
- 快恢复

### 拥塞控制算法

为了把窗口变化讲清楚，先约定一个简化场景：数据只向一个方向发送，反向只回 ACK；接收方缓存足够大，因此发送窗口主要由网络拥塞程度决定，而不是由 rwnd 先卡住。实际发送窗口会取拥塞窗口和接收窗口中的较小者。

#### 慢开始算法

发送方维护拥塞窗口 cwnd。它随网络状况变化，不是一个固定配置。慢开始的想法是：连接刚建立时不要立刻发一大批数据，先从一个较小的窗口试探。

讲解时常用“报文段个数”当单位，真实实现以字节计。初始 cwnd 往往只有 1 个或少数几个 MSS。每收到一个对新数据的确认，cwnd 就增加约 1 个 MSS。一个往返时间 RTT 内，窗口里的段都会被确认，于是每过一个 RTT，cwnd 大约翻倍，呈现指数增长。

指数增长不能一直持续。发送方还有一个慢开始门限 ssthresh：

- cwnd < ssthresh：继续慢开始
- cwnd = ssthresh：慢开始或拥塞避免都可以
- cwnd > ssthresh：改用拥塞避免

#### 拥塞避免算法

进入拥塞避免后，每个 RTT 只把 cwnd 增加大约 1 个 MSS，也就是线性增长，不再翻倍。实现上常常是每收到一个 ACK，cwnd 增加 `MSS * MSS / cwnd`，凑满一个 RTT 后大约加一个 MSS。

无论当前处于慢开始还是拥塞避免，一旦发送方判定发生拥塞（经典判据是超时），就把 ssthresh 设为当时窗口的一半，且不小于 2 个 MSS，再把 cwnd 重置为 1 个 MSS，重新慢开始。目的是立刻减少注入网络的数据量，让路由器把积压队列排空。

用一组具体数字可以把曲线走一遍：

- 初始 cwnd = 1 个段，ssthresh = 16
- 慢开始按指数涨到第 4 个 RTT，cwnd 达到 16，与门限相等，此后改走拥塞避免，窗口线性上升
- 假定 cwnd 涨到 24 时发生超时，新的 ssthresh = 12，cwnd 回到 1，再次慢开始；涨回到 12 时重新进入拥塞避免

**乘法减小和加法增大**

- 乘法减小：一旦判定拥塞，门限立刻变成当前窗口的一半。网络反复拥塞时，门限会降得很快，从而迅速减少发送量。
- 加法增大：拥塞避免阶段窗口每次只加一点，避免刚恢复就再次冲高。

两者合称 AIMD。超时之后把 cwnd 拉回 1 再慢开始，是早期 Tahoe 风格的做法。

#### 快重传算法

若只靠超时才重传，发送方要空等一个重传定时器，吞吐会下降。快重传要求接收方在收到失序段时立刻再发一次对已连续收到的最后一个字节的 ACK，也就是重复确认，而不必等到自己有数据要捎带。

发送方连续收到三个重复 ACK，就认为其后的那个段已经丢失，立刻重传，不必再等定时器到期。三个而不是一个，是为了把偶然乱序和真正丢段区分开。

#### 快恢复

快重传通常和快恢复一起用，也就是 Reno 的行为，目前仍是最常见的基线：

- 连续三个重复 ACK 时，执行乘法减小，ssthresh 降为当前 cwnd 的一半，用来防止真正拥塞继续恶化
- 紧接着并不把 cwnd 打回 1。能收到一串重复 ACK，说明后续段仍在到达，路径并没有完全堵死，于是把 cwnd 设为减半后的 ssthresh，直接进入拥塞避免，让窗口缓慢回升

因此，采用快恢复时，慢开始主要出现在连接刚建立，以及发生超时时。超时比三个重复 ACK 更强烈地暗示网络已经严重拥塞，所以才重新从很小的窗口探路。
