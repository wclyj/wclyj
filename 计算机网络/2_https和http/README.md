# HTTP 与 HTTPS

## HTTP

HTTP 是应用层的请求—响应协议，本身不记住跨请求的会话。一次交互通常是：客户端发出请求，服务器给出响应，若没有额外的保持连接约定，这一轮就结束。服务器不会因为协议本身就记得“刚才是哪一台客户机”。

所谓无状态，指的是协议不在连接里保存业务会话，不是说 TCP 下面一定没有连接。HTTP/1.1 默认可以在一条 TCP 连接上连续发送多个请求，但每个请求仍要自带理解它所需要的信息。登录态、购物车这类“记住用户”的能力，要靠 Cookie、令牌或服务端会话另做。

## HTTPS

HTTPS 是跑在 TLS（历史上常称为 SSL）之上的 HTTP。它的目标是让信道上的窃听者看不到正文，并让客户端能核对服务器身份。浏览器访问 HTTPS 站点时使用端口 443。

建连可以分成下面几步理解。

### 获取连接证书

客户端先完成 TCP 三次握手，随后开始 TLS 握手。它会送出自己支持的协议版本和密码套件。服务器选定一套算法，并把自己的证书发回来。证书里包含站点域名、申请证书的组织、服务器公钥，以及颁发者的签名。

### 证书验证

客户端查看是哪一家证书颁发机构签的名，用本机或操作系统里预置的该机构公钥核验签名。同时还要核对证书里的域名是否就是正在访问的主机名，并检查有效期与吊销状态。任何一项失败，都不应该继续把后续密钥材料交给这台服务器。

### 数据加密和传输

证书通过校验后，双方协商出对称密钥。常见做法是：客户端生成预主密钥，用服务器公钥加密后送出；或者使用基于椭圆曲线的密钥交换，双方各自拿出临时公钥，算出相同的共享秘密。服务器用自己的私钥完成对应的解密或运算。此后大量应用数据改用对称加密传输，因为对称算法比公钥运算快得多。

对称加密指加密与解密使用同一把密钥。微信小程序的业务数据加密里也能看到对称算法，但那是应用层自己的选择，和 HTTPS 记录层不是同一件事。

### 对称加密存在的问题

只使用对称加密时，双方必须事先拥有同一把密钥。若直接在未保护的网络上把密钥明文送过去，窃听者会和接收方同时拿到它，后面的密文就失去意义。

流程可以看成：

> 明文经过密钥变成密文；对端用同一密钥还原成明文。

困难不在算法本身，而在“第一把密钥如何安全送达”。

### 非对称加密

非对称算法使用成对的密钥。公钥可以公开，私钥只留在持有者手里。用公钥加密的数据，只有对应私钥能解开；私钥也可以用来生成签名，任何人都能用公钥验证签名，但无法伪造。

单独用非对称加密传全部网页内容会很慢，所以 HTTPS 只在握手阶段使用公钥运算来保护对称密钥的协商，正文仍然走对称加密。这样同时避开了“对称密钥无法安全分发”和“公钥算法太慢”两个问题。

只交换公钥仍不够。攻击者可以在中间把服务器公钥换成自己的公钥：客户端用假公钥加密，中间人用自己的私钥解开，再用真正的服务器公钥重新加密后转发。两端都以为在和对方直接通信。

### 证书机制

解决掉包的办法，是不要信任网络上随口传来的公钥，而信任由证书颁发机构签名过的证书。

- 服务器把自己的公钥和域名信息交给颁发机构申请证书。
- 机构用自己的私钥对证书内容做签名，把签好的证书交回服务器。机构的私钥不会离开机构。
- 客户端来连接时，服务器返回的是这张证书，而不是一个孤零零的公钥。
- 浏览器和操作系统预先保存了受信任机构的公钥。客户端用对应公钥验证签名，确认证书在运输途中没有被改掉，再核对域名。

签名验证通过，只说明“这把公钥确实属于证书上的那个域名”，随后才继续做对称密钥协商。中间人没有机构的私钥，换不了一张能通过验证的假证书。
