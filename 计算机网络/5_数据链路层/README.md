# 数据链路层

## 链路和数据链路

### 链路

链路是一段点到点的物理线路，中间不再插入交换节点。从一台主机到另一台主机的整条通路，往往由多段链路串起来，其中一段只是通路的组成部分。

### 数据链路

只有导线还不能可靠地传帧。还需要协议来规定成帧、寻址和差错检测，并把实现这些协议的硬件与软件加到链路上，才构成数据链路。个人计算机上，这块职责通常落在网卡（网络适配器）里。

对网络层来说，数据链路层像一条管道：送进去的是分组，在管道里看到的是一帧一帧的数据。

## 数据链路层的主要功能

点对点链路要完成的三件基本工作是：

- 封装成帧
- 透明传输
- 差错检测

局域网还要额外解决多个站点如何共享媒体。

## 封装成帧

封装成帧就是在一段数据前后加上首部和尾部，让接收方知道一帧从哪里开始、到哪里结束。首尾的首要作用是帧定界。

一种经典做法是用控制字符：SOH 表示帧开始，EOT 表示帧结束。若数据里恰好出现 SOH 或 EOT，接收方会把它们误当成边界。发送方要在这些控制字符前面插入转义字符 ESC，接收方把数据交给网络层之前再把插入的 ESC 删掉。这叫字节填充或字符填充。

若数据里本来就有 ESC，就在它前面再插入一个 ESC。接收方连续看到两个 ESC 时，丢掉前一个，把后一个当作普通数据。

面向比特的协议则用另一套办法：帧界是一个特殊比特模式，数据中出现会和帧界混淆的连续比特时，发送方插入一个额外的 0，接收方再删掉。PPP 使用的零比特填充就是这种思路。

## 差错控制

传输中比特会翻转，1 可能变成 0，0 也可能变成 1。一段时间内出错比特数占总传输比特数的比例称为误码率 BER。误码率和信噪比关系很大，噪声越强，误码率越高。

### CRC 循环冗余检验

CRC 是常用的检错算法。帧检验序列 FCS 是附加在数据后面的冗余码，CRC 是计算这段冗余码的一种方法，但不是历史上唯一用过的方法。

发送方选定一个生成多项式，对数据做模 2 除法，余数作为 FCS 接在帧尾。接收方用同一个多项式去除收到的比特串：

- 余数为 0，认为这一帧没有检出错误，接受它
- 余数非 0，认为出错，丢弃

CRC 不能指出是哪一位错了，也不能代替重传。只要 FCS 位数足够，它能检出常见的突发错误。检出错误之后如何恢复，是上层或重传协议的事。点到点的 PPP 只承诺把无差错的帧交给上层，出错的帧直接丢掉。

## 局域网的拓扑结构

局域网里常见的接法包括总线型、星型、环型和树型。早期以太网多台机器挂在同一根同轴总线上；现在的园区网几乎都是交换机为中心的星型，逻辑上仍保留以太网的帧格式。

## CSMA/CD

载波监听多点接入/碰撞检测是共享总线上的协调办法，名字拆开是三件事：

- 多点接入：许多计算机接在同一媒体上
- 载波监听：发送之前先听总线上有没有别人的信号
- 碰撞检测：发送过程中继续听，发现信号叠在一起就认定发生了冲突

## 碰撞检测

检测的具体办法是比较发送时线路上的信号电压。电压异常升高，说明两路信号叠到了一起。

使用 CSMA/CD 的传统以太网不能全双工，只能半双工交替发送。一个站开始发送后的一小段时间内，远端站的信号可能还在路上，碰撞仍可能发生。这段危险时间与传播延迟有关。

发生碰撞的站要立刻停止，发送一串干扰信号让所有站都知道冲突已经发生，然后等待一个随机时间再重试。基本退避单位常取一个争用期 2τ（τ 为端到端传播时延）。重传次数增加时，随机等待的范围按指数扩大。若连续重传 16 次仍然失败，就丢弃该帧，并向高层报告。

交换式以太网把每台主机接到交换机的独立端口上，端口可以全双工工作，CSMA/CD 在这种链路上不再被实际使用，但协议概念仍留在以太网的历史里。

## 以太网

只要采用载波监听、多点接入这套媒体共享思想，早期文献就把这类网络称为以太网。现在“以太网”更多是指 IEEE 802.3 的帧格式和速率族。

局域网的数据链路层曾被拆成两个子层：

- 逻辑链路控制 LLC
- 媒体接入控制 MAC

现行网卡只实现 MAC 子层。LLC 在 IP 网络里基本不再单独出现。

以太网向上提供的是不可靠的尽力交付。帧检验失败就丢弃，不在链路层重传，也不保证按序。可靠性若需要，由 TCP 等上层负责。

## 信道利用率

设帧的发送时延为 T0，传播时延为 τ，则

$$
a = \frac{\tau}{T_0}
$$

a 越小，同样一次往返里真正用来传数据的时间占比越高，信道利用率越容易做高。传播时延相对发送时延很大时，停等式协议会把大部分时间耗在等待上。

## 流量控制协议

### 单工停等协议

停等协议假设链路本身会检错，但发送方和接收方的速度可能不匹配。发送方发出一帧就停下来；接收方收好、交给网络层，再回一个确认。发送方收到确认才发下一帧。逻辑简单，传播时间远大于发送时间时效率很差。

### 连续 ARQ

自动请求重传允许发送方在窗口内连续发出多帧，不必每帧都停。

- 发送方：发完一帧后继续发后面的帧。若某个帧的确认在超时前到达，窗口向前滑动。若超时仍未确认，从该帧开始把后面已发出的帧一并重传。这就是回退 N 帧。
- 接收方：按序接收。遇到一个坏帧，把它和其后到达的帧都丢掉，直到发送方超时重传那个坏帧。接收方只按顺序向上交付。

### 停止等待协议和连续 ARQ 协议的问题

#### 停止等待协议

发送、停止、等待，一个往返只推进一帧。链路很长或速率很高时，性能不可接受。

#### 连续 ARQ 协议

- 未被确认的帧一次发得太多，中间一帧出错就要重传后面的一大串
- 序号空间要够大：一次想连续传 1024 帧，序号至少要 10 比特，头部开销上升
- 因此实际协议都会限制连续发送的帧数，也就是限制窗口

### 滑动窗口协议

滑动窗口是停等和无限连续发送之间的折中：未经确认的帧数量有上限。

- 发送方：只有落在发送窗口里的帧才能发送。收到确认后，左缘右移，空出新的序号。
- 接收方：只有落在接收窗口里的帧才接收。

出错时的处理取决于接收窗口宽度 Wr：

- Wr = 1：接收方只按序收帧，出错帧及其后的帧全部丢弃，不回确认，让发送方超时后从出错帧起回退重传。这就是回退 N。
- Wr > 1：接收方可以把出错帧后面那些仍然正确、且落在窗口内的帧暂存，但不交给网络层。发送方超时后只重传丢失的那一帧，然后从接收方尚未收到的位置继续。这就是选择性重传。等缺失帧补齐，接收方再按序把缓存的帧一起上交。
