# 死锁的产生与解决

死锁是一组线程或进程互相卡住：每个都握着别人需要的资源，又都在等别人先放开。没有任何外力时，这组执行流不会再向前走。

## 四个必要条件

四个条件同时成立，死锁才可能出现。缺任何一个，这种“互相等死”的局面就不会形成。

1. **互斥**。资源一次只能交给一个执行流，例如一把互斥锁、一台独占的打印机。
2. **占有并等待**。已经拿到一部分资源的执行流，不肯放开，同时还在申请新的资源。
3. **不可抢占**。资源只能由持有者自己释放，调度器不能把锁从它手里夺走。
4. **循环等待**。存在一个环：甲等乙握着的资源，乙等丙的，最后又有人等回甲。

四个条件是必要的。都满足也不代表此刻一定已经死锁，只说明结构上存在这种可能。

## 一个具体例子

账户服务里有两把锁，按账户号保护余额。线程 T1 要把钱从账户 7 转到账户 3，线程 T2 做相反方向。两个人都先锁自己的源账户：

| 时刻 | T1 | T2 |
| --- | --- | --- |
| 1 | 锁住账户 7 | |
| 2 | | 锁住账户 3 |
| 3 | 申请账户 3，被挡住 | |
| 4 | | 申请账户 7，被挡住 |

T1 占着 7 等 3，T2 占着 3 等 7。锁不能被抢走，两边都不会超时放弃，于是形成环。CPU 上甚至可以没有任何一个线程处于运行态，它们都在锁的等待队列里。

把资源换成外设也一样。进程 P 已占用扫描仪再去申请刻录机，进程 Q 已占用刻录机再去申请扫描仪，在不可抢占的前提下同样死锁。下面的讨论用账户锁，是因为它能对应到代码里的加锁顺序。

## 如何检测

检测不试图事先禁止等待，而是周期性地问：现在的等待关系里有没有环。

**单实例资源**用等待图。每个线程是一个结点，若 T1 正在等 T2 持有的锁，就画一条 T1 → T2。图里出现环，就是死锁。上面的例子会得到 T1 → T2 → T1，深搜或拓扑排序都能把这个环找出来。拓扑排序时，入度为 0 的结点表示“没人能挡住它”；反复删掉这种结点，最后还剩下结点，剩下的部分就在环上。

**多种资源、每种又有多份**时，等待图不够用，因为“等的是哪一类里的任意一份”。这时做多资源检测，维护三类数据：

- 每类资源一共有多少
- 每个线程已经占了多少
- 每个线程还要申请多少

先算出“还没分出去的数量”。找一个线程，它的剩余需求不超过当前剩余量，就假定它能跑完并归还全部占有。剩余量因此增加，再找下一个。所有线程都能这样假设跑完，当前状态是安全的；中途找不到这样的线程，就说明剩下的线程处于死锁。

检测可以放在申请资源失败时做，也可以定时做。太频繁会占用 CPU，太稀则发现得晚，已经死锁的线程会一直占着锁。

## 解除办法

发现环之后要让系统重新能往前走。常用的做法是破坏四个条件里的一个，或者在已经发生之后回收资源。账户转账这个例子，最稳妥的是事先避免环，而不是等死锁了再杀线程。

**按固定顺序加锁（破坏循环等待）。** 规定任何转账都先锁账户号较小的一方，再锁较大的一方。T1 从 7 转到 3，也要先锁 3 再锁 7；T2 同样先锁 3。后到的线程会堵在第一把锁上，先到的线程可以拿第二把锁并完成转账。环不再出现。顺序必须全局一致，有人按号、有人按“先源后目标”，检测就会再次看到环。

**申请失败就全部放开（破坏占有并等待）。** T1 若在已经持有 7 的情况下申请 3 失败，立刻放开 7，过一会儿再从零申请两把锁。这样不会握着资源睡觉。代价是可能活锁：两个线程反复拿到一把、发现第二把被占、又一起放开，谁都完不成。可以在重试前加随机退避。

**允许抢占（破坏不可抢占）。** 数据库里的做法是给事务设等待超时，超时后回滚其中一个，让它释放锁。被回滚的事务可以重做。选择牺牲谁时，优先选改动少、回滚代价低的那个，避免每次都牺牲同一个低优先级事务，否则会把它饿死。

**死锁已经形成时的恢复。** 若预防没做到，检测线程发现环之后可以：

1. 挑环上的一个线程，强制释放它的锁或直接撤销该线程
2. 把剩余资源退回“可分配”池，再次运行检测
3. 环消失后，让被挡住的线程继续；被撤销的线程由调用方重试

撤销之前要确认这个线程的副作用可以重做。已经把结果写进外部系统、又没有补偿操作时，不能简单杀掉。

银行家算法属于避免而不是事后解除：每次分配前假装分出去，再用上面的多资源检测看会不会进入不安全状态，不安全就拒绝这次申请。实现成本高，业务服务里很少手写；锁顺序和超时回滚更常见。

对前面的转账，采用“账户号小的先加锁”，再给锁等待加一个超时。顺序保证正常路径不产生环，超时用来兜住漏网的加锁路径。两者叠在一起，比只靠事后杀进程更可控。
