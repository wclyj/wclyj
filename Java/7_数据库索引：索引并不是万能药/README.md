# 索引是一棵要花钱维护的查找树

业务数据大多仍放在满足事务特性的关系库里。查询变慢时，第一反应常常是“给相关列都加上索引”。这会把写入、空间和优化器一起拖累。下面以 InnoDB 为例，看数据页、两类索引，以及优化器为什么有时拒绝使用已经建好的索引。

## 数据页里怎样定位一行

InnoDB 以页为读写单位，默认 16KB，用来减少按行随机打磁盘的次数。页和页串成双向链。页内的记录按主键连成单向链，另外有一块页目录：把记录分成若干槽，槽里记下这一小组的条数。最小槽和最大槽指向两条伪记录。有了槽，页内按主键查找可以二分，不用从最小记录一路扫到尾。

假设某页的槽指向的主键依次是 4、11、18、27、36、48，要找主键 28：

- 槽的下标从 0 到 5，中点是 2，槽 2 指向 18，小于 28，于是到右半边。
- 右半边中点落在槽 4，指向 36，大于 28，说明记录就在槽 3 这一组。
- 从槽 2 指向的 18 沿记录链向后走，经过 27，到达 28。

页目录只把一页里的查找从线性变成对数。表一旦跨很多页，还要一棵能定位“行在哪一页”的树。

## 聚簇索引与二级索引

这棵树是 B+ 树，画出来叶子在最底层：

- 叶子放数据，非叶子只放目录项。
- 每一层都把下一层的查找范围切开，降低每一层要比较的次数。
- 同一层节点按键有序，并串成双向链，范围扫描可以沿链走，不必回到根。

InnoDB 把整行存在聚簇索引的叶子上，所以聚簇索引既是数据又是按主键的目录。行在磁盘上只有一份，聚簇索引也就只有一棵。默认用主键当键；没有主键时，选第一个全表非空的唯一列；再没有，就生成一个隐藏的行号。

找主键 4：根上的目录指出它落在某一枝，沿中间节点再降一层到达叶子页，然后用页目录二分。树高通常是 3 或 4，所以几次页读取就能定位。

非主键列要加速，就另建二级索引，也叫辅助索引。它仍是 B+ 树，但叶子不存整行，只存索引列加上主键。拿到主键后再回聚簇索引取行，这一步叫回表。

例如按会员名建了二级索引，叶子上是 `(name, id)`。查名字 `b`，在二级索引上定位到若干叶子，得到主键 7 和 6，再拿这两个主键各做一次聚簇查找，才得到邮箱、注册时间等其余列。

## 多建一棵树要付的三种费用

每多一个二级索引，就多一棵要跟着变动的 B+ 树。插入一行时，聚簇索引要插，每棵二级索引也要插。页内记录按键有序，插到已满的页中间会引起页分裂：新开一页，把一部分记录搬过去。删掉很多行之后，又可能把过空的页合并。分裂和合并都是额外的页写入，极端时还会放大锁冲突。

用一张会员表做对照。列包括自增主键、姓名、积分和注册时间：

```sql
CREATE TABLE member (
  id BIGINT NOT NULL AUTO_INCREMENT,
  full_name VARCHAR(64) NOT NULL,
  points INT NOT NULL,
  registered_at TIMESTAMP NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;
```

用存储过程灌 10 万行。只有主键时，时间主要花在聚簇索引的插入和日志上。再加上下面两棵树，一棵是姓名加积分的联合索引，一棵是注册时间：

```sql
ALTER TABLE member
  ADD KEY name_points (full_name, points),
  ADD KEY registered_at (registered_at);
```

同样灌 10 万行，耗时会上升，因为每行要维护三棵树。上升幅度跟磁盘、日志刷盘和行有多宽有关，不要背一个固定秒数，用同一台机器前后对比即可。

页分裂可以用一个很小的页来想象。假设一页只能按主键放下 4、11、18 三行，此时再插入 12。12 必须排在 11 和 18 之间，页已经满了，于是拆成两页，例如一页留下 4 和 11，另一页拿走 12 和 18，父节点增加一个目录项指向新页。这次插入因此写了两页数据页外加父页，而不是只写一行。若插入顺序就是主键顺序，新行总是追加在最右页，满了就新开一页，很少把旧页拆开。随机主键或随机的二级索引键则会不断从页中间插入，分裂更频繁。二级索引的键若是无序字符串，写入放大比自增主键明显。删除把页抽空之后，合并又是一次额外的页写入。灌数测试若按主键顺序插入，看到的写入成本会低于真实业务里按姓名随机插入。

空间上，二级索引虽不存整行，却要存索引列和主键。查 `information_schema.TABLES` 的 `DATA_LENGTH` 与 `INDEX_LENGTH` 就能看到：索引占用经常接近甚至超过数据本身，尤其索引列是长字符串时。

```sql
SELECT DATA_LENGTH, INDEX_LENGTH
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'member';
```

第三种费用是回表。`SELECT * FROM member WHERE full_name = 'm1'` 的执行计划里，`key` 会显示 `name_points`，`type` 多半是 `ref`，表示二级索引上等值匹配。但叶子上没有其余列，引擎还得拿主键回聚簇索引。把选择列表收成联合索引已经包含的列：

```sql
EXPLAIN SELECT full_name, points FROM member WHERE full_name = 'm1';
```

`Extra` 里出现 `Using index`，说明结果从二级索引就能组装，不必回表。联合索引的叶子按第一列排序，第一列相同再按第二列排序，所以这两列加上主键都已经在叶子上。这种情况叫覆盖索引。

实践上可以收成三条：

- 不要在建表时把能想到的列都索引。等查询、排序、分组的字段稳定，或者行数过万且语句变慢，再按语句加。加完用 `EXPLAIN` 核对是否真的被选中。
- 优先索引窄列。能用整数就不要用长字符串；长字符串可以只索引前缀。全文检索交给专门的检索引擎，而不是在 `VARCHAR(255)` 上堆 B+ 树。
- 查询列出需要的列。若这些列能被一棵联合索引覆盖，就同时得到查找加速和免回表。

## 列上有索引，语句仍可能全表扫

有了 ` (full_name, points) ` 之后，只写姓名条件通常还能用上最左列。但这不表示“列出现在索引里，优化器就一定走它”。

前缀才能比较。索引按完整键排序，`LIKE '%m123'` 要从中间或末尾匹配，无法沿树下降，`type` 成为 `ALL`。把通配符放在右边，`LIKE 'm123%'` 是一个范围，`type` 多为 `range`，`key` 指向这棵联合索引。如果业务永远按后缀查，可以把反转后的字符串另存一列再索引，查询时先把用户输入反转。

函数包住列也不行。`WHERE CHAR_LENGTH(full_name) = 7` 要的是计算后的值，树上存的是原值，只能扫。真要按长度查，就增加一个生成列保存长度，再索引那个生成列。

联合索引只服务从最左列开始的连续前缀。只写 `points > 45000`，第一列没有约束，积分在树上不是全局有序的，计划往往是全表扫描。补上姓名的前缀条件后，同一棵 `name_points` 就能用。姓名写在 `WHERE` 的第几个位置不重要，优化器会重排条件；重要的是条件能不能构成最左前缀。

回到两个选择：

- 建了不等于会用。至少有三类肯定用不上：非前缀匹配、对列做函数或表达式、联合索引跳过了左边的列。即便语法上能用，优化器还可能因为成本拒绝它。
- 多个列经常一起出现在条件里，优先联合索引，覆盖的机会也更大。若语句永远只查其中单独一列，单独的索引更瘦，不必为用不到的列付出维护费用。区分度高的列放在联合索引左侧，否则左边一列几乎不筛选，右边的列也帮不上忙。

同一组列，顺序不同，能服务的语句就不同。`(full_name, points)` 能服务“姓名等于某值”，也能服务“姓名等于某值并且积分大于某值”，不能服务“只限制积分”。若报表永远是按积分区间扫描、姓名只是附带展示，这棵树帮不上，应该另建积分单独的索引，或者把积分放在左侧。把两条语句都 `EXPLAIN` 一遍，比争论顺序有用：

```sql
EXPLAIN SELECT id FROM member WHERE points > 45000;
EXPLAIN SELECT id FROM member WHERE full_name = 'm1' AND points > 45000;
```

第一条在只有 `(full_name, points)` 时通常是全表或另走别的索引；第二条才能在这棵树上做等值加范围。范围条件一旦用在某一列上，它右边的列就不再作为查找键，只能当作覆盖列。所以把等值列放左边、范围列放右边。

长字符串还可以只索引前缀，例如姓名的前 16 个字符。前缀越短，树越瘦，区分度也越差，优化器可能仍然放弃它。用 `EXPLAIN` 看 `key_len` 能确认实际用了多长。前缀索引一般不能覆盖整列的查询，因为叶子上没有完整的字符串，选了这一列仍要回表。

## 优化器在给每种走法估价

一条语句可以全表扫聚簇索引，也可以走某棵二级索引再回表。InnoDB 不是按 `WHERE` 里列的书写顺序挑的，而是给每种访问路径算成本，选更低的那个。

成本粗分成两块。默认模型里，读一页的代价常数是 1，评估一行是否符合条件的代价常数大约是 0.2。全表扫描的代价就是“聚簇索引页数 × 1 + 行数 × 0.2”。

这些数字来自统计信息，不是每次精确点数。`SHOW TABLE STATUS LIKE 'member'` 能看到估算行数和数据长度。行数和真实的 10 万可能差几十到几百。数据长度除以 16KB 约等于聚簇索引页数。统计过期时，`ANALYZE TABLE` 可以重算，但估算永远是估算。

举一个按这个常数手算的例子。假设估算 10 万行、数据长度约 4.8MB，页数约 `4800000 / 16384 ≈ 293`。全表扫描成本约 `293 + 100000 * 0.2 = 20293`。二级索引若要回表 2.5 万行，光回表的行评估成本就是 5000，再加二级索引自身的页读取和回表的随机页，很容易超过 2 万。于是优化器会留下全表扫描，哪怕姓名和注册时间上都有索引。

把范围收窄到只剩一万行以内，二级索引加上回表的成本降到全表扫描之下，计划就改走索引。收窄哪一列，走哪一棵树，由算出来的行数决定，不由列在语句里的先后决定。

统计或成本模型和真实分布差得太远时，才会手工干预：

```sql
EXPLAIN SELECT id, full_name
FROM member FORCE INDEX (name_points)
WHERE full_name > 'm80000' AND registered_at > '2024-05-01 00:00:00';
```

`FORCE INDEX` 是纠偏，不是常规写法。数据分布一变，强制的路径可能变成最差路径。

手算时把范围收窄再比一次，就能看见切换点。仍用“读一页代价为 1、评估一行代价为 0.2”。全表 10 万行、约 293 页，成本约 20293。若注册时间的范围只命中 8000 行，二级索引自身假设要读 20 页，回表若比较散，可能再读数千页。成本一旦落到 20293 以下，计划就会改走这棵时间索引，即使姓名上的条件也能用另一棵树。命中 8000 行但回表页数仍然巨大时，优化器可能继续全表扫描。这就是“列上有索引、范围看起来也不宽，计划仍是 `ALL`”的原因。看 `rows` 列的估算，再决定要不要更新统计信息，而不是先加上强制索引。

覆盖索引改变的是回表页数。只选 `id` 时，二级索引叶子上已经有主键，回表页数按 0 计，同样的 8000 行往往立刻比全表扫描便宜。`SELECT *` 把那些行又读了一遍聚簇索引，优势就消失了。所以同一条过滤条件，选择列表一变，计划就可能变，这不是优化器不稳定，而是成本里多了一截随机读。

想看每种候选的行数和成本，打开优化器跟踪：

```sql
SET optimizer_trace = "enabled=on";
SELECT id FROM member
WHERE full_name > 'm80000' AND registered_at > '2024-05-01 00:00:00';
SELECT TRACE FROM information_schema.OPTIMIZER_TRACE;
SET optimizer_trace = "enabled=off";
```

跟踪结果里每种索引会有 `rows`、`cost`、`chosen`。没被选中时 `cause` 常常是 `cost`。全表扫描作为 `access_type = scan` 出现。对比这几个数字，就能解释“为什么明明有索引却没走”，也能对照覆盖索引和回表：覆盖时访问路径上少了回表那一截成本。

## 收束

索引不是越多越快。每棵二级索引都要付维护、空间和可能的回表。联合索引建好之后，尽量让查询落在它已经保存的列上。

建了也不保证生效。后缀匹配、跳过左前缀、对列做函数，都用不上树。就算语法匹配，优化器仍会比较全表扫描和各条索引路径的成本。调优时以 `EXPLAIN` 或跟踪里的成本为准。只加索引、不看计划，写入变重了，查询却可能原样全表扫。

## 可以接着做的两个实验

第一个：对同一条按姓名等值的查询，一次 `SELECT *`，一次只选 `full_name, points`。分别看 `OPTIMIZER_TRACE` 里回表前后的 `cost`。覆盖那条应当少掉按主键随机读页的开销。

第二个：`EXPLAIN SELECT id FROM member ORDER BY registered_at LIMIT 20`。若 `Extra` 没有 `Using filesort`，说明排序直接沿 `registered_at` 索引的叶子链进行。`type` 常是 `index`，表示沿索引顺序读，不一定是按查找键定位。下面几种情况排序索引会失效，重新出现文件排序：排序方向和索引方向冲突又不能反向扫、`ORDER BY` 的列上包了函数、联合索引的排序列不是最左前缀、同时按两列排序但第二列不在同一棵索引的后续位置上。

再补一条对照就能看见文件排序出现：

```sql
EXPLAIN SELECT id FROM member ORDER BY points, registered_at LIMIT 20;
```

积分和注册时间不在同一棵索引的连续键上，优化器无法沿某一条叶子链同时满足两个顺序，`Extra` 里会出现 `Using filesort`。若改成 `ORDER BY full_name, points`，并且存在 `(full_name, points)`，文件排序应消失。`LIMIT` 很小并不能单独避免文件排序，它只是让排序提前停止；没有索引顺序时，仍可能先挑出符合条件的行再排。看计划时把 `Extra` 和 `key` 一起读，只看到 `type=index` 还不能说明没有额外排序。

统计信息长期不更新时，计划会停在过时的行数上。大批删除或导入之后执行一次 `ANALYZE TABLE member`，再打开跟踪看 `rows` 是否接近真实规模。跟踪是会话级的，打开之后只影响当前连接里随后的语句，记得在看完 `information_schema.OPTIMIZER_TRACE` 后关掉，避免把每次语句的跟踪都留在会话里。跟踪文本很长，检索 `chosen` 和 `cost` 即可，不必通读全部枚举。若强制索引之后成本数字反而更高，说明强制走错了，应撤掉提示、改统计或改写语句。
