# JVM 把类装进内存的过程

## 谁负责把类读进来

加载这一步被设计成可以插在虚拟机外面，这样应用程序才能决定字节码从哪来。常见实现有三类加载器。

### 引导加载器

Bootstrap ClassLoader 由虚拟机用本地代码实现。它只认启动路径里的核心库：默认是 `JAVA_HOME/lib` 下被虚拟机点名的 jar，也可以用 `-Xbootclasspath` 追加。它按文件名做白名单，不是目录里的每个 jar 都会被它收下。

### 扩展加载器

Extension ClassLoader 负责扩展目录。JDK 8 里通常是 `JAVA_HOME/lib/ext`，也可以用系统属性 `java.ext.dirs` 改位置。加密提供者、本地化包这类“跟 JDK 走、但不算核心”的库，一般落在这里。

### 应用加载器

Application ClassLoader 加载 classpath 上的业务 jar 和目录。默认的委派顺序是先问父加载器，父加载器找不到再自己读。如果业务要换来源（例如从数据库或网络拉字节码），可以继承 `java.lang.ClassLoader`，自己实现查找逻辑。

## 从字节码到可执行类的五个阶段

装载一条类，主线是：加载、验证、准备、解析、初始化。

### 加载

这一阶段会在内存里生成一个 `java.lang.Class` 实例，作为方法区里该类元数据的入口。字节码不一定来自磁盘上的 `.class` 文件：可以从 jar 或 war 里读，也可以在运行时生成（动态代理），还可以由别的文本编译出来（模板页先变成字节码再加载）。

### 验证

验证要确认这段字节流符合当前虚拟机的格式约束，并且不会在链接或执行时破坏虚拟机。文件头、常量池索引、访问标志、方法字节码都会被检查。通不过就拒绝进入后面的阶段。

### 准备

准备阶段给类变量（static 字段）分配内存，并写成该类型的零值。这些空间在方法区。

零值和源码里的赋值不是一回事。例如：

```java
public static int limit = 2048;
```

准备结束后 `limit` 仍是 0。把 2048 写进去的 `putstatic` 被编译进类构造器 `<clinit>`，要到初始化阶段才执行。

如果字段同时是 static 和 final，并且右侧是编译期常量：

```java
public static final int limit = 2048;
```

编译器会给它生成 ConstantValue 属性。准备阶段虚拟机直接按这个属性写成 2048，不再等 `<clinit>`。

### 解析

解析把常量池里的符号引用换成直接引用。符号引用在 class 文件里体现为几类常量，例如：

```text
CONSTANT_Class_info
CONSTANT_Fieldref_info
CONSTANT_Methodref_info
```

#### 符号引用

符号引用不依赖某一款虚拟机的内存布局，目标类也不必已经在内存里。不同实现可以把对象头、字段排成不同样子，但它们都必须接受同一套符号引用，因为字面形式写在虚拟机规范的 class 文件格式里。

编译 `lab.demo.Order` 时，它如果用到 `lab.demo.Sku`，编译器并不知道 `Sku` 将来放在哪段地址，只能在常量池里记下名字和描述符。运行前，各家虚拟机的堆布局可以不同，能识别的符号形式却要一致。

#### 直接引用

直接引用是已经能定位目标的指针、相对偏移，或一张能立刻找到目标的句柄。一旦解析成直接引用，目标必定已经在内存中。

### 初始化

初始化是类加载的最后一步。在此之前，除了“用哪个加载器读字节”可以由应用决定，验证、准备、解析都由虚拟机主导。到了初始化，才会真正执行类里的 Java 代码：`<clinit>` 按源码顺序跑静态变量赋值和静态块。父类还没初始化时，会先把父类初始化完。
