# MySQL索引

## 索引的优点

查纸质字典先翻部首目录，再翻到正文页，就是索引：用一小段有序结构换掉「从第一页翻到最后一页」。

对数据库来说，收益集中在三处：

- 少扫描行。过滤条件若能走索引，存储引擎不必把整张表读上来
- 少做排序和临时表。`ORDER BY`、`GROUP BY` 的列若已经按索引排好，优化器可以省掉 filesort
- 把随机读尽量变成顺序读。磁盘（以及页缓存未命中时的 IO）连续读一整段，比东一页西一页地寻址便宜。拷贝一个大文件通常快于拷贝同样体积的大量小文件，原因类似
- 少读不需要的列。不要写 `SELECT *`，覆盖索引才有机会成立
- 少做往返。能一次取出的列，不要拆成三次查询

## 索引的用处

- 快速定位满足 `WHERE` 的行
- 在多个可选索引里挑一个估计代价更低的。优化器比较的是成本，不是「索引越多越优先」
- 复合索引可以只用最左边的若干列
- 表连接时，用索引到另一张表找匹配行
- 求某列的 `MIN` 或 `MAX`，若该列有序，可以从一端直接拿
- 排序或分组落在索引的最左前缀上时，不必再单独排序
- 有些查询只读索引里的列，不必回表拿整行

## 索引的分类

### 主键索引

用主键列建出来的索引就是主键索引，一张 InnoDB 表只有一个主键。下面这张货架表把 `sku_code` 设成主键：

```sql
CREATE TABLE shelf (
  sku_code varchar(32) NOT NULL,
  title varchar(128) DEFAULT NULL,
  zone_no char(4) DEFAULT NULL,
  created_at timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
  qty int NOT NULL DEFAULT 0,
  PRIMARY KEY (sku_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`PRIMARY KEY (sku_code)` 会同时要求非空和唯一。InnoDB 会按这列把整行数据组织成一棵 B+ 树。

### 唯一索引

唯一索引同样禁止重复值，但列上可以出现多个 `NULL`（具体允许多少个 `NULL` 与版本和是否包含其他列有关，业务上不要依赖 `NULL` 来表示「唯一但未知」）。

```sql
CREATE UNIQUE INDEX uk_shelf_barcode ON shelf (barcode);
```

建表时也可以写在列定义后面：

```sql
CREATE TABLE shelf (
  sku_code varchar(32) NOT NULL,
  barcode varchar(32) NULL,
  UNIQUE KEY uk_shelf_barcode (barcode)
);
```

它和主键的差别是：主键承担「这行是谁」，并且不能为空；唯一索引只保证值不重复，一张表可以有好几个。

### 普通索引

既不要求唯一、也不是主键的列，用普通索引加速过滤：

```sql
CREATE INDEX idx_shelf_zone ON shelf (zone_no);
```

建表时的写法：

```sql
CREATE TABLE shelf (
  sku_code varchar(32) NOT NULL,
  zone_no char(4),
  INDEX idx_shelf_zone (zone_no)
);
```

### 全文索引

全文索引按词查找正文，不是按整列等值比较。查询用 `MATCH(col) AGAINST('关键词')`。InnoDB 现在支持在 `CHAR`、`VARCHAR`、`TEXT` 上建全文索引。中文分词效果和 Elasticsearch 不是一个级别，检索量大、要相关度排序时，仍应把文档放到专门的搜索引擎。专用引擎里的倒排索引和这里的全文索引是同一类思想，但工程能力差很多。

数据量很大时，可以先把行导入一张还没有全文索引的表，再 `CREATE FULLTEXT INDEX`。这通常比「先建全文索引、再逐行插入」更快，因为后者每插入一行都要维护倒排。

### 组合索引

条件经常同时出现在多列上时，把这几列合成一个索引。例如会员表常按城市加等级过滤：

```sql
SELECT id, nickname FROM member WHERE city = 'hz' AND rank_no = 3;
```

可以建：

```sql
ALTER TABLE member ADD INDEX idx_member_city_rank_age (city, rank_no, age);
```

索引里每个条目带三个键，顺序是 `(city, rank_no, age)`，按这个顺序排序。后面讲的最左前缀，指的就是这个顺序，不是表定义里列的书写顺序。

## 索引的使用与否

优化器会在「走某棵索引」和「直接扫表」之间做选择，没有索引不等于写错，用了索引也不等于更快。

### 索引的使用

一次普通 `SELECT` 在 InnoDB 里通常选定一条访问路径。不是数据库「不允许用两个索引」，而是同时维护两棵 B+ 树的交集，成本常常高于走一条更合适的复合索引，或干脆扫一张小表。`WHERE city = ? AND rank_no = ?` 最合适的是 `(city, rank_no)` 这种复合索引，树按这两列一起排序。

更可能被用到的情况：

- 主键和唯一列上的等值查找
- 和别的表做连接的字段
- `WHERE` 里对索引列做 `>`、`>=`、`=`、`<`、`<=`、`BETWEEN`、`IS NULL`
- `LIKE` 的右模糊，例如 `city LIKE 'hz%'`。左边是通配符则不能用这列的有序性
- `MIN`、`MAX` 作用在已索引的列上
- `ORDER BY`、`GROUP BY` 的列构成索引的最左前缀

### 何时不使用索引

- 表小到全表扫描更便宜，例如只有几十行的配置表
- 取值几乎不区分行。性别、布尔标记这类列，单独建索引往往过滤不掉多少行
- 写多读少的表，每加一个索引，插入、更新、删除都要维护一棵额外的树
- 大文本、图片二进制不要整列索引。若只需要前若干个字符区分度已经够，用前缀索引
- 优化器估计全表扫描的代价更低时，会放弃索引。统计信息过旧时这个判断会错，需要 `ANALYZE TABLE`

### 索引何时失效

这里的「失效」指这条索引帮不上当前语句，不是索引被删掉。

- 复合索引 `(city, rank_no)`，条件只有 `rank_no = 3`，用不上这棵树的有序前缀
- `LIKE '%hz'`，通配符在左边
- 用列 A 的索引做过滤，又按与 A 无关的列 B 排序。过滤可以走 A，排序仍可能 filesort。MySQL 5.0 之后的索引合并是少数例外，不要当成常规
- `OR` 两侧若分别只能走不同索引，旧版本常常退化为扫表。同一列上的 `IN` 或 `OR`（`city = 'hz' OR city = 'nb'`）可以走这列的范围扫描。`city = 'hz' OR rank_no = 3` 则很难用单一复合索引
- 对索引列做运算或函数，例如 `UPPER(city) = 'HZ'`、`qty + 1 = 10`。列被包住之后，原来的顺序用不上
- 负向条件 `<>`、`NOT IN` 常常让优化器觉得要读的行太多，从而不走索引。行数极少时仍可能走

## 面试技术名词

### 回表

有几份二级索引，InnoDB 里就有几棵额外的 B+ 树。真正把整行放在叶子上的，只有按主键组织的那一棵，叫聚簇索引。二级索引的叶子只保存索引列的值加上主键。

沿主键查一行，叶子上就是完整记录，一次就够：

```sql
SELECT sku_code, title, qty FROM shelf WHERE sku_code = 'A-17';
```

沿普通列 `title` 查，先在 `title` 那棵树上找到叶子，叶子里是主键 `sku_code`，再拿主键回到聚簇索引取整行。这第二步叫回表。

```sql
SELECT sku_code, title, qty FROM shelf WHERE title = '接线板';
```

两次树查找意味着更多的页读取。若一次树从根到叶要读三页，回表就可能变成六页。能不回表就不要回表。

### 索引覆盖

若需要的列已经全部躺在二级索引的叶子里，第二次查找可以省掉。

```sql
SELECT sku_code, title FROM shelf WHERE title = '接线板';
```

假设二级索引是 `(title, sku_code)`，叶子上同时有过滤用的 `title` 和要返回的 `sku_code`（二级索引总会带上主键）。优化器不必再读聚簇索引。`EXPLAIN` 的 `Extra` 里会出现 `Using index`。

下面这条要 `qty`，而 `qty` 不在该索引中，就只能回表，`Extra` 里看不到 `Using index`：

```sql
SELECT qty FROM shelf WHERE title = '接线板';
```

这种「索引里的列已经够回答查询」的情况叫覆盖索引。它不是另一种索引类型，而是某条 SQL 刚好只用到了索引列。

### 最左匹配

最左前缀和下面的索引下推，都是针对复合索引的。

索引是 `(city, rank_no, age)` 时，排序先比 `city`，相同再比 `rank_no`，再比 `age`。因此：

```sql
WHERE city = 'hz' AND rank_no = 3          -- 用到前两列
WHERE city = 'hz'                          -- 只用第一列
WHERE rank_no = 3                          -- 用不上这棵复合索引
WHERE rank_no = 3 AND city = 'hz'          -- 优化器可以调整等值条件的顺序，仍然用得到
```

第四条写法与第二条不同，列在 SQL 里的先后不影响等值匹配。优化器会按索引顺序重排条件。范围条件会打断它右边的列，这个放到后面「优化细节」里讲。

连接的驱动表选择也是优化器的事。`FROM t1 JOIN t2` 并不保证先读 `t1`，小表或过滤更强的一侧可能被选来当驱动表。

### 索引下推

复合索引 `(city, rank_no)`，查询是：

```sql
SELECT * FROM member WHERE city = 'hz' AND rank_no = 3;
```

5.6 之前，存储引擎往往按最左列 `city` 找出所有叶子，把整行（或主键）交回服务器层，再由服务器判断 `rank_no`。5.6 引入索引下推之后，存储引擎在叶子上就能同时看 `rank_no`，不满足的主键根本不回表。

差别是过滤发生的位置。条件下推到引擎内部，少了很多无效回表，IO 更小。`EXPLAIN` 里能看到 `Using index condition`。它要求条件用到的列就在这棵索引里；对列做了函数的条件下推不了。

### 优化器

#### CBO

基于成本的优化。根据统计信息估计扫描行数、IO 和 CPU，挑代价最低的计划。InnoDB 走的是这条。统计信息失真时，计划会偏，需要更新直方图或重新分析表。

#### RBO

基于规则的优化。按一组成文的优先级选计划，不太看数据分布。MySQL 的主流路径不是 RBO。了解这个词，是为了在读其他数据库的资料时能对上号。

## 索引匹配方式

下面的例子都假设职员表上有复合索引 `(name, age, pos)`，主键是 `id`。

### 全值匹配

条件盖住索引的每一列，并且都是等值：

```sql
EXPLAIN SELECT id FROM staff WHERE name = 'lin' AND age = 29 AND pos = 'qa';
```

### 匹配最左前缀

只用左边连续的若干列：

```sql
EXPLAIN SELECT id FROM staff WHERE name = 'lin' AND age = 29;
```

第三列 `pos` 没有出现，索引仍能用，只是用到的前缀更短。

只按主键取一行，并且 SELECT 的列都在聚簇索引里时，`Extra` 可能是 `Using index`（主键本身就是覆盖）：

```sql
EXPLAIN SELECT id FROM staff WHERE id = 1;
```

改成 `SELECT *` 之后，虽然同样走主键，但语义上是在读整行，不同版本对 `Extra` 的标注不完全一样，不要死记某一次截图里的 `NULL`。看 `type` 是不是 `const` 或 `eq_ref`，以及 `key` 是不是 `PRIMARY`，更可靠。

### 匹配列前缀

用某一列的开头做范围，右模糊可以走索引，左模糊不行：

```sql
EXPLAIN SELECT id FROM staff WHERE name LIKE 'li%';
EXPLAIN SELECT id FROM staff WHERE name LIKE '%in';
```

第二条通常是全索引扫描或全表扫描。

### 匹配范围值

第一列上的范围可以走索引：

```sql
EXPLAIN SELECT id FROM staff WHERE name > 'lin';
```

### 左列取等值、右列取范围

左边写死一个值、右边给一个区间时，索引用到范围列为止：

```sql
EXPLAIN SELECT id FROM staff WHERE name = 'lin' AND age > 25;
```

`pos` 即使也出现在 `WHERE` 里，也不能再顺着这棵树的下一列做有序查找，只能在已经扫到的叶子上过滤（索引下推）或回表之后过滤。

### 只访问索引的查询

返回列都在索引中，就是覆盖索引：

```sql
EXPLAIN SELECT name, age, pos FROM staff WHERE name = 'lin' AND age = 29 AND pos = 'qa';
```

`Extra` 含 `Using index` 即可确认没有回表。

## 哈希索引

### 概念

哈希索引用列的哈希值定位行，只适合全部索引列都等值的查询。MySQL 里由 Memory 引擎显式提供。InnoDB 的自适应哈希是另一回事：它在缓冲池内部对热点页建哈希，用户不能指定列。哈希结构紧凑，等值查找通常是一次计算加上一次定位，比从 B+ 树根走到叶的常数更小。

### 哈希索引的限制

- 叶子上是哈希值和行指针，没有原始列值，不能靠索引覆盖来避开读行
- 条目不按列值排序，不能支持 `ORDER BY`，也不能支持范围
- 必须使用索引的全部列计算哈希，少一列就对不上，因此没有最左前缀
- 只有 `=` 和 `IN` 这类等值比较，没有范围
- 哈希冲突时要沿链表逐个比对，冲突多了，查找退化为扫链表
- 冲突多也让插入和删除更贵

所以范围、排序、前缀匹配仍应使用 B+ 树。哈希只留给纯等值、冲突可控的内存表。

## 聚簇索引和非聚簇索引

差别在于叶子上放的是整行，还是只放一个能够再去找到整行的指针或主键。

### 聚簇索引

InnoDB 把表数据按主键组织成 B+ 树，叶子上就是整行，叶子之间用链表串起来，范围扫描可以顺序走。这种「索引和行放在一起」的结构叫聚簇索引，也叫索引组织表。一张表只有一棵聚簇索引。没有显式主键时，InnoDB 会选用第一个全部非空的唯一索引；再没有，就生成一个隐藏的行号。

业务上另外建的索引都是二级索引，也叫辅助索引。它们的叶子指向主键。先查二级索引得到主键，再查聚簇索引得到行，可能回表。

### 聚簇索引的优点

- 按主键取整行只走一棵树，少一次回表
- 主键的范围查询是叶子链表上的顺序扫描，局部性好

### 聚簇索引的缺点

- 插入顺序若和主键差很远，叶子页会频繁分裂，插入变慢。所以 InnoDB 常用递增整数做主键，让新行总是追加在右侧
- 更新主键等于把行搬到别的叶子，代价高，主键应设计成不可变
- 二级索引查找要两次：一次拿主键，一次拿行。用覆盖索引可以去掉第二次

### 非聚簇索引

非聚簇索引就是这里的二级索引。叶子不放整行，只放索引键和主键。有的引擎（例如 MyISAM）叶子放的是行的物理地址，InnoDB 放的是主键值。因此即使表上的行因为页分裂挪了位置，二级索引也不用跟着改地址，只要主键不变。

一张表可以有很多棵二级索引，它们不改变行在聚簇索引里的排列。叶子除了索引列，还一定包含主键；若索引列本身就是主键的一部分，不要在定义里重复写，InnoDB 会自己带上。

从二级索引找到主键之后，还要在聚簇索引的叶子页里用页目录定位到具体记录。这一跳就是回表的内部过程。

## 组合索引

列的顺序要按查询来，而不是按「觉得哪列重要」。区分度高、又总是以等值出现的列放左边；范围列放右边。排序、分组若能和这个顺序一致，可以少一次 filesort。

仍以 `(a, b, c)` 为例：

- `WHERE a = 1 AND b = 2 AND c = 3` 用到三列
- `WHERE a = 1 AND b = 2` 用到两列
- `WHERE a = 1 AND b > 2 AND c = 3` 用到 `a` 和 `b`，`c` 不能再作为有序前缀
- `WHERE b = 2` 用不上这棵索引
- `WHERE a = 1 AND c = 3` 只用 `a`，中间的 `b` 被跳过，`c` 不能接上

## 优化细节

- 不要在索引列上计算，把运算挪到常量一侧

```sql
SELECT id FROM actor WHERE actor_id = 4;       -- 可以走主键
SELECT id FROM actor WHERE actor_id + 1 = 5;   -- 列被表达式包住，主键用不上
```

第二条应写成 `actor_id = 4`。函数索引（8.0 起可以显式创建）是例外，那是另一棵按表达式排序的索引，不是原来的主键突然能用了。

- 能用主键回答的查询优先用主键，避免回表
- 长字符串用前缀索引。整列索引又大又慢，而 InnoDB 对索引键长度有上限。前缀越长，选择性越接近整列，索引也越大。选择性是「不重复的索引值个数 / 行数」，从接近 0 到 1。越接近 1，越能一次过滤掉更多行

可以用下面的办法挑长度：比较 `COUNT(DISTINCT LEFT(title, n)) / COUNT(*)` 在不同 `n` 下和整列选择性的差距。博客正文、备注这类列，前十到二十个字符往往已经够用。前缀索引不能做覆盖索引里「取出完整列值」的那部分，因为叶子上没有完整字符串。

- 排序尽量借索引的顺序，避免 filesort。`ORDER BY` 的方向要和索引一致，或在 8.0 的降序索引里显式声明
- `UNION ALL`、`IN`、`OR` 在同一列上都可以走索引。`IN` 的列表更清晰，优化器对它的范围估计也更直接

```sql
EXPLAIN SELECT * FROM actor WHERE actor_id = 1
UNION ALL
SELECT * FROM actor WHERE actor_id = 2;

EXPLAIN SELECT * FROM actor WHERE actor_id IN (1, 2);

EXPLAIN SELECT * FROM actor WHERE actor_id = 1 OR actor_id = 2;
```

`OR` 是否走索引取决于两侧各自的选择性和统计信息，不能一概而论。不同列上的 `OR` 要单独看 `EXPLAIN`。

- 范围条件 `<`、`<=`、`>`、`>=`、`BETWEEN` 可以用到索引，但范围列右边的列不能再作为有序前缀。复合索引里最多放一个范围列，并且把它放在最后。`(a, b, c)` 上若 `b` 是范围，则 `c` 用不上有序性
- 类型不一致会隐式转换，转换若发生在列上，索引失效。`phone` 是字符串时：

```sql
EXPLAIN SELECT id FROM user_account WHERE phone = 13800001234;    -- 列被转成数字，难以走索引
EXPLAIN SELECT id FROM user_account WHERE phone = '13800001234';  -- 类型一致，可以走索引
```

数字列反过来被字符串比较，也会有同样的问题。绑定参数时让 JDBC 类型和列类型一致。

- 更新极频繁、选择性又低的列不要单独建索引。每次更新都要调整 B+ 树，而索引几乎过滤不掉行。性别就属于这一类。经验上选择性超过大约 0.8 再考虑单列索引，用 `COUNT(DISTINCT col) / COUNT(*)` 估算。这个阈值不是服务器的硬限制
- 可空列能表达「未知」，但会让统计和 `IS NULL` 的计划更难预料。能用明确默认值的列，声明成 `NOT NULL`
- 连接的表太多，优化器要评估的顺序会暴涨。阿里的 Java 规范建议单条 SQL 的 JOIN 不要超过三张表，并且连接列的类型必须一致，避免隐式转换。允许适度冗余，用空间换掉一次跨表。设计上是范式和反范式一起用，不是只站一边
- 业务只需要前几行时写上 `LIMIT`，让执行可以提前停止
- 单表索引个数尽量控制在五个左右，写放大会随着索引数线性增加
- 复合索引的列数也不要超过五个，否则维护成本和最左前缀的理解成本都上升
- 不要在没看过 `EXPLAIN` 和慢查询的情况下加索引。索引不是越多越好，每一个索引都在用写入换读取
