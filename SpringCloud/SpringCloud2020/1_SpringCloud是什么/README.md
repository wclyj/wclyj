# 微服务

## 谈谈你对微服务的理解

它不是单指某一个框架，而是把单体拆开之后必须一起补齐的能力清单：

- 注册与发现
- 服务间调用
- 熔断
- 客户端或网关侧负载均衡
- 降级
- 消息队列
- 配置中心
- 网关
- 运行监控
- 调用链追踪
- 自动构建与发布
- 定时任务调度

少了其中任何一项，拆分出来的进程就很难独立演进。注册中心负责“谁在线”，调用组件负责“怎么找到对方”，熔断和降级负责“对方坏了怎么办”，配置中心和网关则把环境差异、入口流量从业务代码里拿出去。

## Spring Cloud

Spring Cloud 把上面这些能力收成一套可落地的技术组合，常被叫作微服务全家桶。它本身不重写业务，而是约定各子项目怎么接在 Spring Boot 应用上。

电商大促、物流调度这类系统，通常会把流量入口、商品、订单、库存、支付拆成独立服务，再用网关、注册中心和消息总线串起来。云厂商的参考架构也是同一思路：边缘接入、业务中台、数据与中间件分层，只是组件品牌不同。

基础层一般固定放这几样：注册发现、配置、网关、调用链、熔断限流。业务服务只依赖这些基础能力，不互相写死地址。

## Spring Cloud技术栈

2020 年之前常见的组合是 Netflix 系：Eureka 做注册，Ribbon 做负载，Hystrix 做熔断，Zuul 做网关，Config 加 Bus 做配置推送。

Eureka 等组件进入维护状态之后，国内项目更多改用 Nacos、OpenFeign、Sentinel、Gateway 这一组。选型时要看的不是名字新旧，而是注册模型、配置推送方式和网关的线程模型是否还在持续维护。

## Spring Cloud版本选型

### SpringBoot2.X版 和 SpringCloud H版

Spring Boot 2 这条线是当时官方主推的运行时。Spring Cloud 的发行版不用数字，而用伦敦地铁站名，按字母从 A 往后排，例如 Angel、Brixton、Greenwich、Hoxton。

它是一个伞形项目，子项目发版节奏并不一致。为了避免把伞版本和子项目版本搞混，官方用一份依赖清单锁住“某个地铁站版本对应哪些子项目版本”。当累积的修复或一个关键缺陷达到发布线，会再打一个服务发布包，习惯写成 SR，例如 Greenwich 的第二个服务发布包。

## SpringBoot和SpringCloud版本约束

Boot 和 Cloud 不能随意交叉。Boot 2.2 配 Hoxton，Boot 2.3、2.4 往后要换到更新的列车版本。动手前先对照官方的版本矩阵，以及 start 站点 actuator 暴露出来的当前依赖信息，再写父 POM。自己猜版本号，最常见的结果是启动时缺类或自动配置对不上。

## 关于Cloud各种组件的停更/升级/替换

### 停更引发的升级惨案

组件宣布停更，通常意味着三件事叠在一起：

- 缺陷只能自己补
- 社区不再接收合并
- 不会再有新的小版本

已经上线的系统不会立刻坏，但安全补丁和 JDK 升级会越来越难跟。

### 明细条目

按能力对照，括号里是后来更常被选中的替代：

- 注册与发现
  - Eureka
  - Zookeeper
  - Consul
  - Nacos（更常见的选择）
- 服务调用
  - Feign
  - OpenFeign（更常见的选择）
  - Ribbon
  - LoadBalancer
- 熔断降级
  - Hystrix
  - Resilience4j
  - Sentinel（更常见的选择）
- 网关
  - Zuul
  - Zuul2
  - Gateway（更常见的选择）
- 配置
  - Config
  - Nacos（更常见的选择）
- 配置刷新总线
  - Bus
  - Nacos（更常见的选择）

同一能力保留两套实现时，要先定“新服务只用新组件”，再给旧服务留迁移窗口，避免一个调用链上同时出现两套熔断语义。
