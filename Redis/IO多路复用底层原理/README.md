# 从底层了解IO多路复用模型

先把一次读取在内核里的路径走通，再回头看三个框架为什么都落到同一种等待方式。

## 前言

把 Redis、Nginx、Netty 放在一张面试桌上，追问「事件模型是什么」，Linux 上的答案都会落到 epoll。Netty 只是在别的操作系统上改用 kqueue 或 IOCP，思路仍是「一个线程照看很多套接字」。只背名字不够，得从内核怎样对待一次读取说起。

## BIO

开机后最先跑起来的是内核。它掌管磁盘、网卡和声卡，并准备好全局描述符表，把线性地址切成两半：用户空间与内核空间。保护模式打开以后，用户程序不能改内核里的页。

CPU 的特权级从 0 排到 3。内核待在 0 级，普通进程只能用 3 级指令。因此业务代码碰不到硬件，只能通过系统调用陷入内核，由内核代为完成。这次陷入可以看成一次受控的软中断。硬中断则来自设备本身：键盘按下时，控制器按中断号找到内核事先登记的处理函数。

每次把字节从网卡搬进进程，都要付一次态切换的成本。下面用一个会卡住的监听程序把这条路径走实。

```java
public class LineGate {
    public static void main(String[] args) throws Exception {
        ServerSocket gate = new ServerSocket(7701);
        System.out.println("listen 7701");
        while (true) {
            Socket peer = gate.accept();
            int remote = peer.getPort();
            System.out.println("peer " + remote);
            Thread worker = new Thread(() -> pump(peer), "pump-" + remote);
            worker.start();
        }
    }

    static void pump(Socket peer) {
        try {
            BufferedReader lines = new BufferedReader(
                    new InputStreamReader(peer.getInputStream(), StandardCharsets.UTF_8));
            String row;
            while ((row = lines.readLine()) != null) {
                System.out.println(row);
            }
        } catch (IOException ex) {
            ex.printStackTrace();
        }
    }
}
```

要核对进程有没有真的陷入内核，把跟踪结果落到目录里：

```bash
strace -ff -o /tmp/linegate java LineGate
```

另开一个终端查 Java 进程：

```text
jps
51204 Jps
51160 LineGate
```

Linux 用 `/proc` 暴露进程。进入对应目录可以看到线程和打开的文件：

```bash
cd /proc/51160
ls task
ls -l fd
```

`task` 下每个子目录是一条线程。`fd` 里的编号就是文件描述符。0、1、2 固定是标准输入、标准输出和标准错误。Java 把它们包装成流对象，内核只把它们看成文件表的下标。再往后新出现的编号一般是监听套接字，IPv4 与 IPv6 常常各占一个。

```bash
ss -lntp | grep 7701
nc 127.0.0.1 7701
```

`nc` 连上之后，`ss` 会多一条已建立连接，`fd` 里也会多一个 socket。翻 `strace` 日志，能看到 `accept` 返回了新描述符，旁边的端口是客户端的临时端口。源码里的 `gate.accept()` 自己并不完成三次握手，它只是进入内核，从已完成队列取出一条连接。

套接字这条路上常见的系统调用还有 `socket`、`bind`、`listen`、`connect`，以及后面要讲的 `select`。`.java` 先变成字节码，JVM 执行到网络 API 时才落到这些调用。中间无论套了多少框架，最后碰网卡的仍是内核。

上面这个模型就是阻塞 IO。`accept` 和 `read` 在没有连接、没有字节时都不返回。主线程不能卡死在读上面，只好每来一个连接就另开一条线程。连接涨到成千上万，线程也跟着涨。每条线程独占一块栈，HotSpot 默认大约 1MB，调度器还要不停换上下文。问题的根不在「线程太贵」这句口号，而在读写会停住调用者。

## NIO

把套接字改成非阻塞后，没有数据时 `read` 会立刻返回，线程可以去干别的。新的麻烦叫 C10K：一万个已连接的客户端里，同一时刻真正发来报文的往往只有一小撮。若在用户态把这一万个描述符逐个问一遍，CPU 大部分时间耗在空转上。

## 多路复用

复用的做法是把「谁有数据」交给内核。进程交出一组文件描述符，`select` 扫完只带回就绪集合，进程再对这几个描述符做真正的读取。`select` 不搬运业务字节，只回答哪些路已经通了，所以不必自己轮询全部连接。

跟「每个描述符一次系统调用」相比，一万次询问合成一次，陷入次数少了很多。它仍有两个硬伤：

- 每一次调用都要把整组描述符从用户空间再拷进内核
- 内核仍要线性扫完这一万项，复杂度是 O(N)

下一步是让内核自己保存兴趣列表。新连接到来时注册一次即可，不必每次把一万个描述符再送进去。就绪改由事件推动：网卡收到数据，内核把对应描述符放进就绪队列，进程被唤醒后只处理队列里的那几项。这就是 epoll 的路径。

## 同样使用epoll，Redis是轮询，Nginx是阻塞？

对正在跑的 `redis-server` 和 `nginx` 做 `strace`，两边都能看到 `epoll_wait`，等的方式却不同。Nginx 可以一直停在这次等待里；Redis 更常见的是带着很短的超时返回，调用本身不长期堵住。

Redis 在 6.0 之前只有一条主线程，这条线程还要干别的活：接入客户端、清理过期键、按近似 LRU 或 LFU 淘汰内存、检查要不要 `fork` 出去写 RDB 或重写 AOF。它若死等在 epoll 上，这些周期任务就没有运行机会，所以事件循环里会穿插时间事件，等待调用带超时。面对大量空闲连接，它同样靠 epoll，只是把就绪客户端排成一条串行队列，每个客户端依次做读、执行、写回。执行阶段保持原子，避免两条命令把同一个字典改乱。

6.0 增加了 IO 线程，但没有把命令执行改成并行。解析和执行仍留在主线程，用来保住原子性；从套接字把字节读进来、把结果写回去，可以分给若干 IO 线程。读写都要进出内核，比在内存里做一次 `HSET` 更容易吃 CPU。把系统调用摊到多个核上，多核才用得起来。

Nginx 的 worker 几乎只做一件事：等连接、读请求、写响应。它没有 Redis 那种必须插进事件循环的内存淘汰和定时落盘，于是直接阻塞在 `epoll_wait`，有事件再醒来。

## 零拷贝

用一条「落盘后再原样转发给消费者」的链路看拷贝次数。传统写法里，同一段载荷要进内核套接字缓冲，再进中间进程的用户空间，再写回内核去落盘；消费者来拉时，再从页缓存拷进中间进程，然后拷回套接字发出去。内容完全没改，CPU 却搬了好几趟。

零拷贝指的是这段不需要加工的载荷不再经过中间进程的用户空间。内核可以用 `sendfile` 把页缓存直接送进套接字。前提是中间不改字节。一旦要改协议字段、做聚合或解压，进程还是得把数据拿进来。

JVM 侧的 `FileChannel.transferTo` 会尽量走到这条内核路径。`MappedByteBuffer` 则是把文件映射到堆外，少一次堆内拷贝。两者不是同一个系统调用，目标一样：能让内核自己搬的，就不要在 Java 堆里再放一份。
