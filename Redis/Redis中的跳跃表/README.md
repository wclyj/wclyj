# Redis中的跳跃表

## 前言

这种结构让节点除了后继之外，还可以拥有若干层更远的前向指针，用来一次跨过一批元素。它服务的是已经排好序的数据。

## 什么是跳跃表

单链表即使里面的数已经按大小排好，查找仍只能从头逐个比较，比较次数是 O(n)。

要加快查找，可以抽一层索引：每隔一个节点，把该节点再挂到上一层。上一层的步长大约是下一层的两倍。

用一条具体的数来看。底层依次是 4、9、15、21、28、36、40。第一层索引抽出 9、21、36。要找 21：先在索引上从 9 走到 21，发现下一档已经是 36，说明目标不在更右边，于是下降到底层，21 本身就是当前节点。没有索引时，从 4 数到 21 要经过五个节点；有了这一层，比较次数立刻少一截。

数据再多，就在第一层索引上继续抽第二层、第三层。层数大约是 log N，每一层期望只走常数步，查找的期望代价变成 O(log N)。这种「链表加多层稀疏索引」的形状，就是跳跃表。

## Redis中的跳跃表

索引要能用，底层必须有序。有序集合正好满足：成员按分数排列。Redis 在两种情况下用跳跃表作为有序集合的底层之一：

- 成员数量已经超过紧凑编码的阈值
- 成员本身比较长，不适合再塞进压缩列表

查找的平均代价是 O(log N)，最坏仍是 O(N)（每一层都退化为单链表时）。它还可以顺着最底层把一段分数范围内的节点依次扫出来，这是排行榜分页需要的。和平衡树相比，常数和实现复杂度都更友好，所以不少系统用它代替平衡树。平衡树要旋转，跳跃表只靠随机层高维持平衡。

为什么偏偏在「节点多」或「成员长」时才换跳跃表？因为索引是拿空间换时间。原始节点里可能放着很长的成员，索引节点只留分数和几枚指针。成员越大、个数越多，多出来的指针相对越便宜，紧凑列表那种整段内存搬迁的缺点就越明显。成员又少又短时，压缩列表更省，多级指针反而浪费。

## Redis中跳跃表的实现

Redis 用两个结构配合。`zskiplist` 描述整张表，`zskiplistNode` 描述单个节点。表对象记下节点个数，并持有指向表头、表尾的指针。

表对象上的字段：

- `header`：表头。有了它，定位表头是 O(1)。表头不存放业务成员，只当作各层前进指针的起点
- `tail`：表尾，定位表尾同样是 O(1)，范围删除或反向遍历时用得上
- `level`：当前所有业务节点里的最大层数，表头那一层不计算在内。读取「现在最高建到第几层」是 O(1)
- `length`：业务节点个数，不含表头，因此 `ZCARD` 不必真的去数

节点上的字段：

- 层。图里常标成 L1、L2、L3。每一层有前进指针和跨度。前进指针指向同一层上更靠近表尾的节点；跨度是这两个节点之间隔了多少个业务节点，跨度越大跳得越远。从左向右查找时，沿当前层的前进指针走，若下一跳的分数已经超过目标，就降一层。新建节点时，按幂次定律随机一个 1 到 32 的层高：层数越大，被抽中的概率越小。32 是上限，避免极端情况下索引过高
- 后退指针。每个节点只有一枚，指向紧邻的前一个节点。从尾向头走时每次只能退一格，没有多层后退索引
- 分数。节点按分数从小到大排列
- 成员。同一张表里成员必须唯一，分数可以重复。分数相同时，按成员的字典序，较小的靠表头

有序集合在非紧凑编码下并不只有跳跃表。旁边还有一张字典，用成员直接找到分数和节点。按成员做 `ZSCORE` 走字典，按分数做 `ZRANGEBYSCORE` 走跳跃表。只说「底层是跳跃表」会漏掉这张字典。

查找时跨度用来算排名，不必把底层再数一遍。从最高层出发，若前进指针指向的分数仍小于目标，就加上这一跳的跨度并往右走；否则降一层。走到最底层、下一跳已经不小于目标时，累计的跨度就是目标在表中的名次。`ZRANK` 靠的就是这个过程，所以它是 O(log N)，不是先定位再从前往后数。

层高的随机可以看成反复抛硬币：正面就再加一层，反面就停，最多 32 层。因此大约一半节点只有 1 层，四分之一有 2 层，越高越稀。插入和删除只改沿途那些前进指针，不用像平衡树那样旋转整棵树。代价是层高是随机的，单次查找的最坏情况仍可能退回线性扫描，只是概率极低。

## 本文重点

- 跳跃表是单链表加上多层稀疏索引
- 多出来的指针用空间换查找速度，期望 O(log N)
- 有序集合成员多或成员长时，Redis 放弃紧凑列表，改用跳跃表加字典
- 表信息在 `zskiplist`（表头、表尾、层高、长度），节点是 `zskiplistNode`
- 每个节点的层高是 1 到 32 的随机数，服从「越高越少」
- 成员唯一，分数可以相同；排序先比分数，再比成员字典序
