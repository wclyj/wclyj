# 通俗理解多种IO模型

## 前言

几种 IO 模型可以用同一件办事来对照。阿宁要取一份加急材料，窗口两天后才会备好。往返办事大厅单程要半小时。出场的人有四个：阿宁、代办、窗口职员、骑手。

## 多种IO模型

### 阻塞IO模型

阿宁坐在大厅里干等，两天后才拿到材料。

> 代价：两天都耗在大厅，手头的工作完全停摆。

### 非阻塞IO模型

阿宁每半天去问一次「好了没」，其余时间回工位干活。两天后终于取到。

> 代价：来回跑了八趟左右，路上一共大约四个小时，但等待的空隙还能做事。

### IO复用模型

#### select 和 poll

阿宁把单号交给代办，自己每隔三小时打一通电话问进度。代办在两天内取到号，阿宁再亲自去窗口付钱、领材料。

> 代价：电话打了十几通，大厅仍要去两次，另外付一笔代办费。代办同时盯着很多人的单号，但阿宁得不停追问。

#### epoll

还是交给代办。材料一到，代办主动发消息，阿宁再去窗口领。中间不用轮询电话。

> 代价：大厅仍要去两次，代办费还在，电话费没有了。

### 信号驱动IO模型

阿宁把手机号留给窗口。材料到了，职员打电话通知，阿宁自己去领。

> 代价：往返两次，路上大约一小时。没有代办，也不用自己轮询。

### 异步IO模型

阿宁留下地址和电话。材料到了，窗口通知一声，同时让骑手送到家。

> 代价：只为了递交申请去过一次大厅，不用守着，也不用再跑一趟去取。

### 总结

- 阻塞和非阻塞的差别，在于是不是自己一遍遍去问
- 非阻塞和复用的差别，在于询问能不能委托给一个盯着很多单号的人
- 复用和信号驱动的差别，在于还要不要主动打电话，还是等对方来电
- 信号驱动和异步的差别，在于来电之后还要不要自己去取，还是结果直接送到手

## Linux操作系统中的基础概念

讲 `select`、`poll`、`epoll` 之前，先把几个内核名词对齐。

### 用户空间/内核空间

现代操作系统给进程看的是虚拟地址。32 位进程的虚拟地址是 4GB，因为 2 的 32 次方等于 4G。64 位大得多，但划分方式一样：一段给内核，一段给用户进程。

内核独立于普通程序，能读受保护的内存，也能操作设备。为了不让用户进程直接改内核数据，虚拟地址被划成内核空间和用户空间。跨越边界只能走系统调用或中断。

### 进程切换

内核可以暂停正在 CPU 上跑的进程，把寄存器和地址空间换到另一个进程。这叫进程切换，也常被称作上下文切换。切换时要保存和恢复寄存器、刷新部分缓存相关状态，所以频繁换进程本身就是开销。进程看起来在「自己跑」，其实一直靠内核调度。

### 进程阻塞

进程要等的事情还没发生，例如读套接字时对端还没写数据，就会主动进入阻塞，把 CPU 让出去。只有当前占着 CPU 的进程才能把自己改成阻塞。进入阻塞后不再消耗 CPU，直到内核把它唤醒。

### 文件描述符

文件描述符是一个非负整数，用来指代本进程打开的文件、套接字、管道或设备。它是进程文件表里的下标。`open` 或 `socket` 成功后，内核把这个整数交回用户空间。以后的 `read`、`write`、`close` 都拿它做参数。这个概念属于 Unix 和 Linux 一系，Windows 上对应的是句柄，不要混用。

### 缓存IO

默认的读写是带缓存的。调用 `read` 时，内核先把设备上的数据放进页缓存，再从页缓存拷到用户缓冲区。`write` 则先进入页缓存，稍后再刷到磁盘。因此一次「读文件」至少包含一次内核内部的拷贝，外加一次拷进用户空间。后面说的零拷贝，就是想省掉其中用户空间那一跳。

## IO多路复用

若每个连接 fork 一个进程，一百万个连接就是一百万个进程，光是调度和栈内存就不可接受。多路复用改成：一条线程记下很多描述符的兴趣（可读、可写、出错），内核通知哪些已经就绪，线程再逐个处理。吞吐来自「一个执行流照看很多连接」，而不是来自线程数。

调用过程可以分成三拍：

- 进程调用 `select` 或它的同类函数，自己进入等待
- 内核盯着这批套接字，其中有描述符可读或可写时，调用返回
- 进程对返回的那些描述符执行 `read` 或 `write`，数据才从内核缓冲区进入进程

实现这条路径的 API 主要是 `select`、`poll`、`epoll`。

### select

#### 概念

`select` 使用 `fd_set` 这种位图。每一位对应一个已经打开的描述符，套接字、普通文件、管道、设备都可以放进去，由调用方自己把位设上。进入内核后，内核按当前是否可读、可写改写这张位图，返回后进程扫描位图，就知道哪些描述符就绪。

从单次调用看，它比「阻塞地读一个套接字」还多了维护位图和扫描的成本，单个连接不会更快。价值在于同一条线程可以登记很多套接字，反复调用，依次处理已经就绪的那些。阻塞模型要做到这一点，只能一个连接一条线程。

#### select机制存在的问题

- 进入内核前，整张 `fd_set` 都要再送一份过去。登记得越多，这次拷贝越贵
- 内核每次都要扫描调用方传来的全部描述符，其中大部分往往是空闲的
- 位图宽度由编译期的 `FD_SETSIZE` 决定，常见默认是 1024，改大需要重新编译，不能在运行时放宽

### Poll

`poll` 用 `pollfd` 数组代替位图，没有 1024 这个编译期上限，描述符可以更多。它仍然每次把整组描述符拷进内核，并在内核里线性扫描。所以上面三条缺点里，它只去掉了第三条，前两条还在。

### Epoll

`epoll` 在 Linux 2.6 进入内核，按事件驱动。它没有 `select` 那种固定上限，用一个 epoll 描述符管理很多被关注的描述符。兴趣列表留在内核里，用户空间到内核的整表拷贝只发生在 `epoll_ctl` 注册或修改时，之后 `epoll_wait` 只取已经就绪的项。

活跃连接只占全部连接的一小部分时，它不必再扫那些空闲描述符，CPU 不会浪费在空转上。内核在描述符就绪时把它挂进就绪队列，`epoll_wait` 返回的就是这条队列。

两种通知方式：

- 水平触发是默认。描述符上还有未读完的数据，下次 `epoll_wait` 会再次报告，适合不太严格的读循环
- 边缘触发只在状态从「未就绪」变成「就绪」时通知一次。应用必须一次读到 `EAGAIN`，否则剩下的字节不会再次提醒。写方向同理

## 总结

可以换成值班室来记。一个值班员看着一整排呼叫灯。灯亮了就过去处理，没有灯就歇着。这些呼叫方共用一个值班员，就是多路复用。

`select` 和 `poll` 像没有呼叫灯：值班员必须逐个房间问一遍。`epoll` 有灯，只走向亮灯的房间。

三者的差别：

|  | select | poll | epoll |
| --- | --- | --- | --- |
| 检查方式 | 调用时把全部描述符扫一遍 | 同样全量扫描 | 只取内核已经挂进就绪队列的项 |
| 常见说法里的结构 | 位图，面试口述里常记成数组 | `pollfd` 数组，口述里常记成链表 | 兴趣列表加就绪链表；口述里常被记成哈希表 |
| 就绪代价 | 线性于登记数量，O(n) | 同样是 O(n) | 活跃数较少时接近 O(1) 取就绪项 |
| 数量上限 | 受 `FD_SETSIZE` 约束，常见 1024，也有人编译成 2048 | API 本身不设这个上限 | API 本身不设这个上限 |
| 描述符拷贝 | 每次 `select` 都整表拷进内核 | 每次 `poll` 都整表拷进内核 | `epoll_ctl` 时写入内核，之后 `epoll_wait` 不再拷整表 |

内核里更准确的说法是：`select` 用位图，`poll` 用数组，`epoll` 用红黑树保存关注列表、用链表收集就绪事件。面试速记里的「数组、链表、哈希表」是简化，和源码并不一一对应。

若几乎每个描述符都是活跃的，线性扫描的浪费变小，`epoll` 为了维护就绪队列还要加锁，这时它不一定比 `select` 或 `poll` 更快。就绪描述符通过共享内存交回用户空间，省掉一份额外拷贝。

连接数高、活跃比例低时，Linux 上的网络服务优先考虑 `epoll`。Nginx 的事件模块就建立在它上面。连接数不大时，一个连接一条阻塞线程往往更好写，也足够快，不必先上复用。
