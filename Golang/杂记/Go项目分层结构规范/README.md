# Go 项目分层习惯

这里记录的是社区里反复出现的仓库目录，不是 Go 核心团队发布的强制规范。有的目录很常见，有的只在大项目里才划得来。它额外补了几项几乎每个正式服务都会碰到的支撑目录。

学习语法、做验证想法的原型或周末小实验时，不必套这套树。一个 `main.go` 就够。等代码变大，再整理结构，否则依赖和全局状态会缠在一起。协作者变多之后，需要一种大家都认的放法。仓库一旦被别人 import，就该把不希望对外的代码放进 `internal`。克隆一份参考布局后，只留用得上的目录。没有任何一种目录是每个仓库都必须有的，连 `vendor` 也一样。

Go 1.14 起，模块可以放心用在生产构建里。没有特殊原因就使用模块，这样不必再为 GOPATH 和工作区位置操心。`go.mod` 里的模块路径常常长得像托管在 GitHub 上，但这只是习惯。路径可以指向任何位置；旧版本希望第一段带一个点，现行版本已经放宽。若构建因为找不到 `go.mod` 失败，先确认是不是还在用很老的工具链。相关讨论可以检索议题 37554 和 32819。

这套布局不规定你的包必须怎么拆，只建议文件放在哪。

它来自社区约定。出现新的常见放法，或某条已经过时，就去对应仓库提议题更新。

命名和格式先跑 `gofmt`，再用静态检查工具看导出注释和包名。风格上可以对照这些材料的主题，而不是背某一次演讲的地址：命名演讲、Effective Go 的名字一节、包名短文、代码评审备忘，以及 Jaana B. Dogan 写的包风格说明。

背景介绍可以搜索 “Go Project Layout” 的说明文。包的组织和工业界实践，则有几场 GopherCon 演讲经常被引用：Peter Bourgon 谈工业编程，Ashley McNamara 与 Brian Ketelsen 谈实践，Edward Muller 谈反模式，Kat Zien 谈应用如何划分目录。

## Go 目录

### `/cmd`

放每个可执行文件的入口。

子目录名应等于你希望生成的二进制名，例如 `/cmd/ledgerd`。

不要把业务逻辑堆在这里。别的项目也可能 import 的代码去 `/pkg`；只给本仓库用、也不希望被引用的代码去 `/internal`。别人会怎么用你的包往往出乎意料，目录本身就要把意图写清楚。

`main` 函数通常很短：从 `internal` 和 `pkg` 取出类型，调用之后就结束。命令行参数、配置路径和日志初始化可以留在这里，业务规则不要留。一个仓库若有多个进程，就并列多个子目录，而不是在同一个 `main` 里用开关硬分。

### `/internal`

只给本模块用的程序和库。Go 编译器会拒绝外部模块导入任何名为 `internal` 的目录下面的包，这条自 1.4 的发布说明起生效。`internal` 不必只出现在仓库根上，任意子树都可以再放一个。

包内部还可以再分：多个应用共用的私有库放 `/internal/pkg/私有库名`，某个应用专有的代码放 `/internal/app/应用名`。小仓库可以不拆这么细，但目录名最好让人看出“这是共享的”还是“这是某一个进程的”。

编译器的检查以路径中出现的 `internal` 目录为界：导入路径在走到这个目录之前的前缀，必须是当前模块的前缀。因此 `internal` 放得越深，允许导入它的范围越小。把只给某一个命令用的代码放到 `/cmd/ledgerd/internal`，其他命令即使在同一模块里也不能引用。

### `/pkg`

允许外部模块导入的库，例如 `/pkg/money`。别人会依赖这里的稳定性，放进去之前要想清楚。真正能靠编译器挡住外部导入的是 `internal`；`/pkg` 只是一种明示：“这里的 API 打算被使用”。Travis Jeffery 有一篇文章比较这两种目录，标题大意是他更倾向于用 pkg 而不是把一切都藏进 internal，适合拿来对照取舍。

当仓库根上还有大量非 Go 文件时，把 Go 代码收进 `/pkg` 能让 `go test`、`go fmt` 更好下命令。这一点在 Bourgon 的工业实践演讲、Kat Zien 的结构演讲，以及 Massimiliano Pippi 在 GoLab 2018 关于布局模式的演讲里都提到过。

想看哪些知名仓库采用了 `/pkg`，可以翻 golang-standards 的 project-layout 里该目录的说明。这是常见写法，但并非人人赞成，也有核心贡献者不推荐单独设 `/pkg`。

项目还很小、多一层目录没有收益时，就不要建。等到根目录被脚本、配置和多种语言挤满，再考虑收拢。

### `/vendor`

存放依赖的副本，可以手拷，也可以用模块的 `go mod vendor` 生成。Go 1.14 起默认就会使用 vendor（在模块模式且目录存在时）。更早的版本构建时可能要加 `-mod=vendor`。

如果发布的是库，不要把应用的 vendor 提交出去，让调用方自己解析版本。

1.13 同时默认打开模块代理，公共代理是 `https://proxy.golang.org`。官方有文章说明镜像和校验和数据库的用途。若代理能满足构建，可以不保留 vendor。

默认代理在国内网络常常连不上。七牛维护的 `goproxy.cn` 是常用替代，设置 `GOPROXY` 即可。

## 服务应用程序目录

### `/api`

放 OpenAPI 或 Swagger 描述、JSON Schema、协议定义。具体示例见 project-layout 仓库里的 `api` 说明。这些文件是契约，不是生成物。生成出来的客户端可以不提交，但契约本身要进版本库，方便评审接口是否兼容。

## Web 应用程序目录

### `/web`

站点专用材料：静态资源、服务端模板、单页应用的源码。构建产物体积大、可再生成，通常不提交，只在 `/web` 保留源码和打包配置。Go 代码不要和前端脚手架混在同一层目录里。

## 通用应用目录

### `/configs`

配置模板和默认值。`confd`、`consul-template` 一类模板也放这里。含口令的真实配置不要提交，仓库里只留去掉秘密的样例，文件名可以带 `.example`。程序启动时再把样例和本机环境合并。

### `/init`

进程托管配置：systemd、upstart、sysv，以及 runit、supervisord 的单元文件。

### `/scripts`

构建、安装、分析用的脚本。目的是让根上的 Makefile 保持短。HashiCorp Terraform 的 Makefile 是这种拆法的例子。

### `/build`

打包和持续集成。

云镜像、容器、deb/rpm/pkg 的脚本放 `/build/package`。

Travis、Circle、Drone 等 CI 脚本放 `/build/ci`。有的 CI 只认仓库根上的固定文件名，那时在它期望的位置放一个指向 `/build/ci` 的链接。

### `/deployments`

部署编排：docker-compose、Kubernetes/Helm、Mesos、Terraform、BOSH 等。有的仓库把这个目录叫做 `/deploy`，尤其是只用 Kubernetes 的项目。

### `/test`

仓库级的额外测试程序和夹具。大项目可以再分 `/test/data` 或 `/test/testdata`。Go 工具会忽略名为 `testdata` 的目录，也会忽略以 `.` 或 `_` 开头的目录和文件，所以测试数据不必一定叫某一个名字。

这里放的是跨包的黑盒程序和体积较大的夹具，例如一份完整的请求样本。包内的单元测试仍放在对应目录的 `_test.go` 里，不要为了“统一”把所有测试都搬到仓库根上。夹具若含个人数据，提交前要换成虚构内容。

## 其他目录

### `/docs`

给人读的设计和用户文档。godoc 从注释生成的 API 文档不算在这里。设计记录写“为什么这样拆”，用户文档写“怎么调用”。两套读者不同，不要合成一个长文件。

### `/tools`

支撑本仓库的小工具。它们可以 import `/pkg` 和 `/internal`。

### `/examples`

给应用或公共库准备的示例程序。

### `/third_party`

外部辅助程序、分叉出来的代码，以及 Swagger UI 这类第三方前端。

### `/githooks`

Git 钩子脚本。

### `/assets`

随仓库分发的图片、标志等资源。

### `/website`

不使用 GitHub Pages 时，站点源文件放这里。

## 你不应该拥有的目录

### `/src`

有些仓库会在项目里再套一层 `src`，多半是从 Java 的源码目录带过来的习惯。Go 项目不必模仿。

不要把它和 GOPATH 工作区里的 `src` 搞混。`How to Write Go Code` 描述的工作区默认在非 Windows 上是 `$HOME/go`，下面有 `src`、`pkg`、`bin`。你的项目若还放在 GOPATH 里，路径已经是 `工作区/src/你的模块/...`。再在项目内加一层 `src`，路径会变成 `.../src/你的模块/src/代码.go`。1.11 之后项目可以完全放在 GOPATH 之外，这并不构成在模块内部再设 `src` 的理由。

若团队已经习惯按业务而不是按技术分层，可以在 `/internal/app` 下再按领域分子目录，例如账单、会员、通知。领域之间通过公开的小接口通信，不要互相引用对方的存储细节。目录规范解决的是“文件放哪”，包的边界仍然要按依赖方向单独设计。新增目录前先问：这一层是否会被第二个进程或第二个模块用到。用不到就留在最近的 `internal` 里。能不增加顶层目录，就不要增加。
