# 用 NSQ 做消息队列

引入消息队列，通常是为了三件事：把慢步骤挪到请求之外、让上下游不必同时在线、把瞬间的流量先接住。NSQ 是用 Go 编写的实时分布式队列，下面介绍它的角色划分，以及如何用官方客户端收发。

## 它强在哪里

1. 拓扑分散，没有单独的中心转发节点。某个守护进程挂了，其它节点仍能继续投递，并尽量保证消息至少到达一次。
2. 横向扩展时不必先摆一个集中式代理，消费者通过发现服务找到当前的节点。
3. 配置项有默认值，自带网页管理台，单机就能跑起来。

## 三种业务场景

### 异步

下单请求里，扣库存必须马上做完，发短信和写审计可以稍后。把后两步丢进队列，接口只等扣库存成功就返回，响应时间不再被短信网关拖住。

### 解耦

订单服务只负责把“已支付”写进主题，积分、仓储、通知各自订阅。以后新增一个对账服务，只要再加一个订阅，订单服务不用改代码、也不用认识新服务的地址。

### 削峰

秒杀时请求会在几秒内涌进来。接口把订单请求写入队列后立刻回应“已受理”，后端按自己的速度消费。队列成为缓冲区，数据库不会被同时打满。缓冲区也有上限，满了就要拒绝新请求，而不是无限堆积。

## 安装

从项目的安装说明按操作系统下载压缩包并解压，可执行文件集中在 `bin`。单机试验需要三个进程：`nsqlookupd`、`nsqd` 和 `nsqadmin`。

## 三个进程

### nsqd

`nsqd` 负责接收、排队和把消息交给客户端。单机启动时指定广播地址，避免它向发现服务登记一个别人访问不到的主机名：

```bash
nsqd -broadcast-address=127.0.0.1
```

和 `nsqlookupd` 一起用时，还要告诉它发现服务的 TCP 地址：

```bash
nsqd -broadcast-address=127.0.0.1 -lookupd-tcp-address=127.0.0.1:4160
```

管理台单独启动，指向发现服务的 HTTP 地址：

```bash
nsqadmin -lookupd-http-address=127.0.0.1:4161
```

浏览器访问本机 `4171` 端口即可看到主题和通道。部署了多个发现节点时，`-lookupd-tcp-address` 可以重复写多次。

常用开关不必逐条背，按用途记住这些就够：

| 开关 | 作用 |
| --- | --- |
| `-tcp-address` | 客户端 TCP，默认 `0.0.0.0:4150` |
| `-http-address` | HTTP 发布与统计，默认 `4151` |
| `-broadcast-address` | 登记给发现服务的地址，默认是主机名 |
| `-data-path` | 磁盘队列目录 |
| `-mem-queue-size` | 每个主题通道在内存里保留的消息条数，默认 10000；设为 0 则全部落盘 |
| `-max-msg-size` | 单条消息上限，默认 1MB |
| `-msg-timeout` | 发出后多久未确认就重新入队，默认 1 分钟 |
| `-max-rdy-count` | 单个客户端最多同时持有多少条未确认消息，默认 2500 |

压缩、TLS、统计上报也有对应开关。认证地址、心跳上限、刷盘条数和刷盘间隔影响的是安全与持久性，试运行时可以先用默认值，上生产再按磁盘和延迟要求调整。

### nsqlookupd

它维护所有 `nsqd` 的登记信息，让消费者按主题发现该连哪一台。它自己不保存消息，多个实例之间也不用互相协商，因此可以按机房冗余要求多放几份，资源占用很小，常和别的进程放在一起。一个机房至少跑三个，是常见的建议。

它默认在 `4160` 提供 TCP，在 `4161` 提供 HTTP。`-inactive-producer-timeout` 决定一个节点多久不心跳就从活跃列表消失，默认 5 分钟。`-tombstone-lifetime` 控制被标记下线的节点还会保留多久，默认 45 秒。

### nsqadmin

这是查看堆积、暂停通道、删除主题的网页。启动时只要发现服务的 HTTP 地址：

```bash
nsqadmin -lookupd-http-address=127.0.0.1:4161
```

打开本机 `4171` 端口。管理接口默认只允许本机网段访问 `/config`。若要把统计转给 Graphite，或在管理操作发生时回调某个 HTTP 地址，有单独的开关，试运行可以不配。

## 拓扑

一个 `nsqd` 同时处理多路数据。每一路叫 topic。topic 下面有一个或多个 channel。发布到 topic 的每一条消息，都会在每个 channel 里放一份副本。真正的下游订阅的是 channel，不是直接从 topic 抢同一份。

topic 和 channel 不必事先创建。第一次向某个 topic 发布，或第一次订阅它下面的 channel，就会被建出来。两者各自缓冲，一个 channel 的消费者慢，不会把别的 channel 堵住；topic 之间也一样。

一个 channel 通常连着多个客户端。所有客户端都准备好接收时，一条消息只会随机交给其中一个。于是整体是：topic 到 channel 是复制，channel 到消费者是分摊。

### 节点内部的路径

消息进入 `nsqd` 后，先到输入通道，再进入内存队列。内存达到阈值，或进程要退出时，消息被写进磁盘队列。要发给客户端时，从内存或磁盘取出，放进输出通道。所以它不是纯内存队列，而是内存加磁盘。

## 投递语义

- 默认内存优先，可以调成更偏向磁盘。`--mem-queue-size=0` 时消息都进磁盘队列。进程退出前，当时还在内存里的消息也会被刷下去。
- 每条消息至少投递一次。消费者处理完但没来得及确认就断开时，同一条会再被投递，业务要能承受重复。
- 不保证顺序。需要顺序时，应在消息里带序号，由消费方自行排列，不能依赖到达次序。

## Go 客户端

官方客户端是 `github.com/nsqio/go-nsq`。其它语言也有对应实现，协议是同一套。

### 启动顺序

先在 `bin` 目录启动发现服务，它占用 `4160` 和 `4161`：

```bash
nsqlookupd
```

再启动队列进程，并指向发现服务：

```bash
nsqd -broadcast-address=127.0.0.1 -lookupd-tcp-address=127.0.0.1:4160
```

最后启动管理台。三个都起来之后再跑下面的程序。

### 安装客户端

```bash
go get github.com/nsqio/go-nsq
```

### 生产者

从标准输入读一行就发布一条，输入 `Q` 退出。主题叫 `order_paid`。

```go
package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"

	"github.com/nsqio/go-nsq"
)

var writer *nsq.Producer

func openWriter(addr string) error {
	cfg := nsq.NewConfig()
	var err error
	writer, err = nsq.NewProducer(addr, cfg)
	return err
}

func main() {
	if err := openWriter("127.0.0.1:4150"); err != nil {
		fmt.Println("producer:", err)
		return
	}
	defer writer.Stop()

	in := bufio.NewReader(os.Stdin)
	for {
		line, err := in.ReadString('\n')
		if err != nil {
			fmt.Println("stdin:", err)
			continue
		}
		line = strings.TrimSpace(line)
		if strings.EqualFold(line, "Q") {
			return
		}
		if err := writer.Publish("order_paid", []byte(line)); err != nil {
			fmt.Println("publish:", err)
		}
	}
}
```

运行后输入 `1001` 和 `1002`。连接建立时客户端会打印连上了哪一个 `nsqd`。此时管理台的主题页能看到 `order_paid`，点进去可以观察到有消息积压。因为还没有消费者，channel 尚未出现。节点页列出当前登记的 `nsqd`。计数页在没有消费时处理量仍是 0。发现页还允许手工创建主题和通道。

### 消费者

消费者要实现一个处理单条消息的方法。这里通过发现服务查找主题，而不是把 `nsqd` 地址写死。

```go
package main

import (
	"fmt"
	"os"
	"os/signal"
	"syscall"
	"time"

	"github.com/nsqio/go-nsq"
)

type printer struct {
	name string
}

func (p *printer) HandleMessage(msg *nsq.Message) error {
	fmt.Printf("%s from %s body=%s\n", p.name, msg.NSQDAddress, msg.Body)
	return nil
}

func openReader(topic, channel, lookupHTTP string) error {
	cfg := nsq.NewConfig()
	cfg.LookupdPollInterval = 15 * time.Second
	c, err := nsq.NewConsumer(topic, channel, cfg)
	if err != nil {
		return err
	}
	c.AddHandler(&printer{name: "desk-a"})
	return c.ConnectToNSQLookupd(lookupHTTP)
}

func main() {
	if err := openReader("order_paid", "billing", "127.0.0.1:4161"); err != nil {
		fmt.Println("consumer:", err)
		return
	}
	sig := make(chan os.Signal, 1)
	signal.Notify(sig, syscall.SIGINT)
	<-sig
}
```

`HandleMessage` 返回 nil 表示确认。返回错误会导致消息按策略重新入队。直接连某一台 `nsqd` 时用 `ConnectToNSQD`，地址是 `4150`；通过发现服务时用 `ConnectToNSQLookupd`，地址是 `4161`。

先启动过生产者并留下 `1001`、`1002` 的话，消费者起来后会把这两条打出来。管理台的计数页也会变成已处理 2 条。通道名 `billing` 是第一次订阅时创建的，同一通道再挂一个进程，两条消息会被分摊，而不是各收一份。若希望每个进程都收到全部消息，就要使用不同的通道名。

## 一条消息的一生

以订单号 `1001` 为例，走完内部路径是这样的：

1. 生产者连上 `4150`，把正文交给名为 `order_paid` 的主题。主题不存在时，第一次发布会把它建出来。
2. 节点先把消息放进该主题的内存队列。条数超过 `-mem-queue-size`，或进程即将退出，就追加到磁盘队列。磁盘文件按大小滚动，避免单个文件无限增长。
3. 订阅 `billing` 这个通道的客户端发出就绪数量，表示自己还能同时处理几条。节点不超过 `-max-rdy-count`。
4. 节点从内存或磁盘取出一条，推给该通道上随机的一个已就绪客户端，并开始计算 `-msg-timeout`。
5. 客户端处理完返回空错误，节点把这条标成完成。处理函数返回错误，或超时仍未确认，消息回到队列尾部，等待下一次投递。
6. 同一主题若还有 `warehouse` 通道，它会拿到另一份副本，节奏与 `billing` 无关。仓储慢，不会挡住计费。

因此“至少一次”是协议承诺，不是“恰好一次”。计费函数在写完数据库、还没来得及确认时进程崩溃，下一次投递会再写一遍。表上要对订单号做唯一约束，或先查询再插入。

## 两个通道和两个进程

假设积压了四条：`1001` 到 `1004`。

- 两个进程订阅同一个通道 `billing`：四条被分摊，每个进程大约拿到两条，不会重复。
- 两个进程分别订阅 `billing` 和 `warehouse`：每个通道都看到全部四条。这才是“各做各的业务”。
- 通道里的进程比分区概念更多余时不会闲置，NSQ 不按分区绑定消费者，它在通道内随机派发。这一点和 Kafka 的分区分配不同，迁移时不要沿用“一个分区只给一个实例”的心智模型。

管理台上先看主题深度，再点进通道看客户端连接数和已确认数量。深度持续上升说明消费速度不够，应加消费者或检查处理函数是否堵住；深度为零但业务没反应，则多半是订阅了错误的通道名，消息进了另一个没人读的通道。

## 失败与重试

`HandleMessage` 里不要自己无限循环重试。返回错误后，客户端会按 `MaxAttempts` 和重新入队延迟把消息送回。默认尝试次数用完，消息进入该通道的延迟队列或被丢弃，具体取决于配置。把尝试次数和订单号打进日志，才能区分“第一次失败”和“已经重复了很多次”。

需要延迟处理时，可以设置消息的延迟时间戳再发布，而不是让消费者睡很久。睡眠会占住就绪名额，让同一客户端后面的消息也排不上。

发布端的 `Producer` 可以在多个 goroutine 里共用。每条消息都 `NewProducer` 会反复握手。停止进程前调用 `Stop`，把缓冲区里还没写出去的消息刷完。

```go
func publishPaid(orderID string) error {
    body := []byte("paid:" + orderID)
    return writer.Publish("order_paid", body)
}
```

正文里带上业务主键，消费者即使不看消息标识，也能做幂等。NSQ 自己的消息编号只在节点内唯一，不能当成全局业务键。

## 和采集链路怎么接

日志采集若先写本地文件再由代理尾随，队列位于代理和入库进程之间。NSQ 适合日志量中等、希望组件少的场合；单主题每天几十亿行时，磁盘和副本模型更常见的是 Kafka。两者的客户端都要处理重复和失败，不能因为换了产品就假设消息只到一次。

试运行的检查顺序：发现服务端口 `4161` 能打开，队列进程的广播地址是本机可访问的地址，管理台能看到刚发布的主题，消费者的通道名和发布时约定的一致。广播地址若是容器内部主机名，管理台看得到节点，消费者却连不上。

## 上线前要拍板的参数

试运行用默认值就够，真正接流量时下面几项会改变丢数据和延迟：

- 内存队列长度决定崩溃时最多丢掉多少条还没刷盘的消息。改成 0 表示来一条写一条磁盘，更安全，延迟也更高。
- 单条大小上限默认大约 1MB。日志行通常很小，若要投递压缩后的批次，得同时放宽节点和客户端。
- 未确认就重新入队的等待时间默认一分钟。处理函数若要调用外部接口，应把客户端超时设得更短，否则超时后旧消息和新消息叠在一起。
- 单个客户端同时持有的未确认条数默认两千五。处理很慢时把这个数调小，避免一个卡住的进程囤积大量消息。
- 刷盘可以按条数或按时间。条数太大，断电时丢得更多；时间太短，磁盘会忙于小写入。
- 发现服务把多久没有心跳的节点移出列表，默认五分钟。网络抖动频繁时，不要把它改得过短，否则消费者会反复断开重连。

统计可以推到本机的指标采集进程，管理台只适合人看，不适合当报警源。堆积曲线、重入队次数和客户端连接数，至少这三样要进监控。

## 本地先走通再谈集群

单机三进程的顺序不能颠倒：先发现服务，再队列节点，最后管理台。队列节点若先启动又没写发现地址，它会独自工作，消费者用发现地址去查时会得到空列表，表现为发布成功但永远消费不到。此时要么给节点补上发现地址并重启，要么让消费者直接连 `4150`。

主题名和通道名都是第一次使用时才出现，拼写错误会静默制造一个没人读的新名字。约定用小写和短横线，并在仓库里留一份名单，避免 `order_paid` 和 `order-paid` 各存各的。

处理函数应当尽快返回。里面若再去同步调用另一条会回到本通道的链路，可能互相等待，看起来像消费速度突然变成零。这种回环要改成另发一个主题，而不是在回调里阻塞。

停机时先停生产者，等深度降下来，再停消费者，最后停节点。顺序反了，内存里还没刷出的消息要靠节点自己的退出逻辑落盘，默认配置下通常会落，但不要把这个过程当成事务。重启后这些消息会被重新投递，所以业务侧的幂等在演练时就要验证，而不是等真正宕机。

管理台的节点页能看到登记地址。地址若是容器里的主机名，浏览器所在的机器解析不开，页面上的链接会失败。广播地址应写成调用方能够路由到的那个地址，这和绑定监听的地址不是同一个概念：监听可以用全零地址，广播必须是别人连得上的具体地址。

空跑一遍发布和消费，确认管理台深度先升后降，再接到业务。只看进程没退出，不能证明消息真的被确认。把处理函数暂时改成返回错误，深度应维持不住地往上走，改回空错误后再下降。这一下能同时验证重入队和确认两条路径。

通道可以暂停。暂停期间新消息仍会进来，但不会派发给客户端，适合下游数据库维护的窗口。恢复后积压会一次性涌出，下游要扛得住这一小段追赶，必要时先把就绪数量调低。

删除主题会丢掉还没确认的消息，管理台上的删除没有回收站。演练环境可以随意删，生产上应先停生产者，确认深度为零，再删。同名主题稍后被重新发布时，是一个全新的空主题，旧偏移不会保留，因为这里本来就没有按偏移消费的概念。演练时记下删除前的深度和已确认数，重建后再发一条，确认计数从零附近重新开始，而不是接上旧数字。

## 收尾

- 至少一次加上无序，要求消费逻辑用业务主键做幂等。
- 管理台能看到堆积，但堆积本身不会报警，生产里还要把统计接到监控系统。
- 客户端对象可以并发发布，不要为每条消息新建一个生产者。
