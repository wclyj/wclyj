# Go 的并发：goroutine 与调度

## 并发和并行不是一回事

并发描述的是同一段时间里推进多件任务。一个人交替核对两张报表，任务在重叠的时间段内都有进展，这是并发。

并行描述的是同一瞬间真的有多份工作在执行。两台机器各核对一张报表，这是并行。

Go 把并发落实到 goroutine 上。它看起来像线程，却是用户态的执行流，由语言运行时负责排队和切换，而不是直接交给操作系统调度。一个程序里创建成千上万个 goroutine 是常态。运行时还提供 channel，让这些执行流用通信来协作。goroutine 加上 channel，就是 Go 对 CSP（通信顺序进程）这套思路的落地。

学习这部分，核心就是两件事：怎么启动 goroutine，以及怎么用 channel 或标准库里的同步原语等它结束。用户态指的是执行自己编写的逻辑；内核态指的是陷入操作系统去完成系统调用。调度发生在用户态，是 goroutine 比操作系统线程更轻的重要原因。

## Goroutine

用 Java 或 C++ 做并发时，往往要自己维护线程池、把任务包成对象、处理上下文切换。心智负担主要花在“把任务送到 CPU 上”，而不是任务本身。

Go 把这件事收进运行时。需要并发时，把任务写成函数，前面加一个 `go`，运行时会把这个 goroutine 放到合适的逻辑处理器上。程序员侧只保留这一种并发手段，不必再区分进程、线程和协程三套 API。

### 怎么用

一个 goroutine 对应一次函数调用。同一个函数可以被许多 goroutine 同时执行，每次调用有自己的栈和参数。

### 启动一个

普通函数和匿名函数都可以。在调用表达式前写上 `go` 即可。

```go
func greet() {
	fmt.Println("side task ready")
}

func main() {
	greet()
	fmt.Println("primary finished")
}
```

上面的写法是同步调用，`greet` 返回后 `main` 才继续。改成下面这样才会另开一条执行流：

```go
func main() {
	go greet()
	fmt.Println("primary finished")
	time.Sleep(time.Second)
}
```

`main` 所在的 goroutine 返回时，整个进程结束，其它还在跑的 goroutine 会被一起打断。所以主流程必须用某种方式等它们。`time.Sleep` 最直观，但等待时间是猜的：猜短了任务被截断，猜长了程序空转。后面用 `sync.WaitGroup` 按实际完成情况等待。

### 一次启动多条

每启动一条就登记一次，任务结束时销账，主流程阻塞到账清零。

```go
var crew sync.WaitGroup

func greet(n int) {
	defer crew.Done()
	fmt.Println("side task", n)
}

func main() {
	for n := 0; n < 10; n++ {
		crew.Add(1)
		go greet(n)
	}
	crew.Wait()
}
```

`Add` 要放在 `go` 之前。如果放进子任务里，`Wait` 可能抢先观察到计数为零而返回。`Done` 用 `defer` 保证中途返回也能减一。循环变量从 Go 1.22 起每次迭代有独立绑定；更早的版本里，闭包若直接捕获循环变量，可能所有任务都看到最后一次的值，应把变量当参数传进去。

### 什么时候算结束

goroutine 没有单独的“停止”操作。它对应的函数返回，这条执行流就结束了。`main` 返回会结束整个进程，因此主函数返回等价于所有未完成的 goroutine 被强制收场。

## 和操作系统线程比

### 栈会伸缩

操作系统线程通常分配固定大小的栈，常见是 2MB。goroutine 起步只要大约 2KB，随后按调用深度增大，空闲时再缩小，上限可以到 1GB，但很少真的用到那么大。因为初始成本低，一次创建十万条左右是可行的，前提是它们大部分时间在等待，而不是同时占满 CPU。

### G、P、M 三段式调度

这套模型是运行时自己的，不由内核线程调度器替代。

- G 就是 goroutine 本身，保存函数入口、栈以及它和 P 的绑定关系。
- P 是逻辑处理器，手里有一条本地可运行队列，并保存当前 G 的执行现场。P 会把长时间占用的 G 暂停，改跑队列里的下一个。本地队列空了就去全局队列取；全局队列也空了，就从别的 P 那里偷一半任务。
- M 是运行时对内核线程的抽象，一般和一条内核线程一一对应。G 最终要放到某个 M 上才能真正执行。

内核调度线程要在用户态和内核态之间来回切换。goroutine 的排队、切换以及绝大多数内存分配都留在用户态，运行时维护一块大的内存池，不够时才向系统申请。再配合 `GOMAXPROCS` 把可运行的 G 摊到多个核上，就得到了“很多轻量任务复用少量内核线程”的 m:n 调度。代价是：某个 G 如果执行长时间的纯计算且不让出，同一 P 上的其它 G 会被拖住，必要时要用 `runtime.Gosched` 或把工作拆开。

## 使用时的边界

- `go` 出去的函数不要依赖它和主流程的先后顺序，除非用 channel、锁或 `WaitGroup` 明确同步。
- 启动之后没有退出条件的循环会把 goroutine 留到进程结束，通道忘记关闭或接收方提前返回，都是常见泄漏。
- 栈能增长不等于可以无界递归，过深的调用仍会把内存吃光。
